### Stage B/C – Capability Manager Minimal Pack Lifecycle Writer: Register, Activate, Deactivate
- **New `ai_os_kernel.capability_manager` package** (replacing the docstring-only Stage-B/C placeholder scaffolded at Step 1): `errors.py` (`CapabilityManagerError`, `PackAlreadyRegisteredError`, `PackNotFoundError`, `InvalidPackTransitionError`, `PackRegistrationError`), `models.py` (`PackRecord`, mirroring `WorkflowInstance`'s "snapshot returned after a write" role), `ids.py` (`new_transition_id()`, prefix `pkt_` — data_model.md §2's prefix list is illustrative, not exhaustive, the same reasoning `call_` was already chosen under for `evaluation.llm_calls`), `repository.py` (`PackLifecycleRepository` Protocol, `SqlPackLifecycleRepository`).
- **Three operations, not the full eight-state canonical lifecycle** (capability_manager.md §4: `discovered → validated → installed → configured → activated → {deactivated, failed} → uninstalled`): `register()` (installs a fresh pack — no persisted `discovered`/`validated` row exists anywhere in this codebase to transition from, since the Manifest Loader validates a manifest in memory without writing anything, so `register()`'s own recorded transition reads as `discovered → installed`, the lifecycle's first canonical state, not two invented rows), `activate()`, `deactivate()`. No `configured`/`failed`/`uninstalled` states, no version-upgrade path, no health monitoring, no permissions matrix, no sandboxing, no remote/marketplace installation — exactly the approved framing's own exclusions.
- **`activate()` accepts a pack currently `installed` *or* `deactivated`** — capability_manager.md §4's lifecycle diagram draws only the primary forward arrow (`activated → deactivated`, none back), but its own state table calls `deactivated` explicitly "reactivatable." The prose, not the diagram's arrows, is what makes re-activation a real, intended operation; proven directly by a new integration test that activates, deactivates, and re-activates the same pack.
- **Every transition is recorded in `catalog.pack_state_transitions`** with `actor`/`reason`/`occurred_at` — capability_manager.md §8's own documented audit requirement, now genuinely satisfied for the first time rather than an unenforced aspiration. `activate()`/`deactivate()` lock the pack's row (`SELECT ... FOR UPDATE`) before validating its current state and writing, inside one transaction with the transition insert (ADR-0011's "both written in one transaction" pattern, mirroring `workflow_instances`+`workflow_events`) — so two concurrent calls against the same pack cannot both observe the same pre-transition state and both proceed.
- **`register()` rejects a duplicate `pack_id` outright** (`PackAlreadyRegisteredError`) rather than an idempotent upsert — registration is a one-time lifecycle event; re-registering an already-known pack under a new version is an *upgrade*, a distinct, later capability_manager.md §3 responsibility ("Manage pack versions and upgrades") this step does not implement.
- **No new HTTP surface.** No `POST /api/v1/packs`/`.../activate`/`.../deactivate` route (api_architecture.md §6.5 documents these, but a real route would need the `pack:manage` permission modelled and a governance story for "activation of a pack that affects platform behaviour requires human approval," ADR-0007 — neither exists yet). This step is a pure Python write path, called directly (by a test today; by a future route or CLI command later) — the identical "build the real mechanism before deciding how it's triggered" sequencing already used for the Workflow Engine's own trigger before its route existed.
- **Directly proves the one integration point the approved framing named** ("keep agent/tool resolution gated on activated state"): a new integration test registers and activates a pack through `SqlPackLifecycleRepository`, resolves a real agent through the *unchanged* `SqlAgentRegistry`, deactivates the pack, and confirms resolution is refused again with the same `PackNotActivatedError` a hand-seeded row already produced — the new writer's output is provably indistinguishable from test-only seeding for gating purposes, not merely assumed to be.
- **New `tests/integration/capability_manager/test_pack_lifecycle.py`** (10 tests, real Postgres via `testcontainers`, no mocking — ADR-0015): register creates an `installed` row and records `discovered → installed`; a duplicate `pack_id` is rejected; activate transitions `installed → activated`; activating an already-`activated` pack is rejected; activating an unregistered pack raises `PackNotFoundError`; deactivate transitions `activated → deactivated`; deactivating a pack that was never activated is rejected; a deactivated pack can be reactivated (the full four-transition history asserted in order); `get_pack` returns `None` for an unregistered id; and the `SqlAgentRegistry` gating integration test described above. No unit-test file — mirrors the established convention that every `Sql*`-backed class in this codebase (`SqlWorkflowInstanceRepository`, `SqlAgentRegistry`, `SqlPromptCatalog`, ...) is tested exclusively against a real database, never mocked.
- `mypy --strict` (211 source files), `ruff check`, `ruff format --check` all clean on first attempt. Full suite: **436 tests passing, 6 skipped** (six opt-in live tests, skipped by design without credentials). Combined unit+integration coverage: **97.22%** (`capability_manager/`: 95–100% across every new file).

### Stage B/C – Capability Manager Pack Lifecycle Writer Wired Into `kernel/bootstrap.py`
- **`kernel/bootstrap.py`'s `_lifespan` now attaches `app.state.pack_lifecycle_repository = SqlPackLifecycleRepository(engine)`** — one line, added immediately after the existing `workflow_instance_repository` assignment, inside the same `if engine is not None:` branch every other Stage B/C `app.state` attribute already lives in. No new construction logic was needed: `SqlPackLifecycleRepository` already took a bare `AsyncEngine` (see the previous step), so wiring it in was purely "reuse the engine `_lifespan` already builds," exactly as approved.
- **Degrades identically to every sibling attribute**: a missing/misconfigured database leaves `pack_lifecycle_repository` simply absent from `app.state` (never set, never a placeholder, never a crash) — the same "nothing real to run against without a real engine" reasoning `workflow_instance_repository`/`trigger_prompted_agent_workflow` already established. A missing LLM secret alone does not affect this attribute at all, since pack lifecycle writes need no LLM Gateway or Prompt Engine dependency.
- **New `tests/integration/test_bootstrap_pack_lifecycle.py`** (3 tests, real Postgres via `testcontainers`, no live credential needed): the real composition root — `build_app()` + `_lifespan`, not a hand-assembled `SqlPackLifecycleRepository` — genuinely registers, activates, and deactivates a pack, and separately confirms `PackNotFoundError`/`InvalidPackTransitionError` still surface correctly through the bootstrap-built instance; a third test confirms the bare-`TestClient`-never-triggers-`_lifespan` invariant holds for this attribute too, mirroring the identical invariant test already established for `agent_registry`.
- **`tests/unit/kernel/test_bootstrap.py` extended** (2 more tests, 5 total in the file): the degrade-path (no `AIOS_DATABASE_URL` → attribute absent) and the construct-for-real path (a syntactically valid but never-connected database URL — engine construction is lazy, so this exercises real `SqlPackLifecycleRepository` construction with no real infrastructure) — the identical two-sided pattern already used for `agent_registry`.
- **Still deliberately narrow**: no HTTP route reads this attribute (no `/api/v1/packs/...` route exists — explicitly out of scope this step), no discovery, no upgrades, no permissions, no sandboxing. The only caller today is a test with `app.state` in hand; a future route or CLI command is the natural next caller, not built here.
- `mypy --strict` (212 source files), `ruff check`, `ruff format --check` all clean on first attempt. Full suite: **441 tests passing, 6 skipped** (six opt-in live tests, skipped by design without credentials). Combined unit+integration coverage: **97.22%** (`bootstrap.py`: 96%).

### Stage B/C – Minimal `pack:manage`-Gated HTTP Surface for the Capability Manager's Pack Lifecycle Writer
- **Two new permissions**, `PACK_READ`/`PACK_MANAGE` (`ai_os_kernel.security_manager.permissions`), added to the closed vocabulary this codebase enforces (now four permissions total, alongside `workflow:read`/`workflow:start`) — matching api_architecture.md §5's own documented pair ("`pack:read` / `pack:manage` | Read / install, activate, deactivate packs") exactly.
- **Granted only to `maintainer`/`admin`**, not `viewer`/`operator`/`approver` — authentication_authorization.md §4.2's role table gives those three roles grants that never mention packs at all; `maintainer` is the first role the table connects to packs ("`operator` + install/activate/deactivate packs"). Granting `pack:read` to `maintainer` too (not separately spelled out in the prose, but implied — managing a pack requires reading it) is this step's own approved framing's explicit "closest documented permission" allowance, not an invented grant.
- **New `ai_os_kernel/routes/packs.py`**: `POST /api/v1/packs` (register/install), `POST /api/v1/packs/{id}/activate`, `POST /api/v1/packs/{id}/deactivate`, `GET /api/v1/packs/{id}` — all reusing `app.state.pack_lifecycle_repository` (wired into `kernel/bootstrap.py` the previous step) unchanged; no new Capability Manager code was needed.
- **`POST /api/v1/packs` is a reasoned addition, not a documented route.** api_architecture.md §6.5 documents only `GET /packs`, `GET /packs/{id}`, `POST /packs/{id}/activate`, `POST /packs/{id}/deactivate` — no shape for *registering* a pack exists in the docs at all (packs were presumably expected to arrive through a not-yet-built discovery/marketplace flow this step does not build). `POST /api/v1/packs` follows the identical resource-creation convention already established for `POST /api/v1/workflows`/`POST /api/v1/experiments`, returning `201` for a newly created resource.
- **Activate/deactivate return `200` with the real, complete `PackRecord`, not §6.5's documented `202`.** `202` implies accepted-for-later, asynchronous processing — appropriate for a future design where activation may need to wait on ADR-0007 human approval for a pack that affects platform behaviour. Neither approval gating nor any async worker exists yet (explicitly out of scope this step); the underlying repository calls complete synchronously and return a genuinely terminal state — the identical "`200`, not `202`, for work that already finished" reasoning already applied to `POST /api/v1/workflows`.
- **Error mapping**: `PackAlreadyRegisteredError`/`InvalidPackTransitionError` → `409` (api_architecture.md §8: "State conflict" — the same status the docs already use for a conflicting approval decision); `PackNotFoundError` → `404`. An unexpected `PackRegistrationError` (a genuine database failure) is not caught in the route — it propagates to FastAPI's own default `500` handler, the same "no bespoke handling for truly unexpected failures" convention every other route in this codebase already follows.
- **`GET /api/v1/packs` (list) is deliberately not built** — §6.5 documents it, but this step's own approved framing named exactly four operations (register, activate, deactivate, get one pack), not a fifth.
- **New `tests/unit/kernel/routes/test_packs.py`** (13 tests, no real database, no real network — parametrized across all four routes): no bearer token → `401`; a `viewer` token (neither `pack:read` nor `pack:manage` in its documented grants) → `403`; a `maintainer` token with no real database configured → `503` "capability manager is not available"; a bare `TestClient` (lifespan never runs) → `503` from the security dependency itself.
- **New `tests/integration/test_packs_route.py`** (6 tests, real Postgres via `testcontainers`, no live credential needed): a `maintainer` genuinely registers, activates, deactivates, and reads back one pack through the real HTTP routes end to end; a duplicate registration returns `409`; activating an unregistered pack returns `404`; deactivating a pack that was never activated returns `409`; reading an unregistered pack returns `404`; a `viewer` is denied both a register and a read attempt with `403`.
- **`tests/unit/kernel/security_manager/test_permissions.py` updated** — the pre-existing `maintainer`/`admin` exact-equality assertions needed updating for the two new permissions now in their grants (caught by the first full-suite run this step, not missed silently); a new test confirms `viewer`/`operator`/`approver` get neither `pack:read` nor `pack:manage` while `maintainer`/`admin` get both.
- **Still deliberately narrow**: no discovery, no upgrade path, no permissions matrix beyond the two new closed-vocabulary strings, no sandboxing, no Router work, no `GET /api/v1/packs` (list) — exactly this step's own exclusions.
- `mypy --strict` (215 source files), `ruff check`, `ruff format --check` all clean. Full suite: **461 tests passing, 6 skipped** (six opt-in live tests, skipped by design without credentials). Combined unit+integration coverage: **97.12%** (`routes/packs.py`: 95%).
