# AI_OS Implementation History — Workflow Engine Core

**Milestone:** Stage B — the Workflow Engine's own foundational machinery, built increment by increment: definition loading, instance creation, state transitions, multi-step progression, the minimal Agent/Tool contracts and their dispatching step executors, leasing (acquire/release/renew/reap), single-shot and run-to-completion composition, and the materialised per-step/per-event read models (`workflow_steps`, `approvals` schema, `list_steps`/`list_events`).

Split out of the original single `implementation_status.md` on 2026-07-28 — content preserved verbatim, in original order. See `docs/19_roadmap/history/INDEX.md`.

### Stage B – Workflow Engine: Definition Loading and Validation
- **`kernel/src/ai_os_kernel/workflow_engine/`**: `WorkflowDefinitionLoader.load(path)` reads one workflow definition YAML file and returns a validated, in-memory `WorkflowDefinition` — field-for-field against the Workflow Contract (`docs/03_architecture/workflow/workflow_architecture.md`), the Human Approval Point Contract (`human_approval_points.md` §4), and the concurrency rule in `workflow_engine.md` §7.1. Fails clearly (`WorkflowDefinitionError`) on a missing file, invalid YAML, a non-mapping document, or any structural violation — never a bare stack trace.
- Validates: required fields (`id`, `name`, `description`, `version`, `inputs`, `outputs`, `steps`, `failureHandling`); `id`/`version` patterns mirroring `platform_sdk/schemas/manifest.schema.json`'s `workflows[]` entry; `inputs`/`outputs` are well-formed JSON Schema documents (via the already-used `jsonschema` library); `steps` non-empty with unique `id`s; a `parallel` step must declare `joinPolicy` (`all`/`any`/`collect`) — explicitly mandatory, "fails validation rather than defaulting silently"; `qualityGates` entries are well-formed gate-id references; `humanApprovalPoints` entries satisfy the full Human Approval Point Contract (`context`, non-empty `options`, etc.); `retryPolicy`, when declared, must bound both attempts and duration ("Retries must be bounded (maximum attempts + maximum duration)" — `error_handling_retry.md` §4); unrecognised fields are rejected (`extra="forbid"`), matching the Manifest Loader's strictness.
- **Deliberately deferred, not invented:** per-step-type fields beyond `id`/`type` (agent/tool references, decision branching, sub-workflow linkage, quality-gate-step/human-approval-step payloads) — no document defines a field-level contract for these yet. Recorded in the module docstring so a future step doesn't mistake the gap for an oversight.
- 17 unit tests (`tests/unit/kernel/workflow_engine/test_loader.py`): one valid minimal definition, one with a full `humanApprovalPoints` entry and `retryPolicy`, and 15 distinct invalid-input cases (missing file, bad YAML, non-mapping, missing required field, unknown field, bad `id`/`version`, empty `steps`, duplicate step ids, `parallel` without `joinPolicy`, malformed gate reference, empty `failureHandling`, `humanApprovalPoints` without options, unbounded `retryPolicy`, malformed `inputs` schema).
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full unit suite: 46 tests passing.

### Stage B – Workflow Engine: Instance Creation Only
- **`kernel/src/ai_os_kernel/workflow_engine/ids.py`**: `new_workflow_id()`/`new_event_id()` — prefixed ULIDs (`wf_…`, `evt_…`) per data_model.md §2, using `python-ulid`.
- **`input_validation.py`**: `validate_inputs()` checks candidate inputs against the definition's already-validated `inputs` JSON Schema (via `jsonschema.Draft202012Validator`); `validate_principal()` rejects a blank `principal_id` — `workflow_instances.principal_id` is `NOT NULL` and an empty string would satisfy that constraint while meaning nothing. Both raise `WorkflowInputValidationError`.
- **`instance.py`**: `WorkflowInstance` (frozen) and `WorkflowInstanceStatus` (the canonical nine-state enum, workflow_engine.md §7) — the in-memory shape of one `workflow_instances` row.
- **`repository.py`**: `WorkflowInstanceRepository` (`Protocol`) and its only implementation, `SqlWorkflowInstanceRepository` — writes the `workflow_instances` row (`status = created`, `last_event_seq = 1`) and the first `workflow_events` row (`workflow.started`, `seq = 1`) inside one `engine.begin()` transaction, returning the instance read back via `RETURNING`. Failures are wrapped in `WorkflowInstanceCreationError`.
- **`service.py`**: `WorkflowInstanceService.create_instance()` — validates (principal, then inputs), then delegates to the injected repository. No DI container (ADR-0010): the concrete repository is constructed and handed in by the caller.
- **Deliberate design note:** `workflow_events.occurred_at` is application-supplied (`datetime.now(UTC)`), not database-generated — a departure from data_model.md §2's blanket "TIMESTAMPTZ … database-generated" convention, reasoned explicitly in `repository.py`: an event's occurrence time is a fact the application knows and the database commit clock does not. `created_at`/`updated_at` on `workflow_instances` remain database-generated, unchanged.
- 9 new unit tests (input validation + a fake-repository service test proving validation runs *before* any repository call) and 3 new integration tests against real Postgres (`tests/integration/workflow_engine/test_instance_creation.py`): the repository writes both rows correctly; the service produces the same result end-to-end through a real `SqlWorkflowInstanceRepository`; and — the key proof — a deliberately-broken second insert inside one `engine.begin()` block leaves **no** trace of the first insert, demonstrating the one-transaction guarantee ADR-0011 requires.
- No FastAPI route added. This step built a callable service, not an HTTP surface — nothing currently asked for one, and adding one would have been scope beyond what was approved.
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite at this point: 62 tests passing (55 unit + 7 integration: 4 persistence + 3 workflow_engine).

### Stage B – Workflow Engine: State Transition (`created` → `running`)
- **`repository.py`**: `WorkflowInstanceRepository.transition_to_running()` and its `SqlWorkflowInstanceRepository` implementation. The guard ("only `created` → `running`") is the `UPDATE workflow_instances ... WHERE status = 'created'` clause itself — one atomic statement, no separate read-then-write race window. `last_event_seq` is incremented via `last_event_seq + 1` in the same statement rather than a hardcoded `2`, so it does not assume this is always the second event. On no matching row, raises `WorkflowInvalidTransitionError` with a message distinguishing "instance does not exist" from "instance exists but is in status X, not created" (a follow-up `SELECT` on the failure path only).
- The `state.transitioned` event payload carries exactly the four things workflow_engine.md §7 says every transition event must carry: `previousStatus`, `newStatus`, `reason`, `triggeringEventId` (nullable — no leasing/trigger producer exists yet, so it is always `None` at this stage, not invented content).
- **`input_validation.py`**: added `validate_reason()` (reused the existing blank-check helper — `validate_principal` and `validate_reason` now both call a shared `_require_non_blank`).
- **`service.py`**: `WorkflowInstanceService.start(workflow_id, reason, triggering_event_id=None)` — validates `reason`, then delegates. No status check duplicated at the service layer; the repository's guard is the single source of truth.
- **`errors.py`**: added `WorkflowInvalidTransitionError` (guard rejection — distinct from `WorkflowInstanceCreationError`, which now also covers a transition write that fails unexpectedly).
- 6 new unit tests (`test_service.py`): `start()` delegates correctly, passes through an optional `triggering_event_id`, and rejects a blank `reason` before the repository is ever called.
- 4 new integration tests (`tests/integration/workflow_engine/test_state_transitions.py`) against real Postgres: the happy path (status becomes `running`, `last_event_seq` becomes 2, the event payload has the right shape); a second transition attempt on an already-`running` instance is rejected with no new event written; a transition on a non-existent instance is rejected; and — the atomicity proof — a pre-inserted conflicting event forces the transition's own event insert to fail *after* its guarded `UPDATE` already matched a row, and the instance is confirmed to still read `status = created`, `last_event_seq = 1` afterward, proving the "succeeded" update was rolled back.
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite at this point: 69 tests passing (58 unit + 11 integration).

Real agent invocation, real tool invocation, and LLM calls remain out of scope. (This module is unchanged by the generalization below.)

### Stage B – Workflow Engine: Multi-Step Progression and Completion
- **`repository.py`**: the first-step-only `complete_first_step_noop()` is **replaced** by `WorkflowInstanceRepository.advance_workflow()` (plus a new plain-read `get_instance()`), which generalises "execute the first step" into "advance by exactly one step, or complete if none remain." The guard is the same atomic `UPDATE ... WHERE` pattern, now comparing `current_step_id` against a caller-supplied `expected_current_step_id` (`None` for "no step yet," or a specific step id) instead of hardcoding `IS NULL` — the same check-and-write-in-one-statement design, generalised rather than duplicated. When `next_step` is given: appends `step.started`/`step.completed`, `last_event_seq += 2`. When `next_step` is `None` (no step left in the definition): appends `workflow.completed` — a documented event-type example in data_model.md §4.2 — and sets `status = completed`, `completed_at = now()`, `last_event_seq += 1`. `WorkflowInvalidTransitionError` distinguishes "does not exist" / "not running" / "wrong definition" / "current step is X, not the expected Y — it may have already advanced."
- The `workflow.completed` payload is deliberately `{}` — no document specifies what fields it should carry (unlike `step.started`/`step.completed`, which trace to `workflow_steps` columns), so nothing was invented. `step.started`/`step.completed` payloads are unchanged from the previous step.
- **`service.py`**: `execute_first_step()` is **replaced** by `WorkflowInstanceService.advance(workflow_id, definition)`. It reads the instance (`get_instance`) to learn `current_step_id`, resolves the next step by position in `definition.steps` (`None` → `steps[0]`; found → the following entry or `None` if last; not found → a clear rejection — the instance's current step doesn't belong to this definition), runs the executor if there is a next step, then delegates the write. One call advances by one step; a caller (test, or later an orchestrator) drives repeated calls to reach completion. No internal loop, no scheduler — still out of scope.
- 6 new/changed unit tests (`test_service.py`, generalized fake repository): first-step resolution when `current_step_id` is `None`; second-step resolution after the first; completion after the final step; rejection when the instance doesn't exist; rejection when `current_step_id` doesn't match any declared step; rejection when the definition has no steps (unchanged case, preserved through the rewrite).
- 5 new integration tests, replacing the superseded first-step-only file (`tests/integration/workflow_engine/test_step_progression.py`) against real Postgres: full progression first → second → `workflow.completed` in one continuous flow (asserting the exact 7-event sequence and `step_id`/`payload` shapes); rejected when not `running`; rejected when already `completed`; rejected on a stale `expected_current_step_id` (a caller acting on data read before another advance happened); and the atomicity proof — a pre-inserted conflicting event forces the `workflow.completed` insert to fail *after* the guarded `UPDATE` already matched a row, and the instance is confirmed to still read `status = running`, `completed_at = NULL`, `last_event_seq` unchanged afterward.
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite at this point: 80 tests passing (64 unit + 16 integration).

### Stage B – Workflow Engine: Minimal Agent Contract and Real Trivial Agent Invocation
- **`agent.py`** (new): `Agent` (`Protocol`) — `output_schema: dict[str, Any]` plus `async def execute(inputs) -> outputs`. A deliberately reduced slice of the full Agent Contract (`docs/03_architecture/agents/agent_architecture.md`): no `AgentRequest`/context/security-context/budget/deadline, no Prompt Registry, no LLM Gateway, no Tool Invoker — all separate, not-yet-built Kernel components. `input_schema` is deliberately **not** included: no per-step input-mapping mechanism exists yet (that is the Context Manager's job), so there is nothing real to validate against — adding it now would be a half-finished field. `EchoAgent` is the one trivial in-process implementation, declaring and satisfying a minimal `output_schema`.
- **`step_executor.py`**: `AgentStepExecutor` invokes the injected `Agent` with `{}` (no per-step inputs yet) and validates the returned output against `agent.output_schema` via `jsonschema.Draft202012Validator` — the same library already used everywhere else in this codebase, no new validation approach introduced. Raises `AgentOutputValidationError` (new, in `errors.py`) with every violation listed, clearly. Guards against being handed a non-Agent step (`ValueError` — an internal wiring bug, not a runtime condition, so not part of the platform's structured-error taxonomy). `DispatchingStepExecutor` routes an Agent-type step to `AgentStepExecutor` and every other step type to `NoOpStepExecutor` — the only place that knows both exist; neither executor needs to know about step types it doesn't handle.
- **No changes to `service.py` or `repository.py`.** `WorkflowInstanceService` already took any `StepExecutor` — wiring `DispatchingStepExecutor(AgentStepExecutor(EchoAgent()), NoOpStepExecutor())` happens entirely at the call site (composition root / tests), proving the Protocol boundary from the previous step was genuinely sufficient.
- 5 new unit tests (`test_agent_step_executor.py`): the agent is called and its output returned; an agent whose output violates its own declared schema is rejected with a clear message; a non-Agent step is refused; the dispatcher routes an Agent step to the agent executor and everything else to the default executor.
- 1 new integration test (`tests/integration/workflow_engine/test_agent_step_execution.py`) against real Postgres, through the real `WorkflowInstanceService.advance()`: a two-step definition (one `agent` step, one `tool` step) is driven to completion; the `step.completed` event for the agent step carries the agent's real output (`{"status": "ok"}`), while the tool step's `step.completed` event still carries `{}` — proving the dispatcher genuinely differentiates behaviour end to end, not just at the unit level.
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite at this point: 86 tests passing (69 unit + 17 integration).

### Stage B – Workflow Engine: Minimal Tool Contract and Real Trivial Tool Invocation
- **`tool.py`** (new): `Tool` (`Protocol`) — `trust_tier: TrustTier` plus `output_schema: dict[str, Any]` plus `async def execute(inputs) -> outputs`. Grounded directly in `platform_sdk/schemas/manifest.schema.json` `tools[]` — the authoritative Tool Contract, which requires `outputSchema` and `trustTier` alongside registration metadata (`id`, `name`, `version`, `description`, `entrypoint`) that belongs to the Manifest Loader, not to invoking an already-resolved tool object. `TrustTier` is a `StrEnum` with exactly the schema's two values (`tier1_sandboxed`, `tier2_trusted`). `input_schema` is excluded for the same reason as Agent's: no per-step input-mapping mechanism exists yet. `EchoTool` is the one trivial implementation, honestly declared `tier2_trusted` (it executes no command, compiles nothing, processes no untrusted content — the ADR-0016 conditions that would require `tier1_sandboxed`).
- **`step_executor.py`**: `ToolStepExecutor` invokes the injected `Tool` with `{}` and validates the returned output against `tool.output_schema`, mirroring `AgentStepExecutor` exactly. It additionally refuses any tool that is not `tier2_trusted` (`ToolSandboxRequiredError`, new) — there is no sandbox yet, so running a `tier1_sandboxed` tool in-process would silently violate the guarantee that tier is supposed to carry. `DispatchingStepExecutor`'s constructor is now three-way: `agent_executor`, `tool_executor`, `default_executor` — Tool-type steps route to the tool path, everything else unchanged.
- **`errors.py`**: added `ToolOutputValidationError` (mirrors `AgentOutputValidationError`) and `ToolSandboxRequiredError` (the trust-tier guard — a genuine, expected runtime rejection, not an internal wiring bug, so it gets a real error class rather than the `ValueError` used for the "wrong step type" guard).
- **No changes to `service.py` or `repository.py`** — same reasoning as the Agent step: the `StepExecutor` Protocol boundary was already sufficient.
- 7 new/changed unit tests: `test_tool_step_executor.py` (4 tests, mirroring the agent ones, plus the `tier1_sandboxed` rejection) and a new `test_dispatching_step_executor.py` (3 tests, fake executors throughout, proving the three-way routing in isolation — the two dispatching tests previously inline in `test_agent_step_executor.py` moved here since the dispatcher's own contract no longer belongs to either single-executor test file).
- 1 integration test, replacing the superseded agent-only file (`tests/integration/workflow_engine/test_agent_and_tool_step_execution.py`) against real Postgres: a three-step definition (`agent`, `tool`, `human_approval`) is driven to completion through the real `WorkflowInstanceService.advance()`; the agent step's `step.completed` event carries `{"status": "ok"}`, the tool step's carries `{"result": "ok"}`, and the human-approval step's still carries `{}` — proving all three paths are genuinely distinct end to end.
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite at this point: 91 tests passing (74 unit + 17 integration).

### Stage B – Workflow Engine: Lease Acquisition and Release
- **`lease.py`** (new): `WorkflowLease` (frozen, mirrors `WorkflowInstance`'s pattern), `WorkflowLeaseRepository` (`Protocol`) and its implementation `SqlWorkflowLeaseRepository`, and `WorkflowLeaseService`. Grounded in data_model.md §4.4 and workflow_engine.md §7.1: "Claimed with `SELECT … FOR UPDATE SKIP LOCKED`... expiry is what makes a crashed worker's work recoverable."
- **`acquire()` is one transaction, three steps:** (1) the target instance must exist and be `running` — leasing anything else is rejected (`WorkflowLeaseUnavailableError`, new); (2) `INSERT ... ON CONFLICT (workflow_id) DO NOTHING RETURNING *` — the common, no-contention case, one round trip; (3) only if a lease row already exists: `SELECT ... WHERE expires_at < now() FOR UPDATE SKIP LOCKED` — reclaims an **expired** lease, and `SKIP LOCKED` means a concurrent claimant racing for the exact same row gets no row back immediately rather than blocking on the other transaction. A non-expired existing lease, or a concurrently-locked row, both surface as the same clear rejection.
- **`release()`** deletes the lease row, but only if `worker_id` matches the holder — a worker cannot release someone else's lease. `WorkflowLeaseUnavailableError` again, distinguishing "does not exist" from "does not hold."
- **Deliberately deferred, not invented (at the time):** heartbeat *renewal* and a background expiry reaper. Renewal is now built (see next section); the reaper remains deferred.
- **No changes to `WorkflowInstanceService`/`WorkflowInstanceRepository`.** Leasing is deliberately a separate, independently composable service — `advance()` has no lease-awareness baked in. The documented "claim before calling `advance()`, release afterward" pattern is proven by composition in the tests (acquire → `advance()` → release), not by a new merged method; a future worker-loop orchestrator is the natural place to own that composition, and it does not exist yet.
- **`input_validation.py`**: added `validate_worker_id()` (reuses the shared `_require_non_blank` helper) and `validate_lease_duration()` (must be positive — a lease expiring at or before acquisition protects nothing).
- **`ids.py`**: added `new_lease_id()` (`lease_` prefix — data_model.md's prefixes are illustrative examples, not an exhaustive list, so this is a reasoned choice, not an invented schema field).
- 5 new unit tests (`test_lease_service.py`, fake repository): acquire/release delegate correctly; a blank `worker_id` is rejected before either operation reaches the repository; a non-positive `lease_duration_seconds` is rejected before acquire.
- 7 new integration tests (`tests/integration/workflow_engine/test_lease_acquisition.py`) against real Postgres: acquire-then-release leaves no row behind; a second claim while held is rejected; `advance()` succeeds normally with the lease held; release lets a different worker claim afterward; releasing without holding the lease is rejected; acquiring against a non-`running` instance is rejected; and an expired lease (its `expires_at` forced into the past to simulate a crashed worker, since heartbeat renewal doesn't exist to keep it current) is successfully reclaimed by a different worker.
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite at this point: 103 tests passing (79 unit + 24 integration).

### Stage B – Workflow Engine: Lease Heartbeat Renewal
- **`lease.py`**: `WorkflowLeaseRepository.renew()` / `WorkflowLeaseService.renew()` (plus the `SqlWorkflowLeaseRepository` implementation) complete the "acquire → heartbeat → release" cycle from workflow_engine.md §7.1. One atomic guarded `UPDATE workflow_leases SET expires_at = :new_expiry, heartbeat_at = now() WHERE workflow_id = :id AND worker_id = :worker_id AND expires_at >= now() RETURNING *` — the row is already known (unlike `acquire()`'s reclaim step, which scans an *unknown* row's state), so the guarded `UPDATE` itself is the correct, sufficient atomic primitive; `FOR UPDATE SKIP LOCKED` is deliberately **not** used here, and the module docstring now explains why, so a future reader doesn't mistake the absence for an oversight. Postgres's ordinary row lock during the `UPDATE` already serialises a renewal against a concurrent `acquire()` reclaim attempt on the same row.
- On rejection, `WorkflowLeaseUnavailableError` distinguishes three cases via a new `_describe_rejected_renewal` helper (mirroring the `_describe_rejected_*` pattern already used in `repository.py`): no lease exists at all; the lease is held by a different worker; the caller's own lease already expired (and may have been reclaimed by someone else).
- **`WorkflowLeaseService.renew()`** validates `worker_id` and `lease_duration_seconds` before delegating — identical validation to `acquire()`, reusing the same `input_validation.py` functions (no duplicated logic).
- 3 new unit tests (`test_lease_service.py`, fake repository extended with `renew`): renewal delegates correctly; a blank `worker_id` is rejected before renew reaches the repository; a non-positive `lease_duration_seconds` is rejected before renew.
- 5 new integration tests (`tests/integration/workflow_engine/test_lease_acquisition.py`) against real Postgres: the holder renews and `expires_at` genuinely advances; a non-holder's renewal attempt is rejected; renewing a lease that doesn't exist is rejected; renewing an already-expired lease is rejected; and — the key proof for this step — a lease acquired with a 1-second duration, then renewed to 60 seconds, is confirmed **still** claim-protected after the original 1-second window has elapsed (a second worker's `acquire()` attempt at that point is still rejected), proving the renewal genuinely extended protection rather than just updating a timestamp cosmetically.
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite at this point: 111 tests passing (82 unit + 29 integration).

### Stage B – Workflow Engine: Single-Shot Claim-and-Advance Composition
- **`advance_runner.py`** (new): `WorkflowAdvanceRunner.run_once(workflow_id, definition, worker_id, lease_duration_seconds)` — acquires a lease via the injected `WorkflowLeaseService`, calls `WorkflowInstanceService.advance()` exactly once, and releases the lease in a `finally` block. Release runs whether `advance()` succeeds or raises; if acquisition itself fails, `advance()` is never called and there is nothing to release. No new abstraction beyond a plain `try`/`finally` — the two composed services already do their own validation and guarding, so the runner adds no logic of its own beyond ordering the three calls correctly.
- **No changes to `WorkflowInstanceService`, `WorkflowLeaseService`, or either repository.** This step is purely composition over the two existing, already-Protocol-backed services — confirming they were genuinely independent and composable, as designed across the two previous steps.
- Deliberately not a Protocol-based dependency: `WorkflowAdvanceRunner` takes the concrete `WorkflowInstanceService`/`WorkflowLeaseService` classes directly, matching how every other call site in this codebase composes services (only the *repository* boundary underneath each service is a `Protocol`). Adding a second layer of interfaces here, with only one implementation of each service ever to exist, would be an unused abstraction.
- Explicitly not a loop: one call is one `acquire` → one `advance` → one `release`. A future worker loop would call `run_once` repeatedly and decide for itself when a long-running step needs `WorkflowLeaseService.renew()` in between — that decision and the loop itself remain out of scope.
- 3 new unit tests (`test_advance_runner.py`, fake repositories under real services): the happy path calls acquire → advance → release in order; when `advance()` raises, release still happens and the original exception still propagates to the caller (not swallowed, not replaced); when lease acquisition itself is rejected, `advance()` is never reached and no release is attempted.
- 4 new integration tests (`tests/integration/workflow_engine/test_advance_runner.py`) against real Postgres: a full claim→advance→release cycle leaves no lease row behind; a definition-id mismatch causes `advance()` to fail *after* the lease was already acquired, and the lease is still released; a lease already held by another worker is rejected before `advance()` runs at all (proving the existing concurrency-rejection behaviour survives being wrapped in this composition); and `run_once` called twice in sequence drives a one-step workflow all the way to `workflow.completed`.
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite: **118 tests passing** (85 unit + 33 integration: 4 persistence + 3 instance-creation + 4 state-transition + 5 step-progression + 1 agent-and-tool-step-execution + 12 lease-acquisition-and-renewal + 4 advance-runner).

### Stage B – Workflow Engine: Run-to-Completion Loop for One Instance
- **`advance_runner.py`**: `WorkflowAdvanceRunner.run_to_completion(workflow_id, definition, worker_id, lease_duration_seconds, max_iterations)` — calls `run_once()` repeatedly for **one** instance until it reaches `completed`, `max_iterations` calls have been made without completing, or a call raises. Added as a second method on the existing `WorkflowAdvanceRunner` rather than a new class: it already composes the two services this loop needs, so no additional wiring or abstraction was introduced.
- **`WorkflowRunOutcome`** (new `StrEnum`: `completed` / `max_iterations_reached` / `failed`) and **`WorkflowRunResult`** (new frozen Pydantic model: `workflow_id`, `outcome`, `iterations`, `last_instance`, `error`) — a structured, always-returned summary of what happened. `error` is typed `BaseException | None`, which requires `ConfigDict(frozen=True, arbitrary_types_allowed=True)` (the one model in the codebase holding a raw exception instance, matching the pattern of every other frozen read-model/snapshot type otherwise).
- **Deliberate broad `except Exception` boundary:** `run_to_completion` is an explicit, documented exception to this codebase's usual avoidance of broad excepts — it exists specifically to convert whatever `run_once()` raises into a non-raising `WorkflowRunResult` (`outcome=failed`, the exception captured in `error`) so a caller can inspect a multi-iteration run without wrapping every call in its own `try`/`except`. `run_once()` itself is unchanged and still always propagates exceptions normally.
- **Validation-before-loop:** `validate_max_iterations()` (new, in `input_validation.py` — non-positive is rejected, mirroring `validate_lease_duration`) runs *before* the loop starts and is allowed to raise `WorkflowInputValidationError` normally, not converted into a `FAILED` result — reasoned as a caller programming error (like a bound of zero, which would never even attempt one `advance()` call), not a workflow-runtime outcome.
- **No changes to `WorkflowInstanceService`, `WorkflowLeaseService`, `run_once()`, or either repository.** Each `run_once()` call still acquires and releases its own lease independently; hitting the `max_iterations` bound from the outer loop leaves no lease behind, proven explicitly in the new tests rather than merely assumed.
- 4 new unit tests (`test_advance_runner.py`, extended with a new stateful fake repository — `_StatefulInstanceRepository` — that tracks `current_step_id`/`status` across calls, since the original stateless fake used for `run_once` tests always reported the same fixed state regardless of what `advance_workflow` had returned): a two-step workflow reaches `completed` across multiple iterations with matching acquire/release counts; `max_iterations=1` stops the loop with `MAX_ITERATIONS_REACHED` after exactly one `advance()` call; a simulated failure on the second call is reported as `FAILED` with the exception captured in `result.error`, not raised, and the lease is still shown released; a non-positive `max_iterations` is rejected before any advance/lease call happens.
- 3 new integration tests (`tests/integration/workflow_engine/test_advance_runner.py`) against real Postgres: a two-step definition run through `run_to_completion` reaches `completed` in exactly 3 iterations (step_a, step_b, the completing call) with no lease row left behind; `max_iterations=1` on the same definition stops before completion, with the lease still fully released; and a definition-id mismatch causes every `advance()` call's guard to reject it, `run_to_completion` reporting `FAILED` without letting the exception propagate out of the call.

### Stage B – Workflow Engine: Background Lease Expiry Reaper
- **`lease.py`**: `WorkflowLeaseRepository.reap_expired(limit)` / `WorkflowLeaseService.reap_expired(limit)` (plus the `SqlWorkflowLeaseRepository` implementation) close the one remaining reactive gap in the acquire → renew → release → reclaim cycle — until this step, an expired lease was only reclaimed as a side effect of some *other* worker's next `acquire()` call on the same instance; if nothing ever called `acquire()` again (every capable worker crashed or moved on), the stale row sat there indefinitely.
- **`reap_expired()` is one bounded transaction, two steps:** (1) `SELECT lease_id ... WHERE expires_at < now() ORDER BY expires_at LIMIT :limit FOR UPDATE SKIP LOCKED` — scans for candidate rows, capped at the caller-supplied `limit`; a row currently being touched by a concurrent `acquire()`/`renew()`/`release()` is skipped this pass (no row returned for it) rather than blocked on, the same "scanning an unknown row's state" reasoning already used for `acquire()`'s reclaim step. (2) `DELETE ... WHERE lease_id IN (...) RETURNING *` — deletes exactly the rows just locked. Under Postgres's default READ COMMITTED isolation, a concurrent transaction that renews or reclaims one of those rows and commits first causes the `DELETE`'s own re-evaluated `WHERE` to simply not match that row anymore — no separate check-then-act race window, the same guarantee every other guarded statement in this module relies on.
- **`lease_reaper.py`** (new): `WorkflowLeaseReaper.reap_once(limit)` — a thin, structured-logging wrapper over `WorkflowLeaseService.reap_expired()` (no new persistence logic), and `LeaseReapResult` (frozen, holds the reclaimed `WorkflowLease` tuple plus a `count` property). Logs one structured `workflow_lease_reaper.reaped` event (count + affected `workflow_id`s) when anything was reclaimed, `workflow_lease_reaper.no_expired_leases` otherwise — the "Structured logging/errors" requirement for this step. Composes the existing `WorkflowLeaseService` exactly as `WorkflowAdvanceRunner` composes its two services: no new abstraction layer for a job with only one implementation.
- **Deliberately not a scheduler:** `reap_once()` is exactly one bounded pass — nothing in this module decides when or how often to call it, or loops it. A future worker process framework would call it on a timer, deciding scheduling for itself (explicitly out of scope here, per the approved step).
- **`input_validation.py`**: added `validate_reap_limit()` (must be positive, mirroring `validate_max_iterations` — a bound of zero or fewer would never examine a single lease).
- **No changes to `acquire()`, `renew()`, `release()`, `WorkflowInstanceService`, or either instance repository.** The reaper only ever deletes rows that `acquire()`'s own guard already treats as worthless (`expires_at < now()`); it does not change what "expired" means or how acquisition/renewal validate it.
- 6 new unit tests: `test_lease_service.py` extended with `reap_expired` on the fake repository (delegates correctly; a non-positive `limit` is rejected before the repository is called); new `test_lease_reaper.py` (fake `WorkflowLeaseRepository` under the real `WorkflowLeaseService`): `reap_once` returns and the caller can inspect exactly what was reclaimed; an empty result when nothing is expired; the caller-supplied `limit` is honored even when more candidates exist than the bound; a non-positive `limit` is rejected before any repository call.
- 3 new integration tests (`tests/integration/workflow_engine/test_lease_acquisition.py`) against real Postgres: an expired lease is reclaimed while a second, still-active lease on a different instance is left completely untouched; reaping across three simultaneously-expired leases with `limit=2` reclaims exactly two in the first pass and the remaining one in a second pass (proving the bound is real, not advisory); and the `WorkflowLeaseReaper` job itself, composed over the real service and repository, reclaims an expired lease end to end. A new `_clear_all_leases()` test helper gives these tests a clean slate, since `reap_expired` reasons about *all* rows in `workflow_leases` and several earlier tests in the same module-scoped fixture deliberately leave lease rows (held or expired) behind.
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite: **134 tests passing** (95 unit + 39 integration: 4 persistence + 3 instance-creation + 4 state-transition + 5 step-progression + 1 agent-and-tool-step-execution + 15 lease-acquisition-renewal-and-reaping + 7 advance-runner).
