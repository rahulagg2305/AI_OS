### Stage B – Retrieval: Knowledge Schema and Database Migration (data_model.md §7, ADR-0013 — First Real Retrieval Increment)

- **Two architecture reviews performed before any code, per this step's own approved framing — the second triggered by a genuine finding during the first's own validation pass, not by a documentation change.** The first pass (validating against implementation_roadmap.md, data_model.md §7, kernel_architecture.md, ADR-0013, `knowledge_manager.md`, `memory_manager.md`) surfaced two findings and stopped rather than proceeding: (1) `knowledge.embeddings.embedding` is documented as `vector(N)` — pgvector's own Postgres type — which appeared to contradict this step's own "no hidden dependency on pgvector" validation checklist item; (2) the referenced `retrieval.md` does not exist anywhere in the docs tree — the real governing document is `docs/03_architecture/services/search_vector_search.md` (per `DOCUMENTATION_INDEX.md` §9), a naming discrepancy surfaced rather than silently substituted. A second, deeper documentation-driven review (requested explicitly rather than accepting either of two convenience-driven paths) found that `infra/docker-compose.yml` already runs `pgvector/pgvector:pg16` (provisioned since Stage A), `deployment_architecture.md` §5's production topology already names "postgres (with pgvector)", and ADR-0013 already Accepts pgvector as this platform's search/vector technology — concluding this was a **sequencing issue already resolved by existing architecture**, not a genuine conflict, and that the first pass's own alarm should have checked the infra layer before being raised. Both reviews delivered and approved before any code.
- **New `ai_os_kernel.persistence.knowledge_schema` module** — all four tables data_model.md §7 documents: `documents` (`document_id` PK, `source_uri`, `content_hash`, `media_type`, `project_id` nullable, `trust` with a `trusted`/`untrusted` check constraint, `ingested_at`, `archived_at` nullable), `chunks` (`chunk_id` PK, FK to `documents`, `ordinal`, `content`, `token_count`, `chunk_strategy_version`, a real generated `content_tsv tsvector` column, `metadata jsonb`, unique on `(document_id, ordinal)`), `embeddings` (`embedding_id` PK, FK to `chunks`, `embedding`, `embedding_model_id`, `embedding_model_version`, `dimensions`, `index_generation`), and `memory_items` (`memory_id` PK, `memory_type` with a `workflow`/`engineering`/`asset` check constraint, `content`, a real FK to `workflow.workflow_instances.workflow_id`, `quality_signal`/`promoted_at`/`expires_at` nullable, `provenance jsonb`) — the identical "own `MetaData`, own schema, schema-and-migration-only, no reader/writer/search logic" precedent already established for `trace`/`governance`/`platform`/`catalog`/`evaluation`. A new `kernel/alembic/versions/0029_knowledge_schema.py` migration mirrors it column-for-column, plus `CREATE SCHEMA IF NOT EXISTS knowledge` and `CREATE EXTENSION IF NOT EXISTS vector`, with a fully symmetric `downgrade()` (drops all four tables, then the schema, then the extension). `kernel/alembic/env.py` gains `knowledge_metadata` in `target_metadata`. New Python dependency: `pgvector>=0.3,<1.0` (ADR-0009 — `pyproject.toml` edited, `uv.lock` regenerated and verified against both the latest `uv` and the CI-pinned `uv==0.5.11`).
- **`embeddings.embedding` is declared as an unconstrained `pgvector.sqlalchemy.Vector()` (no fixed dimension), and the documented HNSW index on it is deliberately not created — a decision made and recorded during implementation, not raised as a third stop-and-report cycle, since (unlike the extension question) it had exactly one clear, precedented, non-speculative answer.** data_model.md §7's own `vector(N)` notation names no concrete `N` anywhere in the approved documentation, and inventing one (1536, 1024, …) would be exactly the "no speculative architecture" this step must avoid; the table's own separate, per-row `dimensions` column (alongside `embedding_model_id`/`embedding_model_version`) confirms the schema already anticipates rows from different embedding models — and therefore different real vector sizes — coexisting, which an unconstrained column is the faithful reading of, not a workaround. pgvector's HNSW index requires a fixed dimension to be created at all, which requires the same not-yet-made embedding-model decision the column itself defers; the GIN index on `chunks.content_tsv` has no such dependency and is created normally. The HNSW index is deferred to whichever future step first chooses a real embedding model and dimension, at which point it is a purely additive migration, not a redesign of this one. `content_tsv` uses `to_tsvector('english', content)` — a concrete, necessary choice (English is this project's own working language throughout every existing document) to make a documented "generated" column real, changeable later in a purely additive migration.
- **New integration tests only, per the established "schema-and-migration-only steps get integration tests, not unit tests" precedent** (`trace`/`governance`/`platform` schema steps have none either): `tests/integration/persistence/test_migrations.py` gains a `_EXPECTED_KNOWLEDGE_TABLES` set (folded into the existing up/down/up round-trip test, now covering seven schemas across twenty-nine migrations) and 14 new tests — `pg_extension` genuinely lists `vector` after upgrade; each of the four tables' real column shapes; the `trust`/`memory_type` check constraints reject an invalid value; `chunks`/`embeddings`/`memory_items`' foreign keys reject an unknown parent row; the `(document_id, ordinal)` unique constraint rejects a duplicate; `content_tsv` is proven genuinely generated (real content inserted, read back via `::text`, the stemmed term "architectur" found — not just declared); the unconstrained `embedding` column is proven to genuinely accept a 3-dimension and an 8-dimension vector in the same table — the key behavioural proof of the architectural decision above; and `quality_signal`/`promoted_at`/`expires_at` are proven to genuinely default to `NULL`.
- **Still deliberately narrow, exactly per this step's approved scope**: no Retrieval Service, no keyword/vector/hybrid search, no RRF, no embedding generation (nothing calls the still-nonexistent LLM Gateway `embed()`), no chunking pipeline, no knowledge ingestion, no Knowledge Manager or Memory Manager component (their existing empty stub packages under `knowledge_manager/`/`memory_manager/` are untouched — the new schema lives only in `persistence/knowledge_schema.py`), no Context Manager resolver, no APIs, no background jobs, no CLI, no Stage C functionality, and no HNSW index (see above).
- `mypy --strict` (241 source files), `ruff check`, `ruff format --check` all clean. Unit suite: **520 passed, 1 pre-existing unrelated flake** (`test_anthropic_adapter.py::test_complete_classifies_real_http_error_responses`, a real-local-HTTP-server race in an untouched `llm_gateway` test — a different parametrized case failed on each of two runs under load, then passed 3/3 in isolation immediately after, the same documented flake family as prior steps). **Environment note:** Docker Desktop was unavailable again this session (three consecutive steps now), so the new integration tests above could not be executed against a real Postgres/pgvector instance; verification instead relied on `CreateTable(...).compile(dialect=postgresql.dialect())` producing the exact expected DDL for all four tables (including the `GENERATED ALWAYS AS (...) STORED` clause and the unconstrained `VECTOR` type) plus `mypy --strict`/`ruff` — re-run the full integration suite once Docker Desktop is available.

### Stage B – Retrieval: Minimal Writer for `knowledge.documents`/`knowledge.chunks` (Second Real Retrieval Increment)

- **Read `implementation_status.md`, `DOCUMENTATION_INDEX.md`, data_model.md §7, and `search_vector_search.md` before writing any code, per this step's own context-discipline requirement.** Confirmed `search_vector_search.md`'s own "Indexing Pipeline" component ("deterministic, versioned chunk_strategy_version") is the documented future owner of chunking and writing, still entirely unbuilt — this step's writer is the persistence primitive that component will eventually call, not the pipeline itself. No new architectural contradiction was found; the prior step's own recommendation (§6) named this exact increment.
- **New `ai_os_kernel.persistence.knowledge_writer` module**: `KnowledgeWriter` Protocol (`write_document(*, source_uri, content_hash, media_type, trust, chunks, project_id=None) -> DocumentRecord`) and `SqlKnowledgeWriter`, its only implementation (SQLAlchemy 2.0 Core against Postgres, ADR-0011) — the identical Protocol-plus-implementation shape every other writer in this codebase uses (`WorkflowDefinitionCatalog`/`SqlWorkflowDefinitionCatalog`, `LLMCallRecorder`/`SqlLLMCallRecorder`, `PackLifecycleRepository`/`SqlPackLifecycleRepository`). `ChunkInput` (caller-supplied: `content`, `token_count` (`> 0`), `chunk_strategy_version`, `metadata`) and `DocumentRecord`/`ChunkRecord` (read models returned after a write, mirroring `PackRecord`'s own role) are new Pydantic models. New `ai_os_kernel.persistence.knowledge_ids` (`new_document_id()` → `doc_`, `new_chunk_id()` → `chunk_`) mirrors every other component's own `ids.py` exactly (data_model.md §2's "Prefixed ULID text" convention; neither prefix is documented with an example, the same "illustrative, not exhaustive" reasoning already used for `pkt_`/`call_`/`asm_`).
- **Deliberately placed beside `knowledge_schema.py` in `persistence/`, not inside `ai_os_kernel.knowledge_manager`.** knowledge_manager.md names the Knowledge Manager as this data's eventual retrieval-facing owner, but that package is an intentionally untouched stub (this step's own approved framing: "No Knowledge Manager ... integration yet") — writing into it would itself be a form of "Knowledge Manager integration." This mirrors the identical precedent already set by `workflow_engine.definition_catalog` (registers into `catalog.workflow_definitions` without being a Capability Manager) and `llm_gateway.call_recorder` (writes `evaluation.llm_calls` without being an Observability platform): a bare persistence writer, homed beside its schema, with no owning domain component built yet to claim it.
- **Accepts already-chunked input; computes nothing.** `content_hash` and every chunk's `content`/`token_count`/`chunk_strategy_version` are supplied by the caller — hashing a fetched resource or splitting it into chunks is Indexing Pipeline territory (still unbuilt), excluded by this step's own "no ingestion pipeline" fence. `ordinal` is the one field this writer *does* derive rather than accept: `chunks: Sequence[ChunkInput]` is already an ordered sequence (the caller's own chunking fixed the order), so `enumerate()` supplies `ordinal` directly — the least-invented reading, and one that trivially satisfies `uq_chunks_document_id_ordinal` within a single write.
- **One transaction spans both tables** (`documents` then `chunks`, both inside one `engine.begin()`), mirroring every other snapshot-plus-children writer in this codebase (`workflow_instances`+`workflow_events`, `catalog.packs`+`catalog.pack_state_transitions`): a document is never observable with zero chunks, and chunks are never observable without their parent row. An empty `chunks` sequence is rejected before the transaction opens — `KnowledgeWriteError("chunks must not be empty: ...")` — alongside blank-field checks (`source_uri`/`content_hash`/`media_type`), all raised before any database access, the identical "clear message before a bare constraint-violation stack trace" discipline `SqlLLMCallRecorder` already established. A real check-constraint violation (an invalid `trust` value) still surfaces as `KnowledgeWriteError`, wrapping the underlying `sa.exc.IntegrityError`.
- **`document_id`/`chunk_id` are freshly generated on every call — not an idempotent upsert.** Unlike `catalog.workflow_definitions` (a caller-supplied natural key, `(definition_id, version)`, upserted with `ON CONFLICT DO NOTHING`), a document being ingested has no natural stable identity of its own to key on — the identical "the writer mints a fresh identity for what it creates" reasoning `SqlWorkflowInstanceRepository.create()` already applies to `workflow_id`. Two calls with byte-identical content therefore create two independent documents; deduplicating by `content_hash` is explicitly left as a policy decision for whichever future Indexing Pipeline step calls this writer, not decided here.
- **No `.returning()` on either insert.** Every column value is already fully known before the `INSERT` runs (no server-computed value exists here except `chunks.content_tsv`, a generated column deliberately excluded from `ChunkRecord`) — `DocumentRecord`/`ChunkRecord` are constructed directly from the same values just written, the identical choice `SqlWorkflowDefinitionCatalog`/`SqlLLMCallRecorder` already made. No reader, update, delete, or search method exists — verification uses a direct `SELECT` against the real tables, the same pattern `test_definition_catalog.py` already established.
- **New integration tests only** (`tests/integration/persistence/test_knowledge_writer.py`, ADR-0015 — no mocking the database, the identical `PostgresContainer("pgvector/pgvector:pg16", ...)` module-scoped fixture already used by `test_definition_catalog.py`/`test_call_recorder.py`/`test_migrations.py`): 10 tests — the documented columns are written correctly; ids carry the correct `doc_`/`chunk_` prefixes and chunks reference the right parent; `content_tsv` genuinely generates *through this write path* (not just through a raw `INSERT` — extends `test_migrations.py`'s own proof of the column itself to this writer's own executemany-style insert); `project_id` genuinely defaults to `NULL` when omitted; two calls with identical content produce two independent documents; an empty chunk sequence and each blank required field are rejected with a clear `KnowledgeWriteError`; an invalid `trust` value's check-constraint violation is wrapped, not raised bare.
- **Still deliberately narrow, exactly per this step's approved scope**: no chunking algorithm, no content hashing, no embedding generation, no `knowledge.embeddings` rows, no keyword/vector/hybrid search, no ingestion pipeline, no Knowledge Manager/Memory Manager integration, no Context Manager resolver, no API route, no background job. `kernel/bootstrap.py` is untouched — no consumer exists yet to wire this writer into; doing so would be dead composition-root code, not a real behaviour change, deferred to whichever future step adds a real caller.
- `mypy --strict` (244 source files), `ruff check`, `ruff format --check` all clean. Unit suite: **521 passed**, zero failures (the previous step's own `test_anthropic_adapter.py` real-local-HTTP-server flake did not reproduce this run — consistent with it being a timing race, not a regression). **Environment note:** Docker Desktop was unavailable again this session (a fourth consecutive step), so the 10 new integration tests above have never executed against a real Postgres/pgvector instance; verification instead relied on compiling the writer's own `INSERT` statements against the PostgreSQL dialect (confirming `chunks.content_tsv` is correctly excluded from the compiled column list for the exact executemany-style call the writer issues, so Postgres will populate it rather than reject the insert) and directly exercising the writer's pure-Python validation and `ordinal`-derivation logic against a stub engine — re-run the full integration suite once Docker Desktop is available.

### Stage B – Retrieval: Minimal Keyword Search Reader over `knowledge.chunks.content_tsv` (Third Real Retrieval Increment)

- **Read `implementation_status.md`, `DOCUMENTATION_INDEX.md`, data_model.md §7, and `search_vector_search.md` before writing any code, per this step's own context-discipline requirement.** Confirmed search_vector_search.md's own "Keyword Search: Postgres FTS: tsvector + GIN" line as the exact documented component this step makes real, distinct from the Hybrid Ranker/Metadata Filter/Access Control components that sit in front of it in the full design and remain untouched. No new architectural contradiction was found; the prior step's own recommendation (§6) named this exact increment.
- **New `ai_os_kernel.persistence.knowledge_keyword_search` module**: `KeywordSearcher` Protocol (`search(*, query: str, limit: int = 10) -> list[ChunkSearchResult]`) and `SqlKeywordSearcher`, its only implementation — the identical Protocol-plus-implementation shape every writer/reader in this codebase already uses. `ChunkSearchResult` (`chunk_id`, `document_id`, `content`, `rank`) is a new, frozen Pydantic read model — exactly the four fields this step's own approved framing named, no more.
- **`plainto_tsquery`, not `websearch_to_tsquery` or `to_tsquery` — a reasoned choice, not the only option.** `plainto_tsquery` treats the whole input as plain text and ANDs every recognised lexeme together, exposing no query syntax (no quoted phrases, no exclusions, no boolean operators) — the simplest, safest reading of "accepts a plain-text query string." `websearch_to_tsquery`'s richer syntax and `to_tsquery`'s raw boolean operators are both real Postgres capabilities, deliberately deferred rather than overlooked.
- **The query is parsed with the identical `'english'` configuration `content_tsv` was generated with (`to_tsvector('english', content)`) — not a second, independent choice.** A query parsed under a different configuration would silently stop matching rows it should, since Postgres's `@@` operator compares stemmed lexemes, not raw text. Not made configurable this step, for the same reason the generated column's own configuration is not: doing so would need a per-chunk or per-query configuration column data_model.md §7 does not document.
- **Ranking is Postgres's own `ts_rank` against the matched query, descending, with `chunk_id` (a sortable ULID) as a deterministic tiebreak — ADR-0022's reproducibility requirement.** Two chunks scoring identically under `ts_rank` would otherwise have no guaranteed relative order across repeated identical queries. No custom scoring, weighting, or multi-signal ranking exists — that remains the still-unbuilt Hybrid Ranker's job.
- **A blank query, or a non-positive `limit`, is rejected before any query runs** (`KeywordSearchError`) — the identical "clear error before a query that could only ever be useless" discipline `SqlLLMCallRecorder`'s own blank-field checks already established. `limit` defaults to a named `_DEFAULT_LIMIT = 10` constant rather than being unbounded or a magic number inline at each call site, overridable per call.
- **Deliberately placed beside `knowledge_writer.py`/`knowledge_schema.py` in `persistence/`, not inside `knowledge_manager` or a new "retrieval" package.** search_vector_search.md's Hybrid Ranker/Metadata Filter/Access Control/Retrieval Service components remain entirely unbuilt — this is a bare persistence-layer reader, the identical "own module, no owning domain component built yet" reasoning already applied to the writer, mirroring `SqlPromptCatalog`'s own thin-reader shape. No metadata/`project_id`/`trust` filtering, no access control, no ranking beyond `ts_rank` — explicitly out of scope.
- **No writer, update, delete, HTTP route, or Context Manager wiring — "prove the reader in isolation," per this step's own scope.** `kernel/bootstrap.py` is untouched, for the identical "no consumer exists yet to wire this into" reasoning already applied to the writer step.
- **New integration tests only** (`tests/integration/persistence/test_knowledge_keyword_search.py`, ADR-0015 — no mocking the database, the identical `PostgresContainer("pgvector/pgvector:pg16", ...)` module-scoped fixture already used throughout `tests/integration/persistence/`): 10 tests, seeding real rows through the previous step's own `SqlKnowledgeWriter` rather than hand-written SQL (proving the two increments compose end to end) — a matching chunk is found and returns the documented fields; a chunk mentioning a term more often ranks above one mentioning it once; non-matching chunks are excluded entirely; an explicit `limit` and the documented default `limit` are both respected; the plural query "documents" matches singular "document" content via English stemming, proving `content_tsv`'s own generation and this reader's query parsing genuinely agree on the `'english'` configuration; two chunks tied on rank are ordered identically and deterministically across repeated calls; a blank query and each non-positive `limit` are rejected with a clear `KeywordSearchError`.
- **Still deliberately narrow, exactly per this step's approved scope**: no vector search, no hybrid search, no RRF fusion, no `knowledge.embeddings` involvement of any kind, no Knowledge Manager/Memory Manager component or integration, no HTTP route, no Context Manager resolver, no Workflow Engine wiring, no new index or schema change.
- `mypy --strict` (246 source files), `ruff check`, `ruff format --check` all clean. Unit suite: **521 passed**, zero failures. **Environment note:** Docker Desktop was unavailable again this session (a fifth consecutive step), so the 10 new integration tests above have never executed against a real Postgres/pgvector instance; verification instead relied on compiling the reader's exact `SELECT ... WHERE content_tsv @@ plainto_tsquery(...) ORDER BY ts_rank(...) DESC, chunk_id ASC LIMIT ...` statement against the PostgreSQL dialect, confirming it renders valid SQL with the expected bind parameters (`'english'`, the query text, the limit) — re-run the full integration suite (now covering the schema, the writer, and this reader together) once Docker Desktop is available.
