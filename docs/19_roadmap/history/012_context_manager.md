### Stage B – Context Manager: First Real Slice (Request Flow + One Real Resolver)

- **Architecture review performed first, per this step's own approved framing.** Read context_manager.md, workflow_architecture.md, kernel_architecture.md, agent_architecture.md, and prompt_engine.md in full before writing code; confirmed the Context Manager's documented position in the request lifecycle (workflow_architecture.md's High-Level Architecture: "Context Manager -> assembled context, Agent or Tool -> structured result", per declared step; agent_architecture.md's Invocation Lifecycle step 1: "Workflow Engine assembles context via the Context Manager") and its documented interactions (Workflow State, Knowledge Manager, Memory Manager, AI Context Packs, Runtime Configuration, User-provided inputs — context_manager.md §3).
- **Discovered, before writing any code, that the real production path had no source of prompt template variables at all.** `AgentStepExecutor._invocation_inputs()` only ever set `promptId`/`promptVersion`/`modelAlias`; `WorkflowStep` has no `variables` field; `WorkflowInstanceService.advance()` called `step_executor.execute(next_step)` without the `WorkflowInstance` in scope for the executor. So every prompt rendered through the real Workflow Engine path (as opposed to a test calling `PromptedAgent.execute()` directly with a hand-built `inputs` dict) rendered with **zero** variables — only a template needing none could ever succeed for real. This made the Context Manager's first slice not merely an architectural nicety but the fix for a genuine, previously undocumented gap in the production path.
- **New `ai_os_kernel.context_manager` package** — `models.py` (`ContextRequest`, `AssembledContext`, `ContextItem`, `SourceRef`, `SourceType` — a deliberately reduced slice of context_manager.md §5/§6's full contract, the identical "reduced slice" shape `TraceContext` already established: `required_context_types`/`token_budget`/experiment-or-run identifiers are absent from `ContextRequest` because nothing declares or enforces them yet, and `index_generation` is absent from `AssembledContext` because no retrieval index exists to pin — see that module's own docstring for the full reasoning), `ids.py` (`new_assembly_id()`, the identical prefixed-ULID convention every other subsystem uses), `resolvers.py` (`ContextSourceResolver` Protocol + `WorkflowStateResolver` — the one real resolver, reading a workflow instance's own declared `inputs`; also a shared `estimate_tokens()` length heuristic, explicitly distinguished from llm_gateway.md §12's real, provider-endpoint-only token counting — context assembly happens before a model alias is even chosen, so no provider `count_tokens()` call is reachable here even in principle), and `manager.py` (`ContextManager` Protocol + `DefaultContextManager` — queries every configured resolver in order and concatenates their items; no filtering, ranking, or truncation, since nothing yet needs it with one resolver and no declared budget).
- **Exactly one real resolver, per this step's own approved framing ("the minimum number of real context resolvers required to establish the complete end-to-end flow").** Of context_manager.md §3's six documented sources, only Workflow State has a real, already-built implementation to read from (`WorkflowInstanceRepository`); Knowledge Manager, Memory Manager, and AI Context Packs are entirely unbuilt Kernel components, and a Runtime Configuration resolver — while technically buildable, since the Configuration Manager is real — is deliberately deferred too, since one real resolver already proves the end-to-end request flow this step exists to establish. "User-provided inputs" (§3's sixth source) is not built as a second, separate resolver: in this codebase there is exactly one place user-provided data lives (`WorkflowInstance.inputs`), so `WorkflowStateResolver` is read as honestly covering both documented sources, not artificially split into two resolvers over one data source.
- **`StepExecutor.execute()` gained one new, additive, defaulted-`None` keyword: `workflow_id`.** `WorkflowStep` (shared across every instance of a workflow) has no instance identity of its own, and `WorkflowInstance` is the one place this Kernel currently has both a resolvable instance identity and a real "Workflow State" to read — so the Context Manager's own `ContextRequest.workflow_id` needed a source, and there was none in the existing `StepExecutor.execute(step)` call chain. Every implementation (`NoOpStepExecutor`, `AgentStepExecutor`, `ToolStepExecutor`, `DispatchingStepExecutor`) updated to accept it; only `AgentStepExecutor` uses it (agent_architecture.md documents context assembly for Agents, not Tools — a Tool is "a trivial in-process unit of work" per workflow_architecture.md's own Step Contract, with no prompt or LLM involvement to supply context to). `WorkflowInstanceService.advance()` is the one real call site that now supplies it (`self._step_executor.execute(next_step, workflow_id=workflow_id)`) — the only Workflow Engine behaviour change this step makes, and it is purely additive: every existing test/caller that never supplies `workflow_id` gets byte-for-byte the same `inputs` dict as before.
- **`AgentStepExecutor` gained one new, optional, defaulted-`None` constructor parameter: `context_manager`.** When both `context_manager` and the `workflow_id` passed to `execute()` are present, it asks the Context Manager to assemble context (`ContextRequest(workflow_id=workflow_id, step_id=step.id, agent_id=step.agent_id)`) and adds the result to `inputs["context"]` as a structured `AssembledContext` object — passed through, not flattened, since flattening into named prompt-template variables is judged to be the *consuming agent's* own "Context Consumer" responsibility (agent_architecture.md), not the executor's. Either piece missing (`context_manager=None`, or `workflow_id=None`) leaves `inputs` exactly as it was before this step — "cannot be checked, not an error," the identical shape already established for a missing `workflow_id` on `TraceContext`.
- **`PromptedAgent` is now agent_architecture.md's first real "Context Consumer."** Reads `inputs.get("context")` and, when present with at least one item, flattens every item's `content` (newline-joined, in resolver order) into exactly one prompt template variable: `context`. A deliberately minimal mapping, not a general one — with only one real resolver and no ranking, there is no basis yet for mapping different items to different named variables. An explicit `variables["context"]` supplied by a caller still wins (`setdefault`, not overwrite) — this only fills a gap. No `"context"` key in `inputs` at all (every caller before this step) is a complete no-op.
- **`kernel/bootstrap.py`** now constructs one real `DefaultContextManager` (with the one real `WorkflowStateResolver`) in `_lifespan`, attached to `app.state.context_manager` — the same "reachable independently of any one closure" reasoning `app.state.workflow_instance_repository` already established — and threads it into `AgentStepExecutor` inside `_build_workflow_trigger` (which now takes `context_manager` as a parameter rather than constructing its own). Unlike every optional Gateway parameter added in prior steps, there is no "configured or absent" branch here: the one real resolver this step builds has no external configuration to be missing, so a real `ContextManager` is always constructed and always passed — this is genuinely new, observable behaviour for the demo workflow (its one agent step now receives a real `AssembledContext`, and, when the workflow's own `inputs` are non-empty, that context is genuinely visible in the rendered prompt), not inert wiring.
- **No change to `WorkflowDefinition`/`WorkflowStep`'s own schema, the Workflow Engine's state machine, persistence, or leasing.** The only Workflow Engine files touched are `step_executor.py` (the additive `workflow_id` keyword) and `service.py` (the one-line call-site change to supply it) — both narrow, additive wiring changes, not a redesign of either module, per this step's own constraint.
- **A real, otherwise-unavoidable import cycle, resolved with a standard `TYPE_CHECKING` guard, not a design change.** `ai_os_kernel.workflow_engine`'s own `__init__.py` eagerly imports `step_executor` (which now imports `ai_os_kernel.context_manager` for the `ContextManager` Protocol); `context_manager.resolvers` needs `WorkflowInstanceRepository` only as a static type. The underlying dependency is real and bidirectional by design — the Context Manager reads Workflow State, and the Workflow Engine calls the Context Manager — so the fix is deferring the type-only import to `TYPE_CHECKING`, not restructuring either package.
- **Two documentation items surfaced and flagged, not silently resolved:** (1) context_manager.md §6 does not classify whether workflow/user-provided input is `trusted` or `untrusted` — only "repository content, ingested documents, tool output, and web content" are given as `untrusted` examples; `WorkflowStateResolver` classifies it `untrusted` as a reasoned default (it originates outside the Kernel's own trusted subsystems), not a documented certainty. (2) context_manager.md §9 requires every context assembly to be recorded "for audit and replay" (a "Context Audit Logger"), but data_model.md defines no persistence schema for a context assembly at all — `AssembledContext` is therefore purely in-memory this step, with no writer, since inventing an undocumented table would itself be the "placeholder architecture" this step must avoid.
- **New tests**: `tests/unit/kernel/context_manager/test_models.py` (9), `test_resolvers.py` (7), `test_manager.py` (8) — the package's own reduced contract, the one real resolver (including an ADR-0022 determinism check: identical inputs in a different key order serialise identically), and the assembler (including a same-request-twice determinism check). `tests/unit/kernel/workflow_engine/test_agent_step_executor.py` (+5), `test_dispatching_step_executor.py` (+2), `test_service.py` (+1): the new `workflow_id` keyword is forwarded correctly at every layer and defaults to a no-op when absent; `AgentStepExecutor` only assembles context when both `context_manager` and `workflow_id` are present. `tests/unit/kernel/workflow_engine/test_prompted_agent.py` (+4): context flattening into the `context` variable, explicit-variable precedence, and no-op behaviour for empty/missing context. `tests/unit/kernel/test_bootstrap.py`, `tests/integration/test_bootstrap_workflow_trigger.py` (+1 new real-database test), `tests/integration/test_workflows_route.py`: real composition-root wiring, including one genuinely new real-database integration test proving a workflow's own `inputs`, written to a real Postgres row, are read back by the real `WorkflowStateResolver` and appear, verbatim, in the agent's final rendered/echoed output — the Context Manager's own end-to-end proof, not a stub.
- **Still deliberately narrow, exactly per this step's approved framing**: no Knowledge Manager, Memory Manager, or AI Context Pack resolvers (none of those Kernel components exist); no Runtime Configuration resolver; no semantic retrieval; no ranking beyond a constant `relevance_score`; no compression or context optimization; no Size & Token Budget Enforcer (`items_excluded_count` is always honestly `0`); no `required_context_types` (no Step Contract field to drive it); no `index_generation` (no retrieval index to pin); no Context Audit Logger persistence writer (no schema exists, see above).
- `mypy --strict` (237 source files), `ruff check`, `ruff format --check` all clean. Full suite: **652 tests passing, 6 skipped** (six opt-in live tests, skipped by design without credentials; no flaky tests observed this run, including the previously-observed `test_local_adapter.py` case, which passed cleanly). Combined unit+integration coverage: **97.63%** (`context_manager/__init__.py`/`ids.py`/`manager.py`/`models.py`/`resolvers.py`: 100%; `workflow_engine/prompted_agent.py`: 100%; `workflow_engine/service.py`: 100%; `workflow_engine/step_executor.py`: 96% — the two uncovered lines are pre-existing defensive "should never happen" branches unreachable given `WorkflowStep`'s own validators, unrelated to this step's changes).

### Stage B – Context Manager: Size & Token Budget Enforcer (implementation_roadmap.md §3's Own Stage B Deliverable)

- **Architecture review performed first, per this step's own approved framing — re-evaluated from scratch, not defaulting to the previously-recommended Runtime Configuration Resolver.** Found a stronger, more specific signal than context_manager.md's own source list: implementation_roadmap.md §3 names the Stage B deliverable for this exact component as *"Context Manager with deterministic assembly, budget enforcement, and trust tagging."* Deterministic assembly (verified by an ADR-0022 test in the prior step) and trust tagging (every `ContextItem.trust` populated) were already done; budget enforcement was the one named, in-stage, unmet piece — a smaller, more explicitly-documented target than Runtime Configuration (named nowhere in the roadmap), and unblocked, unlike Security Context propagation (explicitly a Stage C deliverable — "Security Manager enforcing monotonic permission narrowing," and §5's own "What Must Not Be Deferred" table: "Monotonic permission narrowing | Stage C" — not yet due) or Knowledge/Memory retrieval (blocked on an entirely unbuilt Platform Service, ADR-0013, plus the LLM Gateway's unbuilt `embed()`). Full review delivered and approved before any code.
- **`ContextRequest` gains one new field: `token_budget: int | None = None`, rejecting `<= 0` (`pydantic.Field(gt=0)`).** context_manager.md §5 documents `token_budget` as something a request *may* carry, not something every request must declare — an optional field is therefore the faithful reading, not a compromise. `required_context_types` and experiment/run identifiers remain absent as fields, unchanged from the prior step's own reasoning.
- **`DefaultContextManager` gains one new, optional, defaulted-`None` constructor parameter: `default_token_budget`.** Mirrors `PerScopeBudgetEnforcer`'s own shape — a ceiling the *assembler* is configured with, applied only when a request's own `token_budget` is absent. This avoids forcing every existing caller to start declaring a per-request budget, the identical "assembler-level default, request-level override" reasoning already applied to the LLM Gateway's own budget ceilings, adapted to a component where the request contract, not the constructor, is the documented home for the value.
- **The admission algorithm: rank by `relevance_score` (descending, stable sort), greedily admit whatever still fits, return survivors in original resolver order.** A stable sort means items tied on score (every item today, since only one resolver with a constant score exists) preserve their original resolver order rather than being reordered or arbitrarily chosen among — ADR-0022's "context assembly ... is deterministic given the same inputs," and this step's own explicit "preserve stable ordering" requirement. Admission does not stop at the first item that doesn't fit: a smaller, lower-ranked item can still fill room a larger, higher-ranked one left unused (first-fit continues past a skip) — proven by a dedicated test. The final `items` list is reconstructed in the *original* resolver order among only the admitted items — truncation decides *which* items survive, never reorders the ones that do; rank governs admission, not final presentation order, which is what "preserve stable ordering" was read to require alongside ADR-0022's determinism obligation.
- **No budget at all (`ContextRequest.token_budget=None` and `DefaultContextManager`'s own `default_token_budget=None`, every caller before this step) is unaffected — the same "disabled means `None`, zero behaviour change" shape every other Kernel policy limit in this codebase already uses** (`budget_enforcer`/`workflow_budget_enforcer` on `DispatchingLLMGateway`, `circuit_breaker`, `backoff_policy`). Every existing test/caller from the prior Context Manager step passes unmodified.
- **This is genuinely budget *enforcement*, not the still-unbuilt Context Filter/Ranker — a distinction recorded explicitly, not blurred.** context_manager.md §4 names these as two separate internal components. `relevance_score` is reused here only as a stable truncation tie-break ("*which* items survive when there isn't room for all of them"), not as a first-class ranking capability with its own logic, weighting, or multi-signal scoring — that remains unbuilt, deliberately, until a second resolver gives `relevance_score` genuine variance to rank by.
- **`kernel/bootstrap.py`** adds one new named constant, `_CONTEXT_TOKEN_BUDGET = 8000` — the identical "named, documented, placeholder safety limit, not a tuned production value" carve-out every other Kernel policy constant in this file already uses — passed to `DefaultContextManager(..., default_token_budget=_CONTEXT_TOKEN_BUDGET)`. No Workflow Engine, `AgentStepExecutor`, or `PromptedAgent` file changed — the entire increment lives inside `ai_os_kernel.context_manager` and its one composition-root call site.
- **New tests**: `tests/unit/kernel/context_manager/test_models.py` (+4): `token_budget` defaults to `None`, accepts a positive value, rejects zero and negative values. `test_manager.py` (+11): no budget includes everything unfiltered; a request-level budget excludes what doesn't fit; the assembler's own default applies when the request specifies none; a request-level budget overrides the default; higher-relevance items are admitted before lower-relevance ones regardless of input position; survivors are returned in original resolver order, not rank order; tied scores preserve original order when truncating; a smaller lower-ranked item fills room a skipped larger item left unused; an item larger than the entire budget is excluded outright, never partially included; budget enforcement is deterministic across repeated calls on the same request. `tests/unit/kernel/test_bootstrap.py` (+1): the real composition root wires a real `DefaultContextManager` with a real, positive `default_token_budget`. `tests/integration/test_bootstrap_workflow_trigger.py` (+1 new real-database test): a real oversized workflow input is genuinely excluded against a real 1-token budget, and the workflow step genuinely fails (a required-but-now-absent `context` prompt variable) rather than silently rendering without it — the Size & Token Budget Enforcer's own end-to-end proof, not a stub.
- **Still deliberately narrow, exactly per this step's approved scope**: no additional Context Resolvers (Runtime Configuration, Knowledge, Memory, AI Context Packs); no semantic ranking; no retrieval; no compression; no Context Audit Logger persistence (still no data_model.md schema); no `required_context_types` or experiment/run identifiers on `ContextRequest`; no `index_generation` on `AssembledContext`.
- `mypy --strict` (237 source files), `ruff check`, `ruff format --check` all clean.
