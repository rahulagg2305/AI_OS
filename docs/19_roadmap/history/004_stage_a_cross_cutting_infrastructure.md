### Stage A – CI Pipeline Aligned With the Current Codebase
- **`.github/workflows/ci.yml`**: every stage now either runs for real against what the repository actually contains, or is gated to a clean no-op via `if: hashFiles(...) != ''` on the specific not-yet-existing path — never silently deleted, since deleting a stage would drop the pipeline shape ADR-0015 and test_strategy.md §6 document as the target. Each gate is commented with what it's waiting for, so the stage starts running for real the moment its prerequisite lands, with no further CI change required. `contract`'s two steps (`tests/contract`, `scripts/check_import_boundaries.py`), `security`'s one step (`tests/security`), `integration`'s one step (`tests/workflow`), `build` (`Dockerfile`), and `frontend` (`dashboard/package.json`, combined with its original trigger condition) are all gated this way — nothing in this list exists yet.
- **`types`**: the `mypy --strict` invocation now targets exactly `kernel/src kernel/alembic tests` — mirroring `[tool.mypy] files` in `pyproject.toml` and every `mypy --strict` run performed by hand throughout this whole implementation log. It previously named `platform_sdk platform_services capability_packs`; `platform_services` doesn't exist as a directory at all (mypy would hard-fail just resolving the path), and `platform_sdk`/`capability_packs` currently hold only schema/manifest/YAML files, no Python.
- **`integration`**: switched fully to the `testcontainers` approach every integration test already uses — the GitHub Actions `services: postgres`/`services: redis` containers and their hardcoded `AIOS_DATABASE_URL`/`AIOS_REDIS_URL`/`AIOS_SECRET_BACKEND` env vars are removed; each test module provisions and tears down its own ephemeral Postgres and sets the URL itself, exactly as `tests/integration/persistence/test_migrations.py` already does. The standalone "Alembic migrations up/down/up" step is removed too — it had nothing to run against once the shared service was removed, and `test_migrations.py`'s own round-trip test already proves the same thing against its own container.
- **Coverage (NFR-060, "≥ 90% kernel test coverage") moved from the `unit` job to `integration`, and now measures `tests/unit` + `tests/integration` together** — not `tests/unit` alone, which was never structurally capable of reaching 90%: ADR-0015 deliberately keeps real SQL persistence code (`SqlWorkflowInstanceRepository`, `SqlWorkflowLeaseRepository`, ...) exercised only by integration tests against a real Postgres, never by unit-test mocks. Measured against unit tests alone, coverage was **81.28%** (verified locally); measured against unit + integration together it is **95.61%**, comfortably clearing the 90% floor — confirming the *combined* suite, not either layer alone, is what "Kernel test coverage" (NFR-060) means. The `--cov`/`--cov-branch` flags now take no explicit `--cov=<package>` argument, relying on the single already-declared `[tool.coverage.run] source = ["ai_os_kernel"]` in `pyproject.toml` instead of a second, driftable list of package names in the workflow file (the previous `--cov=kernel --cov=platform_sdk --cov=platform_services` referenced one nonexistent and two Python-free directories).
- **`security`'s "Dependency vulnerabilities" step was not actually runnable at all before this change**: `pip-audit` was never declared as a dependency anywhere in the workspace (verified locally: `command not found`). Added `pip-audit>=2.7,<3.0` to the root `pyproject.toml`'s dev dependency group (`uv.lock` regenerated) — completing tooling ADR-0015/test_strategy.md §2 already named as the chosen tool, not introducing a new one. Running it against the live environment then failed for an unrelated reason: `pip-audit --strict` cannot look up the unpublished local `ai-os-kernel` workspace package on PyPI and hard-fails on that lookup under `--strict`. Fixed by auditing an exported requirements list instead (`uv export --format requirements-txt --no-emit-workspace --no-dev`), which excludes both the local package (`--no-emit-workspace`) and dev-only tooling (`--no-dev` — pytest, mypy, ruff, ... never ship in a deployed AI_OS instance, so a *runtime* vulnerability gate is the wrong place to fail on one of them). Verified locally: the runtime-only dependency set has zero known vulnerabilities; the full environment (including dev tools) currently has one, in `pytest` itself, deliberately out of scope for this gate for the reason just stated.
- **No changes to any workflow-engine source, test, or business logic.** This step is CI configuration and dev-tooling metadata only (`.github/workflows/ci.yml`, `pyproject.toml`'s dev dependency group, `uv.lock`), exactly as approved.
- Verified locally, command-for-command matching what CI now runs: `ruff check .`, `ruff format --check .`, `mypy --strict kernel/src kernel/alembic tests`, `pytest tests/unit -v`, `pytest tests/unit tests/integration -v --cov --cov-branch --cov-report=term-missing --cov-fail-under=90`, `uv sync --frozen --all-packages`, and the exported-requirements `pip-audit --strict` invocation — all pass. `gitleaks/gitleaks-action` is unchanged and cannot be exercised locally the same way; nothing about this step's changes affects it.
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite unchanged by this step: **143 tests passing** (95 unit + 48 integration).

### Stage A – Minimal Secrets Resolution (ADR-0024)
- **New `kernel/src/ai_os_kernel/secrets_manager/` subpackage** (no such module existed before this step — confirmed by scanning the repo first). Named to match the sibling `_manager` components already present (`configuration_manager`, `security_manager`, `capability_manager`, ...); no dedicated `docs/03_architecture/kernel/secrets_manager.md` exists, so ADR-0024 and `docs/09_security/secrets_management.md` are the sole source of truth this step is grounded in.
- **`reference.py`**: `parse_secret_reference()` parses the ADR-0024 URI format `secret://<provider>/<name>[#<version>]` (`SecretReference`: `provider`, `name`, `version`) — backend-agnostic and shared by every future provider, not `EnvSecretProvider`-specific. `<name>` accepts Vault-style nested paths (`llm/anthropic-api-key`), exactly the example ADR-0024 itself gives.
- **`value.py`**: `SecretValue` — `__str__`/`__repr__` return `"***"` (ADR-0024 rule 2); the raw value requires an explicit `.reveal()` call. A plain class with `__slots__`, not a Pydantic model — there is nothing to validate, only a value to guard.
- **`provider.py`**: `SecretProvider` — a `Protocol` with one method, `async def resolve(self, reference: str) -> SecretValue`. `async` even though the only implementation today does no real I/O, matching every other backend seam in this codebase (`WorkflowLeaseRepository`, `WorkflowInstanceRepository`, ...) and because every *other* backend ADR-0024 names (Vault, cloud secret managers) will need it.
- **`env_provider.py`**: `EnvSecretProvider` — the `env` backend, explicitly scoped by ADR-0024 to local development only. Maps a reference's `<name>` onto an environment variable via a fixed `AIOS_SECRET_` prefix (e.g. `llm/anthropic-api-key` → `AIOS_SECRET_LLM_ANTHROPIC_API_KEY`) — namespaced so this backend can only ever read a variable clearly meant for it, never collide with an unrelated one. Rejects a reference naming a different provider, rejects a reference requesting a `#version` (a plain env var has no versions to serve), and raises clearly on a missing variable. The environment mapping is injectable (`env: Mapping[str, str] | None = None`, defaulting to `os.environ`) — ADR-0004, and it means unit tests never mutate real process state.
- **`errors.py`**: `SecretResolutionError` — one exception class covering both "the reference itself is malformed" and "a provider could not resolve it," mirroring `ConfigurationError`'s single-class-per-concern style.
- **Deliberately not built, per approved scope:** the encrypted-file backend, Vault, cloud secret managers, the Access Broker (authorization + audit per access), TTL caching with rotation invalidation, the prompt-assembly scan rejecting a resolved value from reaching a model, and wiring into any consumer (Configuration Manager, LLM Gateway, Git Integration Service) — none of those consumers exist yet either.
- 24 new unit tests (`tests/unit/kernel/secrets_manager/`): `test_reference.py` (valid nested-path/flat/versioned references parse correctly; 10 malformed variants — empty, wrong scheme, uppercase provider, trailing slash, empty version, ...) all rejected with a clear message); `test_value.py` (`.reveal()` returns the raw value; `str()`/`repr()`/f-string interpolation all return `"***"` and never contain the raw value); `test_env_provider.py` (flat and nested-path names resolve to the correct env var; a missing var, a wrong-provider reference, a versioned reference, and a malformed reference are all rejected with the expected message; a real `monkeypatch`-set process env var is read correctly when no `env` mapping is injected, proving the default path works too).
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite: **167 tests passing** (119 unit + 48 integration). Combined unit+integration coverage: **95.87%** (secrets_manager itself: 100%).

### Stage A – Real OpenTelemetry Span Instrumentation (ADR-0017)
- **New `observability/tracing.py`**: `configure_tracing()` installs a process-wide OTel `TracerProvider` (called once, from `bootstrap.build_app()`, mirroring `configure_logging()`); `get_tracer(name)` mirrors `get_logger(name)`; `bind_otel_span_context()` is a new structlog processor that adds the *active span's own* `otelTraceID`/`otelSpanID` (hex, OTel-native) to every log line emitted while a span is active — distinct from and additional to this platform's own `trace_id` field, which is unchanged.
- **Export is the OTel console exporter** (`ConsoleSpanExporter` + `SimpleSpanProcessor`), exactly as approved — not OTLP: ADR-0017's actual target needs a Collector, and none is deployed (no Compose observability profile exists yet). Swapping to OTLP later is a one-line change inside `configure_tracing()` and nowhere else, which is the literal "backend-swappable without touching application code" guarantee ADR-0017 makes — verified in spirit by how cleanly the console exporter itself drops in.
- **`middleware.py`**: `TraceIdMiddleware.dispatch()` now wraps `call_next()` in a real span (`tracer.start_as_current_span(f"{method} {path}")`) with attributes `aios.trace_id`, `http.method`, `http.target`, `http.status_code`. The existing `X-Trace-Id` header contract (an opaque, caller-supplied-or-generated token with no format requirement) is **unchanged** — it is deliberately not replaced by the OTel trace id, which has a strict 128-bit format the existing, already-tested `test_incoming_trace_id_is_honored` (`X-Trace-Id: my-custom-trace`, an arbitrary non-hex string) would violate. Both ids are recorded; they answer different questions ("what did the caller send/receive" vs. "which span is this"). An exception raised inside `call_next()` is recorded on the span and re-raised automatically by OTel's own span context manager — no extra handling needed.
- **`configure_tracing()` is idempotency-guarded**: the OpenTelemetry API only allows the global `TracerProvider` to be set once per process and otherwise just logs a warning; since every test in this repo calls `build_app()` (and therefore `configure_tracing()`) independently, an unguarded call would emit a spurious warning on every call after the first. Guarded by checking whether the current provider is already a real SDK `TracerProvider` (as opposed to OTel's default no-op proxy) before installing one.
- **New runtime dependencies**: `opentelemetry-api>=1.27,<2.0` and `opentelemetry-sdk>=1.27,<2.0` added to `kernel/pyproject.toml` (real Kernel runtime code, not dev tooling — alongside `fastapi`, `sqlalchemy`, ...); `uv.lock` regenerated. Both ship inline type hints (`py.typed`), so no separate `types-opentelemetry-*` stub packages were needed for `mypy --strict`.
- **Manually verified end to end** (not just unit-tested): built the real app via `bootstrap.build_app()` and issued a request — the console exporter printed a real span with the documented attributes and `service.name: ai-os-kernel`, and the `X-Trace-Id` response header behaved exactly as before. Separately, calling `get_logger(...).info(...)` outside vs. inside an active span showed the log line gains `otelTraceID`/`otelSpanID` only when a span is active, and those values exactly match the corresponding exported span's own `trace_id`/`span_id`.
- 7 new unit tests: `tests/unit/kernel/observability/test_tracing.py` (`get_tracer` returns a real `Tracer`; `bind_otel_span_context` adds two 32/16-char lowercase-hex fields while a span is active and leaves the event dict untouched with none active; two spans in the same trace share a `trace_id` but not a `span_id`; `configure_tracing()` is safe to call twice) and `tests/unit/kernel/observability/test_middleware.py` (a real request through `TraceIdMiddleware`, with the tracer swapped via `monkeypatch` for a locally-created `TracerProvider` + `InMemorySpanExporter` — never the process global, so fully isolated from `configure_tracing()`'s once-per-process state — produces exactly one finished span with every documented attribute correct, for both a caller-supplied and a generated `X-Trace-Id`).
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite: **174 tests passing** (126 unit + 48 integration). Combined unit+integration coverage: **95.97%** (`observability/middleware.py` and `observability/tracing.py`: 100%).

### Stage A – Real OpenTelemetry Metrics Instrumentation (ADR-0017)
- **New `observability/metrics.py`**, mirroring `tracing.py`'s shape exactly: `configure_metrics()` installs a process-wide OTel `MeterProvider` (called once, from `bootstrap.build_app()`, alongside `configure_tracing()`); `get_meter(name)` mirrors `get_tracer(name)`; `get_http_requests_counter()` returns the one `aios.http.requests` counter (unit `{request}` — the OTel convention for a dimensionless count of things — description "Number of HTTP requests handled by the Kernel API"), named per the `aios.<subsystem>.<metric>` convention `observability_stack.md` §3.1 already specifies.
- **Export is the OTel console exporter** (`ConsoleMetricExporter` via `PeriodicExportingMetricReader`), exactly as approved, for the identical "no Collector deployed yet" reason spans use one — swapping to OTLP later is a one-line change inside `configure_metrics()` and nowhere else.
- **`middleware.py`**: `TraceIdMiddleware.dispatch()` now increments `get_http_requests_counter()` by 1, with attributes `http.method` and `http.status_code`, once a response actually exists (after `call_next()` returns) — a request whose handling raises before producing a response is not counted against any status, matching how the span's own attribute-setting is already guarded the same way.
- **The counter is created once and cached** (a module-level singleton, lazily built on first use), not re-created per request: OTel instruments are meant to be created a single time per name and reused, unlike `get_tracer`/`get_meter`, which are cheap and idempotent to call fresh every request. `get_http_requests_counter()` calls `configure_metrics()` itself if nothing has yet, so it carries no assumption about call order relative to `bootstrap.build_app()`.
- **`configure_metrics()` is idempotency-guarded**, identically to `configure_tracing()` and for the same reason: the OpenTelemetry API only allows the global `MeterProvider` to be set once per process.
- **New test-infrastructure fixture, not application code**: `tests/conftest.py` (new file — none existed before) shuts down the OTel `MeterProvider`'s background export thread at the end of the test session. `PeriodicExportingMetricReader` runs a background thread that, left unmanaged, could attempt one more export after pytest has already closed the streams it captured, producing a spurious `ValueError: I/O operation on closed file` traceback after an otherwise fully-passing run (observed and reproduced locally on the full unit suite before adding this fixture; confirmed silent afterward). This did not affect `SimpleSpanProcessor` in the tracing step, which exports synchronously with no background thread.
- **No new runtime dependency**: metrics are already part of the `opentelemetry-sdk`/`opentelemetry-api` packages added in the tracing step; nothing new was added to `kernel/pyproject.toml`.
- **Manually verified end to end**: built the real app via `bootstrap.build_app()`, issued three requests, then called `MeterProvider.force_flush()` (bypassing the default 60-second export interval for immediate verification) — the console exporter printed `aios.http.requests` with `value: 3`, attributes `{"http.method": "GET", "http.status_code": 200}`, the documented unit and description, and `service.name: ai-os-kernel` in the shared resource.
- 6 new unit tests: `tests/unit/kernel/observability/test_metrics.py` (`get_meter` returns a real `Meter`; `get_http_requests_counter` returns a real `Counter`; two calls return the identical cached object; `configure_metrics()` is safe to call twice) and 2 new tests in `tests/unit/kernel/observability/test_middleware.py` (a real request through `TraceIdMiddleware`, with the counter swapped via `monkeypatch` for a locally-created `MeterProvider` + `InMemoryMetricReader` — never the process global — records exactly one data point with the documented attributes and value 1; two requests accumulate to value 2 on the same data point).
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite: **180 tests passing** (132 unit + 48 integration). Combined unit+integration coverage: **96.07%** (`observability/metrics.py`, `middleware.py`, `tracing.py`: all 100%).
