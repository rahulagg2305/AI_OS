# AI_OS Implementation History — First Real LLM Integration and PromptedAgent

**Milestone:** The minimal Capability Manager slice (pack activation gating for registry resolution), the `AnthropicAdapter`, the first end-to-end Prompt→LLM→`llm_calls` path, `PromptedAgent` + `AgentStepExecutor`, `PromptedAgent` wired into bootstrap, and the Workflow Engine's step-execution wired into bootstrap.

Split out of the original single `implementation_status.md` on 2026-07-28 — content preserved verbatim, in original order. See `docs/19_roadmap/history/INDEX.md`.

### Stage B – Capability Manager Minimal Slice: Pack Activation Gating for Registry Resolution
- **New `kernel/src/ai_os_kernel/workflow_engine/pack_state.py`**: `PackState`, a `StrEnum` mirroring capability_manager.md §4's canonical eight-value pack lifecycle (`discovered` … `uninstalled`) — the identical role `TrustTier` (`workflow_engine/tool.py`) already plays for `catalog.tools.trust_tier`'s own `CHECK` constraint, and for the identical reason lives in `workflow_engine`, not `persistence/catalog_schema.py` (the persistence layer never imports from `workflow_engine`; a migration's own duplicated literal list stays a frozen historical record regardless of whether this enum's membership ever changes). Only `ACTIVATED` is consumed by anything yet — the other seven exist so the enum is a complete, honest mirror of the documented lifecycle, not a partial one reverse-engineered from this step's own narrow need.
- **`SqlAgentRegistry.resolve_agent`/`SqlToolRegistry.resolve_tool` (`workflow_engine/registry.py`) now gate on pack activation before loading anything.** Each query changed from a single-table lookup to one `LEFT JOIN` against `catalog.packs` on `pack_id` (still one round trip, not a second query) — a new shared `_require_activated_pack()` helper raises the new `PackNotActivatedError` (`workflow_engine/errors.py`) when the join found no matching pack row (`state IS NULL` — `pack_id` is not FK-enforced against `catalog.packs`, so a genuinely unregistered pack is a real, reachable case) or when the matched row's `state` is anything other than `activated`, with a distinct message for each. This check runs *before* `EntrypointLoader.load()` is ever called — an otherwise-perfectly-valid, otherwise-perfectly-loadable entrypoint is still refused while its owning pack is not `activated`, the exact "practical meaning" this step was scoped around.
- **`InMemoryAgentRegistry`/`InMemoryToolRegistry` are unchanged** — a caller-supplied mapping entry has no owning pack row to check against; the gate is specific to the two catalog-backed implementations, consistent with them already being the only two that read `catalog.packs`/`catalog.agents`/`catalog.tools` at all.
- **Still deliberately not the rest of the Capability Manager**: no pack install/upgrade UI or workflow, no health monitoring, no permissions system, no sandboxing, no network/code download — a resolved agent/tool's declared pack being a real, `activated` `catalog.packs` row is the one and only additional fact checked. Nothing writes to `catalog.packs`/`catalog.pack_state_transitions` yet either; this step only reads `state`, exactly as scoped.
- **`tests/integration/workflow_engine/test_registry.py` extended** (16 tests total, real Postgres, ADR-0015): a new `_seed_pack()` helper and an autouse fixture keep a shared default pack (`se.software_engineering`) `activated` so every pre-existing test keeps exercising entrypoint loading rather than this new gate; `_seed_agent`/`_seed_tool` gained an optional `pack_id` parameter (default unchanged) so new tests can seed a distinct pack per scenario. **6 new tests** prove: an agent/tool whose pack is genuinely `activated` still resolves successfully (the required "activated pack → resolution succeeds" case, for both); an agent/tool whose pack exists but is `deactivated` raises `PackNotActivatedError` (the required "non-activated pack → resolution fails" case, for both); an agent/tool whose declared `pack_id` has no `catalog.packs` row at all raises the same error with a distinguishing message, for both.
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite: **334 tests passing** (194 unit + 140 integration). Combined unit+integration coverage: **96.58%** (`pack_state.py`: 100%; `registry.py`: 96% — only the pre-existing `SQLAlchemyError`-wrapping branches remain uncovered, unchanged from last step).

### Stage B – One Real LLM Provider Adapter: `AnthropicAdapter`
- **New `kernel/src/ai_os_kernel/llm_gateway/adapters/` package** — the CI-enforced import boundary llm_gateway.md §2 documents ("Provider SDKs may be imported only inside `kernel/llm_gateway/adapters/`"): the only place in this codebase that imports `anthropic` (added as a real dependency, `anthropic>=0.69,<1.0`, `uv.lock` regenerated). The mechanical CI check itself (`scripts/check_import_boundaries.py`) still does not exist — `.github/workflows/ci.yml`'s own "Import boundary check" step remains gated on that script's absence, unchanged by this step — so the boundary is honoured by placement today, not yet enforced by tooling.
- **`AnthropicAdapter`** (`anthropic_adapter.py`) is the first real, non-`Echo*` `LLMGateway` implementation: `complete()` resolves `request.model_alias` to a real model id, builds the `messages.create()` call from exactly the fields the already-reduced `LLMRequest` carries (no `thinking`/`effort` — the contract gives no caller a way to control them, so none is invented), and maps the real response back through `_map_response()`, a pure function unit-tested directly against genuine `anthropic.types.Message`/`Usage`/`TextBlock` objects. `EchoLLMGateway` is untouched and remains the deterministic implementation tests and local development use.
- **New `kernel/src/ai_os_kernel/llm_gateway/adapters/model_config.py`**: `load_provider_config()` reads a small, dedicated `config/llm.yaml` — a flat `aliases: {alias: model_id}` map plus per-model `pricing` (USD per million input/output tokens) — deliberately **not** the documented Router (llm_gateway.md §7's alias *chains*, fallback, provider health, experiment pinning) and deliberately not routed through `ConfigurationManager`/`PlatformConfig` (a different, larger, not-yet-approved schema decision). This is the smallest configuration-driven mechanism satisfying ADR-0002 ("never a literal model id") and computing an honest `cost_usd` for a real call, without hardcoding either in source.
- **API key access goes through the existing `SecretProvider`, not `ANTHROPIC_API_KEY` auto-detection.** `build_anthropic_adapter()` calls `secret_provider.resolve(api_key_secret_reference)` and constructs `anthropic.AsyncAnthropic(api_key=secret.reveal())` — `AnthropicAdapter` itself never imports `secrets_manager` or sees a reference string, only an already-authenticated client. Local development resolves `secret://env/llm/anthropic-api-key` via the existing `EnvSecretProvider` to `AIOS_SECRET_LLM_ANTHROPIC_API_KEY` — the exact example that provider's own docstring already used, now a real, working path (`.env.example` updated).
- **New errors** `LLMProviderError`/`LLMRefusalError` (`llm_gateway/errors.py`): every non-2xx response (`anthropic.APIStatusError`) and every network/timeout failure (`anthropic.APIConnectionError`) becomes one `LLMProviderError`, chained via `from`; a real safety decline (`stop_reason: "refusal"`) is the distinct `LLMRefusalError`, matching llm_gateway.md §5's own framing that a refusal is "a policy decision about the request, not a fault." A `stop_reason` this reduced contract cannot represent (`tool_use`, `pause_turn`, `stop_sequence`, `model_context_window_exceeded` — none reachable yet, since no tools/stop-sequences are declared) also raises `LLMProviderError`, clearly, rather than crashing on an unmapped enum value.
- **No live credentials or cassette library are used for the required test suite.** `.github/workflows/ci.yml`'s own comment ("Adapter tests use recorded cassettes") describes infrastructure (e.g. `vcrpy`) that does not exist in this repository yet — building it was judged bigger than this one step. Instead: `_map_response` is tested with real SDK response objects (no I/O at all); `complete()`'s pre-flight validation (unconfigured alias/pricing) needs no network; and `complete()`'s real network path is exercised against **real local endpoints** — a closed TCP port (genuine `APIConnectionError`) and a tiny local `http.server` returning a genuine 401 body and a genuine well-formed 200 `Message` body (genuine `APIStatusError` and a full, real success round trip) — real transport and real SDK parsing throughout, never a mocked client. **New `tests/integration/llm_gateway/test_anthropic_adapter_live.py`** is the opt-in exception: skipped unless `AIOS_SECRET_LLM_ANTHROPIC_API_KEY` is set, it makes one real, cheap (`fast-cheap` alias, `max_output_tokens=16`) call to the live Anthropic API — this is also how a real call is manually verified (see this step's own report).
- **Still deliberately not a Gateway redesign**: no Request Validator, Capability Negotiator, Policy & Budget Enforcer, real Router, Prompt Cache Planner, Retry & Fallback Manager, or Rate Limiter — the SDK's own default retry behaviour (`max_retries=2`) is the only retry present, and it is the SDK's, not this Gateway's. Nothing in the Workflow Engine calls `LLMGateway.complete()` yet, so this adapter is not wired into any composition root — the same position `EchoLLMGateway` itself has always been in.
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite: **356 tests passing, 1 skipped** (the opt-in live test, skipped by design without credentials). Combined unit+integration coverage: **96.80%** (`anthropic_adapter.py`: 100%; `model_config.py`: 100%).

### Stage B – One Real End-to-End Path: `PromptEngine` → `LLMGateway(AnthropicAdapter)` → `llm_calls` Recording
- **New `build_anthropic_prompted_completion_service()`** (`ai_os_kernel.prompted_completion`) — the "connect the existing composition path" deliverable this step approves. Composes three already-existing, already-tested real implementations into one `PromptedCompletionService`: `SqlPromptCatalog(engine)` (real `catalog.prompts` reads), `AnthropicAdapter` via `build_anthropic_adapter()` (API key resolved through the injected `SecretProvider`, never `ANTHROPIC_API_KEY` directly — reused unchanged from last step), and `SqlLLMCallRecorder(engine)` (real `evaluation.llm_calls` writes). `model_ids`/`pricing` are accepted as parameters, not loaded from a hardcoded path — a caller decides where its configuration comes from (production: `config/llm.yaml` via `load_provider_config()`), mirroring `build_anthropic_adapter()`'s own shape for the identical two parameters.
- **`PromptedCompletionService` itself is completely unchanged.** It was already generic over the `PromptEngine`/`LLMGateway` Protocols — this step needed no new composition logic, only a convenient, secrets-resolved, production-quality way to *construct* the one real combination the approved framing names explicitly. `EchoLLMGateway`/`InMemoryPromptEngine` remain fully available and are exactly what the service's own pre-existing unit test suite (`tests/unit/kernel/test_prompted_completion.py`) continues to use for deterministic composition-logic tests — unchanged, still passing.
- **New unit test** (`test_build_anthropic_prompted_completion_service_wires_the_real_components`) proves the factory's own wiring — real `EnvSecretProvider` (fake key value), a never-connected `AsyncEngine` (construction is lazy; no real I/O happens until a method is awaited) — asserting the returned service's components are genuinely `SqlPromptCatalog`/`AnthropicAdapter`/`SqlLLMCallRecorder`, not silently something else.
- **New `tests/integration/test_prompted_completion.py`** (real Postgres, ADR-0015, no live credentials): seeds a real `catalog.prompts` row with a template (`"Hello, {{name}}!"`) and a real `catalog.agents`/`workflow_instances` row, then proves the *database-backed* two-thirds of the chain end to end with `EchoLLMGateway` standing in for the paid call — a real row renders with real variable substitution, and a real `evaluation.llm_calls` row is written with the right `agent_id`/`prompt_id`/`prompt_version`/`model_alias`, plus the existing "no recording without workflow/step context" rule still holding against a real database.
- **New `tests/integration/test_prompted_completion_live.py`** — the opt-in live test bullet 5 of the approved framing calls for: skipped unless `AIOS_SECRET_LLM_ANTHROPIC_API_KEY` is set, it seeds a real prompt, builds the service via `build_anthropic_prompted_completion_service()`, and makes one real, cheap Anthropic call — asserting the rendered content, a real non-empty response, a real positive `cost_usd`, and a real recorded `evaluation.llm_calls` row with `provider = 'anthropic'`. This is every piece of the approved chain real at once, and how a real end-to-end call is manually verified (see this step's own report).
- **Still not wired into any composition root.** Like `AnthropicAdapter` itself, nothing in the Workflow Engine or any API surface calls `PromptedCompletionService`/`build_anthropic_prompted_completion_service()` yet — this step proves the composition works, it does not make anything real call it. No Router, no budgets, no streaming, no Workflow Engine changes, per the approved framing's own exclusions.
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite: **359 tests passing, 2 skipped** (both opt-in live tests, skipped by design without credentials). Combined unit+integration coverage: **96.81%** (`prompted_completion.py`: 100%).

### Stage B – One Thin Real Agent: `PromptedAgent`, Wired Through `AgentStepExecutor`
- **New `kernel/src/ai_os_kernel/workflow_engine/prompted_agent.py`**: `PromptedAgent`, the first real, non-`Echo*` `Agent`. Reads `promptId`/`promptVersion`/`modelAlias` from its `inputs` dict, validates all three are present (`PromptedAgentInputError` otherwise, new in `workflow_engine/errors.py`), and delegates to an injected `PromptedCompletionService.complete_from_prompt()` — returning `{"content": <the completion's text>}` against a matching `output_schema`. `variables`/`workflowId`/`stepId`/`agentId` are also read from `inputs` as a direct, unmodified passthrough to that method's own already-existing, already-optional parameters — no new input-mapping system, just forwarding keys that were already there. `maxOutputTokens` is deliberately not one of these: it is not part of the documented Step Contract, so it is a required constructor parameter instead (configuration the composition root supplies once per agent instance).
- **`AgentStepExecutor.execute()` now forwards a step's declared invocation fields instead of always calling `agent.execute({})`.** A new private `_invocation_inputs()` builds `{"promptId": ..., "promptVersion": ..., "modelAlias": ...}` from whichever of `step.prompt_id`/`step.prompt_version`/`step.model_alias` the step actually declared (all three remain optional on `WorkflowStep`) — realising agent_architecture.md's own already-documented sentence: "the Workflow Engine passes them through without acting on them itself." A step declaring none of them still executes with an empty `inputs` dict, byte-for-byte the same behaviour as before this step; `EchoAgent` and every other existing `Agent` implementation are unaffected since they already ignore `inputs`.
- **Constructor-injected, deliberately not entrypoint-loadable, and that boundary is pre-existing, not new.** `EntrypointLoader` always constructs with zero arguments — its own docstring already states that passing manifest-declared configuration into a dynamically-loaded entrypoint's constructor is "real Capability Manager design work, not attempted here." A real `PromptedCompletionService` needs a database engine, a resolved secret, and model/pricing configuration — genuine constructor dependencies with nowhere honest to come from inside a zero-argument `cls()` call. `PromptedAgent` is therefore used through `InMemoryAgentRegistry` — the identical "existing registry path" `EchoAgent` itself is already exercised through — not `SqlAgentRegistry`. Making a dependency-carrying agent real-entrypoint-loadable would mean building exactly the constructor-configuration mechanism the entrypoint loader was explicitly scoped to exclude two steps ago.
- **New `tests/unit/kernel/workflow_engine/test_prompted_agent.py`** (9 tests, `InMemoryPromptEngine`/`EchoLLMGateway`/a fake recorder — no database, no network): proves rendering + completion with and without template variables, all three "missing required field" error cases (individually and all-at-once), recording when workflow/step context is supplied, no recording without it, and the declared `output_schema` shape itself.
- **`tests/unit/kernel/workflow_engine/test_agent_step_executor.py` extended** (3 new tests, a new `_InputCapturingAgent` fake): proves a step declaring none of the three fields still passes an empty `inputs` dict, a step declaring all three forwards exactly those three camelCase keys, and a step declaring only one forwards only that one — real evidence of `AgentStepExecutor`'s own new behaviour, not an assumption about it.
- **New `tests/integration/workflow_engine/test_prompted_agent_live.py`** — the opt-in live test this step's own bullet 4 calls for, and the top of the chain the last two steps' own live tests already proved the middle and bottom of: skipped unless `AIOS_SECRET_LLM_ANTHROPIC_API_KEY` is set, it builds a real `WorkflowStep` declaring `promptId`/`promptVersion`/`modelAlias`, executes it through a real `AgentStepExecutor` and `InMemoryAgentRegistry` resolving to a real `PromptedAgent`, and asserts a real, non-empty completion came back from the live Anthropic API — proving the full path from a declared step to a real model call, not just the pieces in isolation.
- **Still deliberately narrow**: no Router, no budgets, no streaming, no Capability Manager expansion, and no general per-step input-mapping mechanism — only the three Step Contract invocation fields flow from a step into an agent, exactly as documented and no further. Nothing writes `PromptedAgent` into `kernel/bootstrap.py` or any real API surface; it is proven, not yet consumed, the same position every other piece of this chain has been left in.
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite: **371 tests passing, 3 skipped** (all three opt-in live tests, skipped by design without credentials). Combined unit+integration coverage: **96.87%** (`prompted_agent.py`: 100%; `step_executor.py`: 96% — only the two pre-existing, statically-unreachable "step declares no agentId/toolId" defensive branches remain uncovered, unchanged from before this step).

### Stage B – Real Composition-Root Registration: `PromptedAgent` Wired Into `bootstrap.py`
- **`kernel/bootstrap.py` gained a `_lifespan` hook** — FastAPI's own recommended async-startup mechanism, used here for a specific, structural reason: `build_app()` runs synchronously at import time (`app = build_app()` in `entrypoints/api.py`, before any event loop exists), but building a real `PromptedCompletionService` needs async secret resolution. `_lifespan` runs once when the app actually starts serving, builds the real chain, and attaches it as `app.state.agent_registry` — the same "attach a real composed object to `app.state`" pattern `manifest_loader`/`health_service` already use, just deferred to the point where async construction becomes possible.
- **The real chain, reusing every already-built piece unchanged**: `DatabaseSettings()` (env-driven `AIOS_DATABASE_URL`, already established for persistence) → `build_engine()` → `load_provider_config(config/llm.yaml)` → `build_anthropic_prompted_completion_service()` (Secrets Resolution + `AnthropicAdapter` + `PromptedCompletionService`, unchanged from two steps ago) → `PromptedAgent` (unchanged from last step) → `InMemoryAgentRegistry({"platform/prompted-agent": agent})`. No new production logic was needed in any of the composed pieces — this step is entirely "wire it," matching its own approved framing.
- **Degrades to an empty registry, not a crash, when unconfigured.** A missing `AIOS_DATABASE_URL`, a missing/unresolvable Anthropic secret, or a missing `config/llm.yaml` are all caught by one `try`/`except Exception` around the whole construction, logging a warning and leaving `app.state.agent_registry` as an empty `InMemoryAgentRegistry` — mirroring `manifest_loader_check`'s own established "catch, report, don't crash the process" shape in the same file. Stage A functionality (health checks, manifest discovery) must not depend on a Stage B integration being present.
- **`platform/prompted-agent`** is the registered id — a fully-qualified `pack_id/agent_slug` shape (data_model.md §5) even though no real Capability Pack owns it yet; there is no Capability Manager to assign a real one (Stage C), and inventing a fake pack registration would be further from the truth than naming it honestly as platform-level. `_ANTHROPIC_API_KEY_SECRET_REFERENCE` reuses the exact `secret://env/llm/anthropic-api-key` reference every prior step already used. `_PROMPTED_AGENT_MAX_OUTPUT_TOKENS` (not part of the Step Contract, so not derivable from a step) is a named, documented constant — the Constitution's own explicitly-permitted carve-out ("Hardcoding is prohibited unless technically unavoidable and explicitly documented") until a real per-agent configuration mechanism exists.
- **Verified, not assumed: a bare `TestClient(app)` never triggers `_lifespan` at all** (confirmed with a minimal standalone reproduction before relying on it) — only `with TestClient(app) as client:` does. Every existing health-check test in `tests/unit/kernel/entrypoints/test_api.py` uses the bare form and is therefore completely unaffected by this step; a new explicit test proves this invariant directly rather than leaving it implicit.
- **New `tests/unit/kernel/test_bootstrap.py`** (3 tests, no real database, no real network): the degrade-gracefully path (unconfigured environment → empty registry → `AgentNotRegisteredError` on resolve, not a crash); the construct-for-real path (a syntactically valid but never-connected database URL plus a fake-but-present secret — construction itself does no I/O — → a genuine `PromptedAgent` instance resolves successfully); and the bare-`TestClient`-never-triggers-lifespan invariant.
- **New `tests/integration/test_bootstrap_prompted_agent_live.py`** — the opt-in live test verifying this step's own deliverable specifically: skipped unless `AIOS_SECRET_LLM_ANTHROPIC_API_KEY` is set, it is the *only* live test in this codebase that goes through `bootstrap.build_app()` itself (every prior live test constructed its chain by hand) — proving the real composition root, not a hand-assembled equivalent, produces a working agent against a real (`testcontainers`) Postgres and the live Anthropic API.
- **Still deliberately narrow**: no Router, no budgets, no streaming, no Capability Manager entrypoint-configuration framework, and the Workflow Engine's own step-execution machinery (`AgentStepExecutor`, `WorkflowInstanceService`, ...) is still not wired into `bootstrap.py` at all — only the `AgentRegistry` a future step-execution wiring would need is. Nothing reads `app.state.agent_registry` from a real HTTP route yet ("No API surface," §4, remains open).
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite: **374 tests passing, 4 skipped** (all four opt-in live tests, skipped by design without credentials). Combined unit+integration coverage: **96.92%** (`bootstrap.py`: 92% — the only gaps are `_load_configuration()`, uncalled because every test supplies an explicit `config`, and `manifest_loader_check`'s own pre-existing exception branch, both unrelated to this step).

### Stage B – Workflow Engine Step-Execution Machinery Wired Into `bootstrap.py`; One Minimal Real Trigger
- **`_lifespan` now builds the database engine itself**, once, separately from `_build_prompted_agent_registry` — a deliberate refactor: previously that function built its own engine internally and returned `tuple[AgentRegistry, AsyncEngine | None]`, collapsing "database unavailable" and "LLM/secret unavailable" into one degrade path, silently discarding a perfectly good database connection whenever only the unrelated LLM secret was missing. `_build_prompted_agent_registry(engine: AsyncEngine) -> AgentRegistry` now takes an already-built engine and only degrades its own LLM-specific failure to an empty registry; a missing database is now handled one level up in `_lifespan`, which skips building both the registry and the trigger when there is no real engine to run either against.
- **`_build_workflow_trigger(engine, agent_registry)`** composes the real `WorkflowInstanceService` (`SqlWorkflowInstanceRepository`, `SqlWorkflowDefinitionCatalog`, `DispatchingStepExecutor` over `AgentStepExecutor(agent_registry)` / `ToolStepExecutor(InMemoryToolRegistry({}))` / `NoOpStepExecutor`) and the real `WorkflowAdvanceRunner` (`WorkflowLeaseService(SqlWorkflowLeaseRepository(engine))`), closes over one demo `WorkflowDefinition`, and returns a plain async `trigger(inputs, principal_id)` closure — a new class was not justified (ADR-0004): this is "call three already-built async methods in sequence," the identical reasoning `PromptedCompletionService` itself was built on.
- **The demo `WorkflowDefinition`** (`platform.prompted_agent_smoke_test`, version `1.0.0`, one `AGENT` step naming `agentId: platform/prompted-agent`) is constructed directly in Python in `bootstrap.py`, not loaded from a file via `WorkflowDefinitionLoader` — that loader's own design (confirmed by reading it and its tests) is for loading a real pack's own definition file from a manifest-declared path, and there is no real Capability Pack directory for one to live in yet at the platform level; every existing test in this codebase already constructs `WorkflowDefinition` objects directly in Python for the identical reason. `workflow_steps` has no foreign key on `agent_id`/`prompt_id`/`prompt_version`/`model_alias` (confirmed by inspecting `persistence/schema.py`), so declaring these without a matching `catalog.agents`/`catalog.prompts` row is safe for persistence — though a real `catalog.prompts` row is still needed for the agent to actually render successfully against the live Anthropic API, which the new live test seeds.
- **Deliberately not a real HTTP route.** Re-reading `docs/07_api/api_architecture.md` in full (this step's own mandated alignment checkpoint) found its documented `POST /api/v1/workflows` contract requires OIDC bearer authentication and `workflow:start` permission-based authorization through a Security Manager that does not exist in this codebase yet — building a real, unauthenticated route would violate that already-approved contract, not just leave it incomplete. `app.state.trigger_prompted_agent_workflow` is the "otherwise a minimal explicit service entrypoint that bootstrap owns" fallback this step's own approved framing explicitly anticipated: a real, callable, composition-root-owned function, reachable by a test or a future Security-Manager-fronted route, never by an unauthenticated request.
- **New `tests/integration/test_bootstrap_workflow_trigger.py`** (2 tests, real Postgres via `testcontainers`, no live Anthropic credential): a hand-built `PromptedAgent` wrapping `InMemoryPromptEngine`/`EchoLLMGateway` is substituted into `_build_workflow_trigger`'s `agent_registry` parameter, proving the real Workflow Engine machinery (create → start → advance → step dispatch → agent resolution → output validation → persistence) genuinely reaches and invokes whatever agent is registered — one test asserts a `COMPLETED` `WorkflowRunResult` with the Echo agent's real output persisted in `workflow_steps`; the other asserts a `FAILED` `WorkflowRunResult` carrying `AgentNotRegisteredError` when the demo agent isn't registered, rather than a crash.
- **New `tests/integration/test_bootstrap_workflow_trigger_live.py`** — opt-in, skipped unless `AIOS_SECRET_LLM_ANTHROPIC_API_KEY` is set: seeds a real `catalog.prompts` row matching the demo step's declared `promptId`/`promptVersion`, goes through the real `bootstrap.build_app()` + `_lifespan` composition root (not a hand-assembled equivalent), and calls the real `app.state.trigger_prompted_agent_workflow` to drive the demo workflow to a genuine Anthropic-backed `COMPLETED` result.
- **Still deliberately narrow**: no Router, no budgets, no streaming, no Capability Manager expansion, no real HTTP route, no worker scheduler, no multi-instance queue framework — "create/start/advance one workflow instance path is enough," exactly as approved.
- `mypy --strict` (190 source files), `ruff check`, `ruff format --check` all clean on first attempt. Full suite: **376 tests passing, 5 skipped** (five opt-in live tests, skipped by design without credentials). Combined unit+integration coverage: **96.93%**.
