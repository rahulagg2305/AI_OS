## 5. Blockers / Risks

- **CI has still never actually executed on GitHub's servers** — this working tree is not yet a git repository (no remote, no pushes, nothing to trigger a workflow run). `.github/workflows/ci.yml` is now aligned with the codebase and every real (non-gated) command in it has been verified locally, command-for-command (see §3), but that is not the same guarantee as a real Actions run. Re-verify once this becomes a pushed git repository with Actions enabled. **Note (2026-07-28 infrastructure step): this is now stale — the repository has since been `git init`'d and a baseline commit made; still no GitHub remote/push, since `gh` is unavailable in this environment. See the current, short `implementation_status.md` for the live status.**
- **Only the `env` secrets backend exists.** `AnthropicAdapter` now resolves its API key through `EnvSecretProvider` (ADR-0024 explicitly scopes this backend to local development only) — real production use still needs Vault or a cloud secret manager, neither of which exist yet. Not a blocker for this step (local development and the opt-in live test both work today), but a real blocker before any production deployment calls a real provider.
- **`uv` is still not on `PATH` in this Windows session** (unchanged from earlier steps — `.venv/Scripts/{python,pytest,mypy,ruff}.exe` are used directly). Adding the `anthropic` dependency required regenerating `uv.lock`; `uv` was installed via `pip install uv` into the project venv (not the system binary) to do this. `uv sync --frozen --all-packages` was then verified twice: once with the latest `uv` (0.11.32), and once with `uv==0.5.11` — the exact version `ci.yml` pins (`UV_VERSION: "0.5.11"`) — confirming the regenerated lockfile is genuinely compatible with the CI-pinned CLI, not just a newer one.
- **Environment note, not a repo defect:** the development machine has a native (non-Docker) Postgres already listening on `0.0.0.0:5432`, which shadows the compose container's default port mapping for host-side connections. `infra/docker-compose.yml` already supports overriding via `AIOS_DB_PORT` (used `5434` during verification); worth remembering if `localhost:5432` ever appears to "hang" or reject credentials that are actually correct.
- **`__pycache__` directories present under `kernel/src/`** — harmless (covered by `.gitignore`), noted only because this is not yet a git repository, so nothing has been committed or excluded yet. **Note (2026-07-28 infrastructure step): resolved — the repository now exists and `.gitignore` is in force.**
- **Bearer tokens are pre-shared-secret JWTs, not full OIDC.** `JWTBearerTokenVerifier` (see §3) verifies signature and expiry against an `AIOS_SECRET_SECURITY_JWT_SIGNING_KEY` shared secret — there is no identity provider, no JWKS endpoint, no issuer/audience check. Fine for local development and for proving the auth boundary genuinely works (this step's own tests mint tokens with the same shared secret), but **not production-credible as-is**: anyone holding that one shared secret can mint a token for any principal/role. Replacing it with a real OIDC-backed `TokenVerifier` is the documented upgrade path (§3) and does not require changing any caller — but it has not happened yet, and must before any non-development deployment exposes this route.
- **Nine routes exist, and all are narrower than their own documented (or, for `POST /api/v1/packs`, entirely undocumented) contracts.** `POST /api/v1/workflows` accepts only `inputs` and returns `200` with a reduced body instead of api_architecture.md §6.1's `202`/`definition_id`/`Idempotency-Key` shape; `GET /api/v1/workflows` has no filtering; `/steps`/`.../events` are not paginated; `POST /api/v1/packs` is not in §6.5's documented list at all; pack activate/deactivate return `200` not §6.5's documented `202`; there is no `GET /api/v1/packs` (list). Every other §6 endpoint (approvals, experiments, gates, usage, agents, config, traceability, `/stream`) still returns 404 (FastAPI's default for an undefined route).
- **Pack activation still has no ADR-0007 human-approval gating.** capability_manager.md §4 and api_architecture.md §6.5 both note that activation of a pack affecting platform behaviour requires human approval; `POST /api/v1/packs/{id}/activate` activates immediately and synchronously for anyone holding `pack:manage`, with no approval step at all. Acceptable for this minimal slice (explicitly out of scope — "no permissions matrix" — and no real pack yet has meaningfully "platform-affecting" behaviour to gate), but a real blocker before this route is exposed to anyone beyond a trusted operator.
- **A second real, network-calling provider adapter now exists (`LocalAdapter`), but is not registered by default in the checked-in production config.** `config/llm.yaml`'s `local_provider` section is commented out — no local model server is assumed running in a fresh checkout — so `kernel/bootstrap.py` registers only `anthropic` today. Genuine two-real-provider dispatch is proven by `test_multi_provider_routing.py` against real local HTTP servers standing in for both APIs, not (yet) by a live call to a real Ollama/vLLM/LM Studio instance from the running Kernel.
- **The real fallback chain that exists today is same-provider only; the cross-provider example is commented out for the same reason as `local_provider`.** `coding-strong` genuinely falls back from Anthropic to Anthropic (`claude-opus-5` -> `claude-sonnet-5`) — real chain traversal, proven by a real composition-root test, but it does not exercise a cross-provider failure path against the live Kernel. Fallback itself is still ungated by the Error Taxonomy on purpose (any `LLMProviderError` triggers a fallback attempt, retriable or not — a different provider is a different call, see §3) — only same-candidate retry and circuit-breaker counting are gated by classification.
- **The Circuit Breaker's, the backoff policy's, and both budget enforcers' numbers are hardcoded constants in `kernel/bootstrap.py`, not configuration.** `_CIRCUIT_BREAKER_FAILURE_THRESHOLD = 5`/`_CIRCUIT_BREAKER_RESET_TIMEOUT_SECONDS = 30.0`, `_BACKOFF_MAX_ATTEMPTS = 3`/`_BACKOFF_BASE_DELAY_SECONDS = 0.5`/`_BACKOFF_MAX_DELAY_SECONDS = 8.0`/`_BACKOFF_MAX_TOTAL_SECONDS = 15.0`, and `_ALIAS_BUDGET_CEILING_USD = Decimal("10.00")`/`_WORKFLOW_BUDGET_CEILING_USD = Decimal("25.00")` are all real, documented, but not tunable without a code change and redeploy — the identical, already-accepted carve-out `_PROMPTED_AGENT_MAX_OUTPUT_TOKENS` uses, not a new gap this step introduces. The Circuit Breaker and both budget enforcers are also all **not persisted across process restarts** — a multi-instance or frequently-restarted deployment would lose all circuit state and all recorded spend on every restart, always starting every provider `CLOSED` and every alias/workflow at zero spend again; a real, plausible second implementation of either (e.g. Redis-backed) is deferred, not yet justified by a second real need (ADR-0004).
- **`Retry-After`'s HTTP-date form is not parsed.** `parse_retry_after_seconds()` reads only the numeric-seconds form (the common case for rate limiting); a provider sending `Retry-After: Wed, 21 Oct 2026 07:28:00 GMT` degrades to this Gateway's own computed exponential-backoff delay instead — a real, documented gap, not a crash. The platform-wide `AiOsError` hierarchy `error_handling_retry.md` §8 describes also still does not exist anywhere in the codebase — this step's own `LLMProviderError`/`LLMRefusalError` fields use that document's vocabulary and field names so a future adoption is a migration, not a rewrite, but the hierarchy itself remains unbuilt, deliberately out of scope for an LLM-Gateway-encapsulated step.

No pre-flight cost estimate for either real ceiling — a real call's cost can push cumulative spend past its ceiling before the *next* call is refused, since nothing here guesses an upcoming cost (§12 forbids approximating a token count from anything but a provider's own endpoint).

## 6. Recommended Next Small Step (as of 2026-07-28, before this infrastructure step)

**Unchanged from the previous step, and now stronger: wire `DockerSandbox` in as the pipeline's real sandbox backend.** This step was documentation reconciliation and verification-debt closure, not development — it deliberately did not touch this recommendation's own substance. What has changed is confidence: `DockerSandbox` is no longer merely "real and tested against mocks" — this step's own real run against a genuine daemon found and fixed two real bugs (missing image auto-pull; the Windows/npipe stdin-EOF issue) and then proved all 7 of its own Tier 1 guarantees for real, unmocked, against a live container. The one remaining blocker is unchanged and still real: this pack's own agents construct commands using `sys.executable`, a host-specific path that does not exist inside `DockerSandbox`'s own container image. `LocalSubprocessSandbox` remains every agent's own default; `DockerSandbox` is real, now genuinely proven, and still unreachable from any real run today. Hardening the sandbox was correctly prioritized over an HTTP route or human-approval gating precisely because the pipeline genuinely runs LLM-generated code — that risk remains fully unmitigated until something actually constructs `DockerSandbox` in place of the local backend, and there is no longer a "does it even work" question standing between here and doing so.

**Recommended: resolve the portable-interpreter gap and wire `DockerSandbox` in as the pipeline's real sandbox backend — closing the loop this step's own prioritization opened.** Concretely, the smallest real slice: decide and implement one portable way for the pack's own agents to invoke a generated file without depending on `sys.executable` (the leading candidate: change `BuildAgentEntrypoint`/`TestAgentEntrypoint`/`DocumentationAgentEntrypoint`'s own write/run scripts to invoke `python3` resolved via the sandbox's own `PATH`, rather than the host's own absolute interpreter path — a small, mechanical change, not a redesign, since every one of this pack's own generated files is already Python by construction), then construct `DockerSandbox` instead of `LocalSubprocessSandbox` at the one place agents currently default it (each entrypoint's own `sandbox or LocalSubprocessSandbox()` line, or a single composition-root-level default the pack's own `pipeline.py` supplies to every agent it constructs). Prove it by re-running this pack's own existing deterministic test suites against the swapped-in backend (no new tests needed if this is done as a parametrized substitution — the same passing/failing outcomes should hold, this time inside a real, network-isolated, filesystem-contained container) plus, once Docker Desktop is available, the two currently-unexecuted live suites (`test_docker_sandbox_live.py`, `test_delivery_pipeline.py`'s own live tier) together for the first genuinely hardened, fully live, end-to-end run this project will have produced.

This is justified over returning to the HTTP route or human-approval gating (both still real, still available candidates):
- Neither reduces the concrete risk this whole hardening step exists to close. An HTTP route would make an *unhardened* pipeline reachable by more callers; human-approval gating adds oversight to *what* happens at named checkpoints without changing *how safely* the sandboxed execution underneath any of them actually runs. Both are genuinely valuable, but neither is the step that makes `DockerSandbox`'s own work matter in practice.
- It is the more honest reading of "done": a sandbox backend that exists, passes its own tests, and is never actually constructed by anything real is exactly the kind of "real but not yet exercised end to end" position this document has flagged for other components before (`SqlKnowledgeWriter`, `SqlKeywordSearcher`) — worth closing quickly rather than letting accumulate.
- It is small and well-bounded: one interpreter-invocation convention change plus one composition-site substitution, not new architecture.

This step would need its own explicit scope fence before implementation (at minimum: the exact form of the portable-interpreter fix, whether `DockerSandbox` becomes the unconditional default or an explicit opt-in the composition root chooses per environment, whether the pipeline's own deterministic tests should run against `DockerSandbox` too or remain `LocalSubprocessSandbox`-only for speed, and explicit confirmation this does not extend to solving dependency installation inside the now-network-isolated container, which ADR-0016 itself assigns to "a separate, explicitly-declared step through an egress proxy" — a distinct, later increment) — consistent with how every minimal-slice step in this document has been separately scoped and approved.

If a different step is preferred instead: **an HTTP route** — extend `kernel/routes/workflows.py`'s own pattern (or add a small, pack-specific route) to accept a `POST` triggering `ai_os_pack_software_engineering.pipeline.build_pipeline_trigger()`, gated by a `workflow:start`-equivalent permission; **human-approval gating** — a real `approvals` table writer (schema already exists, data_model.md §4.5) plus a real `HumanApprovalPoint`-type step executor, most naturally inserted between `test` and `documentation`; a general, Kernel-level "restrict a resolver to specific steps" wrapper, promoting this pack's own pipeline-local `_StepScopedResolver` (§5); digest-pinning the default sandbox image (§5); or the automated manifest -> catalog installer for agents/prompts/workflows alike.

The DockerSandbox-wiring recommendation above remains the last substantive-development recommendation on record and is very likely still the right next real development step; see the current, short `implementation_status.md` for what is actually recommended next going forward.**
