# AI_OS Implementation History — DockerSandbox Default Wiring

**Milestone:** Resolves the `sys.executable` portability gap and wires `DockerSandbox` in as the Software Engineering pack's real default Tier 1 sandbox backend — the single remaining safety gap on a pipeline that already runs LLM-generated code. Also: deleted the stale, undocumented, never-git-tracked `capability_packs/analytics/` placeholder folder (investigated and approved in the immediately preceding step).

Recorded 2026-07-28. See `docs/19_roadmap/history/INDEX.md`.

### Stage B/C – `capability_packs/analytics/` Removed
- Re-verified immediately before deletion (per the approved framing's own "confirm nothing changed since the investigation" condition): `find`/`ls` showed the directory still contained nothing at all (no files, no `.gitkeep`), and `git ls-files`/`git log --all -- capability_packs/analytics` both still returned nothing — the directory was never tracked by git, not even in the baseline commit. Removed with a plain `rmdir`; no `git rm` was needed since git held no record of it to remove.

### Stage B/C – The `sys.executable` Portability Gap: `python_command` on `SandboxExecutor`
- **New property on the `SandboxExecutor` Protocol** (`kernel/src/ai_os_kernel/sandbox/executor.py`): `python_command: tuple[str, ...]` — the portable argv prefix that invokes a Python interpreter *inside whatever a given backend actually runs commands in*. `LocalSubprocessSandbox.python_command` returns `(sys.executable,)` (correct and portable there: this backend runs directly on the host, using the same interpreter as the calling process). `DockerSandbox.python_command` (`kernel/src/ai_os_kernel/sandbox/docker_executor.py`) returns `("python3",)` — the name the `python:3.12-slim` image's own official build always provides on its own `PATH`, already relied on by this backend's own pre-existing live guarantee tests (`test_docker_sandbox_live.py`), never the host's own path.
- **Why a Protocol property, not a free function taking a backend as an argument**: a caller with an *injected* sandbox (every agent in the Software Engineering pack already receives one) asks that instance directly — no second lookup, no risk of asking the wrong backend which one it is.
- Real, executed unit tests added to both `test_executor.py` and `test_docker_executor.py` proving each backend's own value.
- `DockerSandbox`'s own module docstring updated in place to record this resolution (an implementation module's docstring, not an ADR — freely editable, unlike ADR-0016 itself, which needed no change: its own decision text never named `sys.executable` as a constraint).

### Stage B/C – Config-Driven Default Selection: `ai_os_kernel.sandbox.default_executor`
- **New module**: `build_default_sandbox_executor()` reads `AIOS_SANDBOX_BACKEND` (`"docker"`, the new default, or `"local"`) — the identical `AIOS_*` bootstrap-config convention `AIOS_SECRET_BACKEND` already established — and returns a real `DockerSandbox()` or `LocalSubprocessSandbox()` accordingly. `default_python_command()` is a thin convenience for a caller (the pipeline's own `output_transforms` callable) that needs the interpreter command without constructing a full executor.
- **Deliberately not live Docker-availability probing with an automatic fallback** — the approved framing for this step explicitly excluded building a new Docker-unavailable fallback beyond the one that already exists (choosing `"local"` explicitly). Constructing either backend does zero I/O; if `AIOS_SANDBOX_BACKEND` resolves to `"docker"` and no daemon is reachable, the *already-built* `DockerSandboxUnavailableError` fires on the first real `execute()` call, unchanged.
- **Why the decision has to live inside each entrypoint's own zero-argument constructor default, not "wherever the pack is composed"**: `EntrypointLoader.load()` — the real, `catalog.agents`-driven production path (`SqlAgentRegistry`) — always constructs an entrypoint with `cls()`, zero arguments. There is no composition-root call site that could instead pass a different `sandbox=` for that real path; the only place this decision can take effect is inside each entrypoint's own bare-default resolution.
- 7 new unit tests (`test_default_executor.py`): default is `DockerSandbox` when the env var is unset; explicit `"docker"`/`"local"` both resolve correctly; case/whitespace-insensitive; an unrecognized value raises a clear `UnknownSandboxBackendError` rather than silently picking either backend; `default_python_command()` matches whichever backend the same env var selects.

### Stage B/C – The Three Pack Agents Wired to the New Default
- **`BuildAgentEntrypoint`/`DocumentationAgentEntrypoint`/`TestAgentEntrypoint`** (`capability_packs/software-engineering/src/ai_os_pack_software_engineering/agents/{build,documentation,verification}.py`): each agent's own `sandbox = sandbox or LocalSubprocessSandbox()` became `sandbox = sandbox or build_default_sandbox_executor()` — the real, load-bearing change. `BuildAgentEntrypoint`/`DocumentationAgentEntrypoint`'s own file-write command changed from `[sys.executable, "-c", _WRITE_FILE_SCRIPT, ...]` to `[*self.sandbox.python_command, "-c", _WRITE_FILE_SCRIPT, ...]` — the same agent code now runs unmodified against either backend.
- **`ai_os_pack_software_engineering.pipeline._run_generated_file_with_python`**: `runCommand = [sys.executable, filePath]` became `runCommand = [*default_python_command(), filePath]` — this function is a pure transform over a persisted step-output dict (no sandbox instance of its own to ask), so it reads the identical `AIOS_SANDBOX_BACKEND` configuration the Build/Test agents themselves resolve from, keeping all three in agreement without threading a sandbox reference through `WorkflowStepOutputResolver`'s own generic `output_transforms` signature.
- **No change to `ArchitectureAgentEntrypoint`** — it makes no sandbox call at all (LLM-only, no file writes).

### Stage B/C – Zero-Regression Test Updates
- **A real, discovered tension, resolved deliberately, not silently**: this pack's own existing unit tests (`test_build_agent.py`, `test_documentation_agent.py`, `test_verification_agent.py`) construct these entrypoints with no `sandbox=` override at all, relying on the *implicit* default for real, Docker-independent subprocess execution — each file's own docstring already states this explicitly ("every write in this file happens through a real `LocalSubprocessSandbox`/real OS subprocess"). Flipping the bare default to `DockerSandbox` would have made every one of these currently-passing, intentionally-fast tests suddenly require a live Docker daemon — a real regression, not merely a cosmetic one, in an environment where Docker Desktop availability is already documented as intermittent.
- **Resolution**: every call site in these three files that actually reaches the sandbox now passes `sandbox=LocalSubprocessSandbox()` explicitly — preserving the exact previous behavior and passing status, just made explicit rather than implicit. Call sites that raise before ever reaching the sandbox (a missing file, a malformed payload) were left untouched where doing so caused no ambiguity, and updated regardless at a few sites for defensive consistency. The one test whose entire point is proving zero-argument construction (`test_test_agent_entrypoint_constructs_with_zero_arguments`) was deliberately *not* given an explicit sandbox — that would have defeated its own purpose.
- **`tests/integration/workflow_engine/test_delivery_pipeline.py`'s own deterministic tier** received the identical treatment (`sandbox=LocalSubprocessSandbox()` added to its Build/Test/Documentation entries) — proving a real Postgres container already; gains nothing from also requiring Docker. Its own **opt-in live tier** was left unchanged and now, as a genuine side effect, exercises the real `DockerSandbox` default for the first time (it resolves agents via `EntrypointLoader`'s own zero-argument `cls()` call) whenever it runs with a live Anthropic key.

### Stage B/C – The Real, Hardened, End-to-End Proof
- **New `tests/integration/sandbox/test_delivery_pipeline_docker.py`** — the centerpiece deliverable this step exists for. Runs the identical four-step Architecture → Build → Test → Documentation hand-off `test_delivery_pipeline.py` already proves through `LocalSubprocessSandbox`, here with `sandbox=DockerSandbox()` passed explicitly to Build/Test/Documentation.
- **Materially stronger than "DockerSandbox's own guarantees hold in isolation"**: every other real proof of network isolation/filesystem containment in this codebase (`test_docker_sandbox_live.py`) constructs a `DockerSandbox` directly and hands it a command the test file itself wrote. Here, the Build Agent's own (Echo-backed, deterministic) completion supplies a probe script's content — the identical code path a real, live LLM completion would take — and the Test Agent's own `SandboxedCommandTool` genuinely executes it, through the pipeline's own real `WorkflowStepOutputResolver` hand-off, with no shortcut.
- **The probe script** (embedded in the deterministic Build completion, run for real inside the container by the Test step) attempts exactly two things ADR-0016 Tier 1 must genuinely refuse: an external socket connect (`socket.create_connection(("8.8.8.8", 53), ...)`) and a filesystem write outside its own mounted working directory (`open("/etc/should-not-be-writable-by-generated-code", "w")`). Both are expected to raise `OSError`, caught, and reported via two printed lines (`NETWORK_BLOCKED=True`/`FILESYSTEM_CONTAINED=True`) that the test asserts appear in the Test step's own real, persisted output — observed from inside the running pipeline, not asserted by the test constructing its own container.
- Also asserts the generated file is genuinely visible on the host afterward (the container→host bind-mount direction of filesystem containment) and that the Documentation step's own real Markdown record reflects a passing outcome.
- **Needs a real Postgres and a real Docker daemon** — `postgres_container()`'s own existing clean-skip behavior already covers "Docker is unreachable" for both needs at once; no second, redundant Docker-availability check was added.
- **Environment note: Docker Desktop was unavailable this session** (consistent with this project's own documented intermittent availability) — this new test, and every other Docker/Postgres-gated integration test (229 total), collected and skipped cleanly, with no errors. **Not yet executed for real this session** — the single highest-priority re-verification item once Docker Desktop is available again, per this project's own established convention for exactly this situation.
- `mypy --strict` (280 source files: kernel + `kernel/alembic` + `tests` + the Software Engineering pack's own src/tests) clean. `ruff check`/`ruff format --check` clean. Full unit suite (kernel + pack): **625 passed**, zero regressions. Full integration suite: **229 collected, 229 skipped, 0 errors** (Docker unavailable this session — every skip has a clear, existing reason, none of them new).
