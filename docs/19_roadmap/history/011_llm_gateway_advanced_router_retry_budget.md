### Stage B – The LLM Gateway's Router: Minimum Viable Slice, Preceded by a Full Architecture Alignment Checkpoint
- **Architecture Alignment Checkpoint performed first**, per this step's own approved framing: re-read the Constitution, System Architecture (v2.0), Kernel Architecture (v2.0), LLM Gateway Architecture (v2.0 — the Router's actual home), Capability Manager Architecture, Security Architecture (v1.0), and Coding Standards, in full, before writing any code. Result: **one real finding, no drift, no ADR violations**. See this section's own last bullet and §5 for the full result.
- **Finding: "Router Architecture" is not a standalone document.** DOCUMENTATION_INDEX.md lists no such document; the Router is documented as one of the LLM Gateway's thirteen internal subsystems (llm_gateway.md §3: "``Router` — alias → provider/model, fallback chain", positioned between the Policy & Budget Enforcer and the Provider Adapters in the Gateway's own internal pipeline diagram). kernel_architecture.md's own `High-Level Kernel Structure` component list never mentions a Router at all — only Workflow Engine, LLM Gateway, Prompt Engine, Context Manager, and the other Kernel-level components already built. The correct implementation location is therefore inside `ai_os_kernel.llm_gateway`, not a new top-level `ai_os_kernel.router` package alongside Workflow Engine/Capability Manager/Security Manager — building the latter would itself have been the architectural drift this checkpoint exists to catch.
- **New `ai_os_kernel/llm_gateway/router.py`**: `Router` (`Protocol`, `resolve(model_alias: str) -> RoutingDecision`) and `RoutingDecision` (`provider: str`, `model_id: str`) — the exact two fields llm_gateway.md §3 documents ("alias → provider/model"). `StaticRouter` is the one deterministic implementation: a fixed `model_ids: Mapping[str, str]` resolved against one named `default_provider`, built from the same `config/llm.yaml` alias mapping `AnthropicAdapter` already read directly.
- **Promotes an already-flagged temporary seam, not a new one.** `AnthropicAdapter`'s own docstring already named its internal flat dict "the Router (beyond the flat alias lookup...)"; `model_config.py`'s own docstring and `config/llm.yaml`'s own comment both already said "Deliberately NOT the documented Router config shape" and deferred it explicitly. This step closes that deferral to exactly the width approved — ADR-0004's "an interface is justified when a second implementation is real or clearly imminent": `StaticRouter` is the first; a provider-health-aware or experiment-pinning-aware implementation is the imminent second.
- **`RoutingDecision` is deliberately a single resolved choice, not a chain.** llm_gateway.md §7's documented `aliases.<alias>.chain` list (an ordered list of provider/model candidates) exists for the *Retry & Fallback Manager* to walk on failure — a distinct, later Gateway subsystem this step does not build ("no retries ... no advanced policies," this step's own approved framing). Extending `RoutingDecision`/`StaticRouter` to consider a real chain is the natural, backward-compatible next step once that subsystem exists to consume one; the `Router` Protocol's own `resolve()` shape does not need to change for that.
- **`AnthropicAdapter` now depends on an injected `Router`, not a raw mapping.** Its constructor takes `router: Router` instead of `model_ids: Mapping[str, str]`; `complete()` calls `router.resolve(request.model_alias)` and refuses clearly (`LLMProviderError`, "does not serve") if the decision names a provider other than the one this adapter actually calls — a real guard against a future second provider's routing decision reaching the wrong adapter, not merely a renamed parameter. `build_anthropic_adapter()`/`build_anthropic_prompted_completion_service()` both now accept `router: Router` the same "composition root decides" way they already accepted `api_key_secret_reference` — "routing decisions constructed through dependency injection," this step's own approved framing's second bullet.
- **`kernel/bootstrap.py`** now constructs a real `StaticRouter` in `_build_prompted_agent_registry`, from the identical `provider_config.model_ids` it already loaded, and passes it through unchanged — the one minimal integration into existing behaviour this step's own approved framing permits ("architecture explicitly requires minimal integration"): resolving `model_alias` through the documented Router seam instead of past it changes no observable behaviour (the same alias still resolves to the same model id), it only relocates *where* that resolution happens to the architecturally correct place.
- **No budgets, no streaming, no retries, no advanced policies, no provider selection heuristics, no optimization logic** — exactly this step's own exclusions. Only one provider (Anthropic) exists, so `default_provider` names it once; a second provider adapter would need `StaticRouter` (or a successor) to carry a real per-alias provider field, not invented ahead of one.
- **New `tests/unit/kernel/llm_gateway/test_router.py`** (5 tests): resolution returns the configured provider+model id; an unconfigured alias raises clearly; resolution is deterministic across repeated calls; the router does not share state with the mapping passed in; multiple aliases all resolve to the same configured provider.
- **`tests/unit/kernel/llm_gateway/adapters/test_anthropic_adapter.py` extended** (1 more test): a `Router` naming a different provider is refused with a clear error, not silently routed around. Every pre-existing test in this file, `test_prompted_completion.py`, and three opt-in live test files was updated to construct a `StaticRouter` instead of passing `model_ids` directly — a mechanical signature change with no behavioural change, all previously-passing assertions unchanged.
- **`config/llm.yaml` and `model_config.py`'s own docstrings updated** — both previously said "deliberately NOT the Router," which is now only half true (the Router exists; this file/module is still only its configuration source, not the Router itself) — corrected in the same change, per the Constitution's own "documentation shall be updated within the same change" rule.
- `mypy --strict` (217 source files), `ruff check`, `ruff format --check` all clean. Full suite: **467 tests passing, 6 skipped** (six opt-in live tests, skipped by design without credentials). Combined unit+integration coverage: **97.19%** (`llm_gateway/router.py`: 100%; `llm_gateway/adapters/anthropic_adapter.py`: 100%).

### Stage B – The Router's First Real Multi-Routing Capability: Per-Alias Providers + `DispatchingLLMGateway`
- **`StaticRouter` now takes `routes: Mapping[str, RoutingDecision]` directly**, replacing the previous step's `model_ids: Mapping[str, str]` + one `default_provider` for every alias. Each alias now carries its own explicit `RoutingDecision` (provider + model id) — genuinely multi-provider, not a single-provider assumption baked into the constructor. `RoutingDecision`/`Router` themselves are unchanged; only the one implementation's construction shape improved.
- **Followed the architecture's own worked example, not the task's other suggested option, and explains why.** llm_gateway.md §7 lists routing inputs in order — "the alias chain, provider health, ..., experiment pinning" — with the alias chain first, and its own worked YAML example (`reasoning`'s chain) names `provider: anthropic` for *both* candidates, proving a real, useful chain does not require a second provider at all. Despite that, this step chose the "second provider abstraction" path over "the first real fallback chain," because a chain with no consumer to walk it on failure (the Retry & Fallback Manager, still out of scope — "no retries") would have been an unused data structure with nothing exercising it beyond its own shape, where per-alias provider resolution has an immediate, real, testable consumer today: `DispatchingLLMGateway`.
- **New `DispatchingLLMGateway`** (`ai_os_kernel.llm_gateway.gateway`) — the first real multi-provider `LLMGateway` implementation: asks the injected `Router` which provider a request's `model_alias` means, then delegates the *unmodified* request to whichever real `LLMGateway` is registered under that provider name, raising `LLMProviderError` clearly if none is. No health scoring, no retry-on-failure, no fallback walking — the one decision made is entirely the Router's answer; this class only acts on it, per this step's own "keep all routing decisions encapsulated inside the Router abstraction" requirement.
- **No second real network-calling provider adapter was built.** `EchoLLMGateway` (llm_gateway.md's own trivial, already-real implementation, not a mock) is a second, genuine `LLMGateway` implementation that already existed — using it as the second provider in tests proves `DispatchingLLMGateway` genuinely dispatches between two different real gateways, without needing a second live external integration (a second real provider adapter remains a distinct, later, larger step, out of scope here).
- **Wired into the real composition root with no observable behaviour change.** `build_anthropic_prompted_completion_service` now wraps the real `AnthropicAdapter` in a `DispatchingLLMGateway` with exactly one provider registered (`anthropic`); every configured alias still resolves to Anthropic, exactly as before. This establishes the real extension point a second provider adapter would register into, in one place, without this function's signature or any caller changing — the identical "minimal integration the architecture requires, no behavioural change" reasoning the Router's own bootstrap wiring used last step.
- **`kernel/bootstrap.py`** updated only mechanically: `_build_prompted_agent_registry` now builds `StaticRouter`'s `routes` mapping via a dict comprehension over `provider_config.model_ids`, pairing each alias with `PROVIDER_NAME` — the identical real configuration, now expressed in the new, more general constructor shape.
- **New `tests/unit/kernel/llm_gateway/test_dispatching_gateway.py`** (4 tests): dispatches to the registered gateway the Router names; two different aliases genuinely reach two different registered gateway objects (via a small recording stand-in, not a mock of the class under test); a resolved provider with no registered gateway raises clearly; an alias the Router does not know raises clearly (the Router's own error, unmodified, propagating through the dispatcher).
- **`tests/unit/kernel/llm_gateway/test_router.py` extended** with a genuinely multi-provider test (`test_different_aliases_can_resolve_to_different_providers`); all pre-existing Router/adapter/prompted-completion tests (unit and the three opt-in live files) updated to construct `StaticRouter` via `routes=` — a mechanical signature change, every previously-passing assertion about *behaviour* unchanged.
- **Still deliberately narrow**: no budgets, no provider health scoring, no experimentation, no streaming, no retries, no optimization logic, no real chain, no second real provider adapter — exactly this step's own exclusions.
- `mypy --strict` (218 source files), `ruff check`, `ruff format --check` all clean. Full suite: **471 tests passing, 6 skipped** (six opt-in live tests, skipped by design without credentials). Combined unit+integration coverage: **97.17%** (`llm_gateway/router.py`: 100%; `llm_gateway/gateway.py`: 100%).

### Stage B – The LLM Gateway's Second Real Provider: `LocalAdapter` (OpenAI-Compatible Self-Hosted Servers)

- **New `ai_os_kernel/llm_gateway/adapters/local_adapter.py`**: `LocalAdapter`, the second real `LLMGateway` implementation, behind the identical `Router`/pricing-injection shape `AnthropicAdapter` already established. Chose the provider llm_gateway.md §3's own internal component diagram names explicitly — `local_adapter`, alongside `anthropic_adapter` and an unspecified `<other provider adapters>` placeholder — over an unnamed cloud provider (OpenAI, Google, ...), since no other provider is named anywhere in the documentation tree and this is the only *other* concretely-named adapter. No official vendor SDK exists for a self-hosted server, so `LocalAdapter` speaks the OpenAI-compatible `/v1/chat/completions` HTTP contract self-hosted servers (Ollama, vLLM, llama.cpp's server, LM Studio, ...) already converge on — a real, already-standard wire protocol, not one invented for this step — using `httpx` (promoted from a transitive `anthropic` dependency to a direct one) rather than a vendor SDK that does not exist. `PROVIDER_NAME = "local"`, public for the identical reason `anthropic_adapter.PROVIDER_NAME` is.
- **Mirrors `AnthropicAdapter`'s error-handling shape exactly**, against real local TCP endpoints, no mocked client: a closed port for a genuine connection failure, a real local HTTP server returning a real error status or a real well-formed chat-completion body. `_map_response` reads the untyped JSON payload defensively (`KeyError`/`IndexError`/`TypeError` -> a clear `LLMProviderError`, since there is no SDK response class to validate structure the way `anthropic.types.Message` already does for `AnthropicAdapter`). Refuses a routing decision naming a different provider, exactly like `AnthropicAdapter` does for its own name — no silent routing-around.
- **`build_local_adapter` is deliberately synchronous**, unlike `build_anthropic_adapter`: there is no secret to resolve (a self-hosted server the composition root already trusts by `base_url` alone, not a credential) and no other I/O at construction time, so an `async` signature would only pretend a real await exists.
- **`config/llm.yaml`/`model_config.py` gained two small, additive sections** — `providers:` (alias -> provider name override, for any alias that is not the Anthropic default; absent means unspecified, not "no provider" — `kernel/bootstrap.py`'s own default applies) and `local_provider.base_url` (the local server's OpenAI-compatible root URL; absent by default). Both are purely additive: `LLMProviderConfig.model_ids`/`pricing`'s existing shape, and every alias that predates this step, are completely unchanged — the second provider is reached by *adding* a new alias with a `providers:` entry, not by changing an existing one. `config/llm.yaml` itself now declares one example (`local-fast: llama3.1:8b`, routed via `providers: {local-fast: local}`), with `local_provider` left commented out — no local model server is assumed running in a fresh checkout, so this changes no default behaviour; a real operator uncomments it to exercise the alias against a real running server.
- **`build_anthropic_prompted_completion_service` gained one new, defaulted-`None` parameter: `additional_gateways`.** It still always builds and registers the real `AnthropicAdapter` unconditionally — every existing caller that never passes this parameter gets the identical single-provider `DispatchingLLMGateway` as before, byte-for-byte the same behaviour. When non-empty, its entries are merged into the same `gateways` mapping `DispatchingLLMGateway` already accepts — not a second, generic "build me any provider" factory (still Router/composition-root territory), only "also register what the caller already built."
- **`kernel/bootstrap.py`** now reads `provider_config.providers.get(alias, PROVIDER_NAME)` when building each alias's `RoutingDecision` (previously always `PROVIDER_NAME`), and builds a real `LocalAdapter` via `build_local_adapter` — passed to `build_anthropic_prompted_completion_service` as `additional_gateways={"local": ...}` — only when `provider_config.local_base_url` is not `None`. No `local_provider` is configured in the checked-in `config/llm.yaml` today, so this constructs nothing extra and changes no observable behaviour for the real running Kernel.
- **New `tests/unit/kernel/llm_gateway/adapters/test_local_adapter.py`** (mirrors `test_anthropic_adapter.py`'s structure): pure `_map_response` mapping tests (stop/length finish reasons, cost computation, malformed-payload handling, missing-usage defaults), pre-flight validation (unconfigured alias/pricing, wrong-provider refusal), and real-network tests (closed-port connection failure, real HTTP 500, a real successful chat-completion round trip against a local `http.server`).
- **New `tests/unit/kernel/llm_gateway/test_multi_provider_routing.py`**: the concrete "verify routing across both real providers" proof this step's own framing required — one real `StaticRouter` and one real `DispatchingLLMGateway`, holding a real `AnthropicAdapter` and a real `LocalAdapter` simultaneously, each pointed at its own real local HTTP server (one shaped like Anthropic's Messages API, one shaped like an OpenAI-compatible chat-completions response), genuinely dispatching two different aliases to two different real adapters and getting back the response each server actually sent.
- **`tests/unit/kernel/llm_gateway/adapters/test_model_config.py`** extended with tests for the two new config sections (a configured `providers:` override, malformed `providers`/`local_provider` sections, `local_base_url` defaulting to `None`). **`tests/unit/kernel/test_prompted_completion.py`** extended with a test proving `additional_gateways` merges into the same `DispatchingLLMGateway` without displacing the always-built Anthropic adapter. The three opt-in live test files' router construction was updated to read `config.providers.get(alias, PROVIDER_NAME)` — mechanical, matching `kernel/bootstrap.py`'s own identical change, no behavioural change to what they test (all still exercise only `fast-cheap`, unaffected by the new `local-fast` alias).
- **Still deliberately narrow**: no provider health scoring, no experimentation, no streaming, no retries beyond each HTTP client's own defaults (`httpx.AsyncClient` retries nothing on its own, an honest difference from the `anthropic` SDK's `max_retries` default, not a gap this step fills), no prompt caching, no rate limiting, no real alias chain, no budgets — exactly this step's own exclusions. `RoutingDecision.provider` now genuinely differs across aliases in the checked-in configuration (`local-fast` vs. every Anthropic alias), but only one adapter (`local`) has an unproven live counterpart in production — no local model server is assumed running, so the real end-to-end proof is the local-HTTP-server test above, not a live call.
- **One honest, small coverage gap, noted rather than hidden**: `kernel/bootstrap.py`'s own two-line `if provider_config.local_base_url is not None: build_local_adapter(...)` branch is not exercised through `tests/unit/kernel/test_bootstrap.py` (which reads the real, checked-in `config/llm.yaml`, where `local_provider` is commented out) — `bootstrap.py` overall sits at 75% line coverage, unchanged in kind from before this step. Every piece of logic that branch calls (`build_local_adapter`, `additional_gateways` merging) is covered directly by `test_local_adapter.py`/`test_prompted_completion.py`; only the one `if` in `bootstrap.py` itself is not, since exercising it through the real composition root would mean temporarily rewriting the checked-in production config file from a test, which was judged not worth the added complexity for two lines of a direct pass-through.
- `mypy --strict` (221 source files), `ruff check`, `ruff format --check` all clean. Full suite: **494 tests passing, 6 skipped** (six opt-in live tests, skipped by design without credentials). Combined unit+integration coverage: **96.11%** (`llm_gateway/adapters/local_adapter.py`: 100%; `llm_gateway/adapters/model_config.py`: 100%; `llm_gateway/gateway.py`: 100%; `llm_gateway/adapters/anthropic_adapter.py`: 100%).

### Stage B – The Retry & Fallback Manager's First Real Alias Chain: Chain Traversal Only

- **`RoutingDecision` gained one new, optional, recursive field: `fallback: RoutingDecision | None = None`.** A chain of any length is simply a linked list of the same, already-existing `RoutingDecision` objects — no new list type, no change to the `Router` Protocol's `resolve(alias) -> RoutingDecision` shape, exactly as router.py's own earlier docstring anticipated ("the natural, backward-compatible next step"). Every alias that sets no `fallback` gets `None`, identical to the field's default before this step, so `StaticRouter`'s existing construction shape and every pre-existing test needed zero changes.
- **New `build_routing_chain(candidates: Sequence[tuple[str, str]]) -> RoutingDecision`** (`ai_os_kernel.llm_gateway.router`) — builds one linked chain from an ordered, primary-first `(provider, model_id)` sequence, so a caller with a real chain does not hand-nest the construction itself. Raises `ValueError` for an empty sequence.
- **`DispatchingLLMGateway.complete()` now walks the chain on failure** — the smallest real slice of the Retry & Fallback Manager (llm_gateway.md §3: "backoff, circuit breaker, chain traversal"): **chain traversal only**. On an `LLMProviderError` from the current candidate (including the pre-existing "no registered LLMGateway for this provider" case, now treated as one more failure rather than a special case), it tries `decision.fallback` next, and so on. No backoff (no delay between attempts) and no circuit breaker (no per-provider failure memory across calls) — this step's own approved exclusions, plus no provider health, no experiment pinning.
- **Chose to catch `LLMProviderError` broadly, not llm_gateway.md §10's full retriable/non-retriable Error Taxonomy, and explains why.** §10 documents that only certain error categories (network, rate limit, overloaded, 5xx) are retriable; auth failures, invalid requests, and refusals are not. That taxonomy does not exist in code today — `LLMProviderError` carries a message only, no `category`/`error_code` — and building it (classifying every HTTP status/SDK exception from both `AnthropicAdapter` and `LocalAdapter` into §10's table) is a distinct, larger subsystem, not "the smallest production-worthy Retry & Fallback Manager." This step catches every `LLMProviderError` uniformly and documents the narrowing to only-retriable-categories as a real, honest future refinement once that taxonomy exists — not invented here.
- **`LLMRefusalError` is deliberately never caught and never triggers a fallback.** A model's refusal is a real, valid response (llm_gateway.md §5's own documented outcome), not a failure to route around — silently trying a different provider on a refusal would be a real behaviour decision this step's approved framing does not ask for. Proven by a dedicated test.
- **A response that only succeeded on a fallback candidate has `usage.fallback_used` set to `True`** before being returned (`response.model_copy(update={"usage": ...})`, since both are frozen pydantic models) — llm_gateway.md §5's own field, previously always `False` for lack of a real fallback to set it honestly. A response that succeeded on the first candidate is untouched — `fallback_used` stays `False`, exactly as before.
- **Exhausting every candidate raises one clear, aggregate `LLMProviderError`** naming every provider attempted, in order, chaining the last underlying error via `from` — llm_gateway.md §10's own `llm.chain_exhausted` outcome, without that full error-code taxonomy behind it yet (see above). An alias with **no** configured fallback still raises the exact same, unwrapped error object as before this step — proven by a test asserting `exc_info.value is original_error` — satisfying "preserve deterministic behaviour when no fallback chain is configured" precisely, not just approximately.
- **`config/llm.yaml`/`model_config.py` gained one new, additive section: `fallbacks:`** (alias -> ordered list of `{provider, model}` entries, mirroring llm_gateway.md §7's own chain-entry key names minus `effort`). New `FallbackCandidate` pydantic model; new `LLMProviderConfig.fallbacks: dict[str, list[FallbackCandidate]]` field, defaulting to `{}`. An alias absent from `fallbacks:` is completely unaffected — the existing `aliases:`/`providers:`/`pricing:`/`local_provider:` sections and every alias that predates this step are unchanged.
- **`config/llm.yaml` now declares one real, live-by-default fallback**: `coding-strong` (`anthropic`/`claude-opus-5`) falls back to `anthropic`/`claude-sonnet-5` — a same-provider chain, matching llm_gateway.md §7's own worked `reasoning` alias example (whose chain also names `provider: anthropic` for every candidate), chosen specifically so this is exercisable today with no extra setup (unlike the second, deliberately-commented-out cross-provider example, `coding-balanced` -> `local`, which also needs `local_provider` uncommented with a real server running to actually succeed).
- **`kernel/bootstrap.py`** now builds each alias's `RoutingDecision` via `build_routing_chain`, from the primary `(provider, model_id)` pair plus `provider_config.fallbacks.get(alias, [])`, in order. A new test (`test_bootstrap.py`) proves the *real* composition root, reading the *real* checked-in `config/llm.yaml`, builds `coding-strong`'s exact two-candidate chain — not only a hand-built test router.
- **New tests**: `test_router.py` extended (`RoutingDecision.fallback` defaults to `None` and can be set explicitly; `build_routing_chain` with one candidate, with several, linking them in order, and raising on an empty sequence). `test_dispatching_gateway.py` extended (falls back on primary failure; does not mark `fallback_used` on a first-try success; raises the original error unchanged with no fallback configured; raises a clear aggregate error when every candidate fails; a missing gateway registration triggers fallback like any other failure; a refusal is never caught and never triggers a fallback). `test_model_config.py` extended (reads a real fallback chain; malformed `fallbacks` section/entries). `test_bootstrap.py` extended (the real composition root's chain-building, see above).
- **Still deliberately narrow**: no backoff, no circuit breaker, no provider health, no experiment pinning, no budgets, no streaming, no prompt caching, no rate limiting, no full Error Taxonomy (§10) — exactly this step's own exclusions.
- `mypy --strict` (221 source files), `ruff check`, `ruff format --check` all clean. Full suite: **513 tests passing, 6 skipped** (six opt-in live tests, skipped by design without credentials). Combined unit+integration coverage: **97.27%** (`llm_gateway/router.py`: 100%; `llm_gateway/gateway.py`: 100%; `llm_gateway/adapters/model_config.py`: 100%; `kernel/bootstrap.py`: 94%, up from 75% — the new real-chain test now exercises the branch that previously went untested).

### Stage B – The Retry & Fallback Manager's First Real Circuit Breaker

- **New `ai_os_kernel/llm_gateway/circuit_breaker.py`**: a `CircuitBreaker` Protocol (`is_available(provider) -> bool`, `record_success(provider)`, `record_failure(provider)`) and one real implementation, `InMemoryCircuitBreaker` — per-provider, in-process, three-state (`CLOSED`/`OPEN`/`HALF_OPEN`), matching llm_gateway.md §10 exactly ("a circuit breaker opens per provider after a configured consecutive-failure count and half-opens on a timer"). No persistence across restarts (a real, plausible second implementation — e.g. Redis-backed, shared across Kernel instances — deferred; no second implementation is real or imminent yet, so a Protocol-only seam is enough per ADR-0004).
- **The timer transition is lazy, not scheduled** — `is_available()` itself checks whether `OPEN`'s configured `reset_timeout_seconds` has elapsed and transitions to `HALF_OPEN` as a side effect when it has, rather than a background thread/timer ticking independently. Correct and sufficient because the breaker is only ever consulted immediately before a real call would be made; matches this codebase's existing "no worker scheduler" stance elsewhere (e.g. `WorkflowLeaseReaper`'s own `reap_once()`, not a running loop).
- **Deliberately not concurrency-hardened**: two concurrent requests arriving during the same `HALF_OPEN` window may both be let through as trials rather than exactly one — a known, accepted imprecision most circuit breaker implementations share, not required to be stricter for this step's scope.
- **`DispatchingLLMGateway` gained one new, optional, defaulted-`None` constructor parameter: `circuit_breaker`.** Every existing caller/test that never passes it (all of them, before this step) gets byte-for-byte identical chain-traversal-only behaviour — the breaker is only ever consulted when one is actually supplied. `_call()` now checks `is_available()` before attempting a real call (raising the identical `LLMProviderError` shape as any other failure if not — "no registered LLMGateway" and "circuit breaker is open" are now uniformly two flavours of the same thing), and reports `record_success`/`record_failure` after a real attempt. **No change at all to `complete()`'s chain-walking/fallback/aggregate-error logic** — a circuit-open skip is indistinguishable, at that layer, from a real failure, so the mechanism this step's own approved framing required ("cooperates correctly with... fallback-chain traversal") needed zero new code, only a new failure source feeding the existing one.
- **A circuit-open skip never calls `record_failure`** — no real call was attempted, so there is nothing new to remember; only genuine call outcomes (success or a real `LLMProviderError` from the adapter) update the breaker's state.
- **`kernel/bootstrap.py`** constructs one real `InMemoryCircuitBreaker` (two new, named, documented constants — `_CIRCUIT_BREAKER_FAILURE_THRESHOLD = 5`, `_CIRCUIT_BREAKER_RESET_TIMEOUT_SECONDS = 30.0`; llm_gateway.md §10 specifies the mechanism, not the numbers, the identical "Hardcoding is prohibited unless technically unavoidable and explicitly documented" carve-out `_PROMPTED_AGENT_MAX_OUTPUT_TOKENS` already uses) and passes it to `build_anthropic_prompted_completion_service`, which threads it straight into `DispatchingLLMGateway` — shared across every provider (keyed internally by provider name), so Anthropic and the local provider each get independent failure memory from one instance. `build_anthropic_prompted_completion_service` itself gained the identical defaulted-`None` `circuit_breaker` parameter, threaded through unchanged — every existing caller unaffected.
- **New `tests/unit/kernel/llm_gateway/test_circuit_breaker.py`** (10 tests): an unseen provider is available; fewer-than-threshold failures keep it available; reaching the threshold opens it; a success resets the consecutive-failure count; circuits are tracked independently per provider; the circuit stays open until the reset timeout elapses (deterministic via monkeypatching `time.monotonic`, no real sleeping); a successful half-open trial fully closes the circuit; a failed half-open trial reopens it immediately; constructor validation (`failure_threshold < 1`, `reset_timeout_seconds <= 0`) both raise `ValueError`.
- **`test_dispatching_gateway.py` extended** (5 tests): skips a candidate whose circuit is open without calling its gateway at all (proven with a gateway that raises `AssertionError` if ever invoked); records success after a real successful call; records failure after a real failed call; and one true end-to-end test using the real `InMemoryCircuitBreaker` (not a spy) — a real failure opens a provider's circuit, and the very next call genuinely skips it in favour of the fallback.

### Stage B – The Retry & Fallback Manager's Backoff Capability (Third and Final Named Piece)

- **New `ai_os_kernel/llm_gateway/backoff.py`**: `BackoffPolicy` (a frozen pydantic model — `max_attempts`, `base_delay_seconds`, `max_delay_seconds`, `max_total_seconds` — with its own `delay_seconds(retry_number)` computation), matching llm_gateway.md §10 exactly ("exponential backoff with jitter, bounded attempts and total time"). **Provider-level retry only** (§10's own closing line: "The Gateway owns provider-level retry; the Workflow Engine owns step-level retry — a single boundary, so retries cannot multiply") — `BackoffPolicy` governs retries of one candidate, never a whole-chain retry loop, and never a second layer on top of the Workflow Engine's own step-level retry policy.
- **Full-jitter exponential backoff**: `base_delay_seconds * 2 ** (n - 1)`, capped at `max_delay_seconds`, then a uniform random draw between zero and that cap — the same "full jitter" strategy in wide production use specifically because it spreads retries out evenly rather than every failed caller retrying at the identical instant. `max_total_seconds` bounds the *cumulative* delay across every retry of one candidate.
- **`retry_after` is deliberately not honoured.** §10 documents providers returning a `Retry-After` value on a 429; no adapter (`AnthropicAdapter`, `LocalAdapter`) extracts that value from a real response today — the full §10 Error Taxonomy (categorising provider errors and surfacing their headers) does not exist in code yet, so there is nothing for this policy to honour. A real, honest gap, documented rather than invented around.
- **`DispatchingLLMGateway` gained one new, optional, defaulted-`None` constructor parameter: `backoff_policy`.** Every existing caller/test that never passes it (all of them, before this step) gets byte-for-byte identical single-attempt-per-candidate behaviour. A new `_call_with_backoff` wraps the existing `_call` in a retry loop; `complete()`'s own chain-walking/fallback/aggregate-error logic needed **zero changes** — it now calls `_call_with_backoff` instead of `_call`, and every exhausted-candidate failure still raises the identical `LLMProviderError` shape it always did, so the pre-existing exception-handling path treats "every retry of this candidate failed" exactly like "this candidate failed once" always was.
- **Backoff cooperates directly with the Circuit Breaker, not just side by side.** Before sleeping for a retry, `_call_with_backoff` consults the breaker (if any) again: if the attempt that just failed already opened this candidate's circuit, no further retry of a now-known-unhealthy candidate is attempted — no wasted delay on a call that would only be rejected anyway — and the chain moves straight to the fallback instead. This is the specific "naturally cooperates with... Circuit Breakers" requirement this step's own approved framing named.
- **A response that only succeeded after one or more retries has `usage.retries` honestly set** to the number of retries that preceded the success (`response.model_copy(update={"usage": ...})`, the identical pattern `usage.fallback_used` already established) — llm_gateway.md §5's own field, previously always `0` for lack of a real retry to count. A response that succeeds on the first attempt is untouched.
- **`kernel/bootstrap.py`** constructs one real `BackoffPolicy` (four new, named, documented constants — `_BACKOFF_MAX_ATTEMPTS = 3`, `_BACKOFF_BASE_DELAY_SECONDS = 0.5`, `_BACKOFF_MAX_DELAY_SECONDS = 8.0`, `_BACKOFF_MAX_TOTAL_SECONDS = 15.0`; the identical "Hardcoding is prohibited unless technically unavoidable and explicitly documented" carve-out the Circuit Breaker's own constants already use) and passes it to `build_anthropic_prompted_completion_service`, which threads it straight into `DispatchingLLMGateway` alongside the Circuit Breaker. `build_anthropic_prompted_completion_service` itself gained the identical defaulted-`None` `backoff_policy` parameter, threaded through unchanged — every existing caller unaffected.
- **New `tests/unit/kernel/llm_gateway/test_backoff.py`** (7 tests): the exponential cap computation across several retry numbers (deterministic, via monkeypatching `random.uniform` to always return its upper bound); the cap at `max_delay_seconds`; a real, uncontrolled draw stays within `[0, cap]`; constructor validation (`max_attempts < 1`, and each of the three duration fields `<= 0`) all raise `ValueError`.
- **`test_dispatching_gateway.py` extended** (8 tests, all using a module-wide `autouse` fixture that makes `asyncio.sleep` a no-op so the suite stays fast): no policy configured makes exactly one attempt; a successful first attempt leaves `usage.retries` at `0`; a candidate that fails then recovers is retried and `usage.retries` reports the correct count; exhausting all retries of the primary genuinely falls back; the final attempt's exact exception object propagates unchanged when no fallback is configured; backoff stops retrying the instant the Circuit Breaker opens (proven by call-count, not just behaviour); backoff stops retrying once the cumulative time budget is exhausted (proven deterministically by monkeypatching `time.monotonic` to advance on each simulated slow call).
- **`test_prompted_completion.py`/`test_bootstrap.py` extended**: `backoff_policy` threads through `build_anthropic_prompted_completion_service` unchanged (both the real-policy-supplied and defaulted-`None` cases); the real composition root, reading real configuration, wires a real `BackoffPolicy` into the real `DispatchingLLMGateway`.
- **All three of llm_gateway.md §3's named Retry & Fallback Manager pieces are now real**: chain traversal, circuit breaking, and backoff. Still deliberately narrow: no provider health beyond the breaker's own binary signal, no experiment pinning, no budgets, no full §10 Error Taxonomy (retriable/non-retriable classification, `retry_after` extraction) — every `LLMProviderError` is treated uniformly by all three mechanisms, exactly this step's own exclusions.
- `mypy --strict` (225 source files), `ruff check`, `ruff format --check` all clean. ### Stage B – The LLM Gateway's Error Taxonomy (llm_gateway.md §10)

- **New `ai_os_kernel/llm_gateway/error_taxonomy.py`**: `ErrorCategory` (a `StrEnum` with exactly the four of `error_handling_retry.md` §3's six unified platform-wide categories — `transient`, `permanent`, `infrastructure`, `budget` — an LLM provider failure can ever actually be; `quality` and `security` do not describe anything a provider call can raise), `ErrorClassification` (a `NamedTuple` of `category`/`error_code`/`retriable`), `classify_http_status()` (maps a real HTTP status code onto llm_gateway.md §10's own table, with a safe range-based fallback for undocumented codes — any other 5xx treated as "Server error," any other 4xx as "Invalid request"), and `parse_retry_after_seconds()` (reads a `Retry-After` header's numeric-seconds form; returns `None` for the HTTP-date form or a missing header — a real, documented gap, not a crash). Well-known non-HTTP classifications (`NETWORK_FAILURE`, `CAPABILITY_UNSUPPORTED`, `CHAIN_EXHAUSTED`, `CIRCUIT_OPEN`, `NO_ROUTE`, `NO_PROVIDER`, `MISROUTED`, `NO_PRICING`, `UNPARSEABLE_RESPONSE`) cover every Gateway-internal condition the provider table itself does not name.
- **Chose not to build the platform-wide `AiOsError` hierarchy `error_handling_retry.md` §8 describes** (`AiOsError` -> `TransientError`/`PermanentError`/`QualityError`/`InfrastructureError`/`BudgetExceededError`/`SecurityError`), and explains why: that hierarchy does not exist anywhere in this codebase today (confirmed by a direct search — the only pre-existing `SecurityError` is a standalone Security Manager class, unrelated), and building it would mean reaching into the Workflow Engine, Quality Gate Engine, and Security Manager — all explicitly out of scope for a step scoped to "keep error classification encapsulated inside the LLM Gateway." Instead, `LLMProviderError`/`LLMRefusalError` carry `category`/`error_code`/`retriable`/`retry_after_seconds` fields directly, using error_handling_retry.md §8's own `StructuredError` field names and vocabulary, so a future platform-wide adoption is a natural migration, not a rewrite.
- **`LLMProviderError` gained four new constructor keyword parameters**, all defaulted: `category=ErrorCategory.TRANSIENT`, `error_code="llm.unknown"`, `retriable=True`, `retry_after_seconds=None`. These defaults exactly reproduce every pre-existing raise site's implicit behaviour (retried by backoff, counted by the Circuit Breaker) — this step's own "preserve existing behaviour where no explicit classification applies" requirement, verified by a dedicated test asserting a bare `LLMProviderError("message")`'s defaults. `LLMRefusalError` gained the identical fields, fixed rather than parameterised (a refusal's classification per llm_gateway.md §10's own row — `permanent`/`llm.refusal`/not retriable — never varies).
- **Both real adapters now classify every failure they raise.** `AnthropicAdapter`: `anthropic.APIStatusError` -> `classify_http_status(exc.status_code)` plus `parse_retry_after_seconds(exc.response.headers.get("retry-after"))`; `anthropic.APIConnectionError` -> `NETWORK_FAILURE`; an unmapped `stop_reason` -> `CAPABILITY_UNSUPPORTED`; the pre-flight "wrong provider"/"no pricing" checks -> `MISROUTED`/`NO_PRICING`. `LocalAdapter`: the identical shape over `httpx.HTTPStatusError`/`httpx.TransportError`, plus a malformed/unparseable response body classified `UNPARSEABLE_RESPONSE` (`transient`/`llm.provider_error`/retriable — a judgement call reasoned through in this step's own design: a malformed response is treated as a possible one-off glitch worth retrying, not assumed permanent). `StaticRouter.resolve()`'s "no configured route" -> `NO_ROUTE`; `DispatchingLLMGateway._call()`'s "no registered gateway"/"circuit open" -> `NO_PROVIDER`/`CIRCUIT_OPEN`; `complete()`'s aggregate "every candidate failed" -> `CHAIN_EXHAUSTED` — an exact match to llm_gateway.md §10's own documented row ("All providers in chain failed | transient | llm.chain_exhausted | Yes, with backoff").
- **Retries occur only when appropriate.** `_call_with_backoff` now checks `exc.retriable` first: a `retriable=False` failure is never retried — abandoned immediately, no delay spent — but the chain still falls back to the next candidate afterward, since a different provider is a different call, not a retry of the same one (a provider-specific auth failure or formatting requirement does not necessarily apply to a different provider or a model with a larger context window). Proven by a dedicated test: a non-retriable failure with `max_attempts=5` still results in exactly one call.
- **Retry-After is honoured.** When a caught failure carries `retry_after_seconds`, the actual delay is `max(policy.delay_seconds(...), exc.retry_after_seconds)` — never less than what the provider explicitly asked for. Proven end to end with a real 429 response carrying a real `Retry-After` header (both adapters) and, at the dispatcher level, with a recording `asyncio.sleep` stand-in proving the provider's hint wins over the policy's own, much smaller computed delay.
- **Circuit Breakers respond appropriately.** `_call()` now only calls `record_failure` when `exc.category in (TRANSIENT, INFRASTRUCTURE)` — a `permanent` failure (the caller's own malformed request, an unsupported capability) no longer opens the circuit, since it is not evidence the *provider* is unhealthy. `infrastructure` (e.g. an auth failure) still counts — repeated authentication failures are a real signal something about this provider's own configuration is broken. Proven by three dedicated tests: a permanent failure records nothing beyond `is_available`; an infrastructure failure records a failure; an unclassified (default) failure still records one too, preserving pre-Error-Taxonomy behaviour exactly.
- **New `tests/unit/kernel/llm_gateway/test_error_taxonomy.py`** (16 tests): `classify_http_status` against every documented code plus undocumented-code fallback ranges; `parse_retry_after_seconds` for the numeric form, a missing header, and the (unsupported) HTTP-date form. **New `tests/unit/kernel/llm_gateway/test_errors.py`** (4 tests): `LLMProviderError`'s defaults, an explicit classification, a `retry_after_seconds` hint, and `LLMRefusalError`'s fixed classification.

### Stage B – The Policy & Budget Enforcer's First Real Slice (llm_gateway.md §3/§9)

- **New `ai_os_kernel/llm_gateway/budget_enforcer.py`**: a `BudgetEnforcer` Protocol (`is_within_budget(scope) -> bool`, `record_spend(scope, cost_usd)`) and one real implementation, `PerAliasBudgetEnforcer` — cumulative spend per scope, held in a plain `dict`, lost on process restart (the identical, deliberate scope limit `InMemoryCircuitBreaker` already documents, for the identical reason: no second, real, persisted implementation is imminent yet, ADR-0004).
- **Scoped by `model_alias`, not by workflow, and explains why.** llm_gateway.md §9's own table names a *workflow* cost ceiling, but `LLMRequest`'s own reduced-contract docstring already excludes workflow correlation and budget fields ("belonging to explicitly deferred subsystems"), and `DispatchingLLMGateway` — the enforcement point this step's own approved framing requires ("keep error classification encapsulated inside the LLM Gateway," the identical spirit for policy/budget) — only ever sees an `LLMRequest`. Extending that contract to carry workflow correlation would be Context Manager/Workflow Engine territory, explicitly out of scope ("do not redesign the LLM Gateway"). `model_alias` is the one caller-facing correlation key already on every request (ADR-0002); a per-alias ceiling is also genuinely useful in its own right, not just an approximation of the documented ceiling — different aliases already represent different cost/quality tiers (`fast-cheap` vs `reasoning`), so capping each independently is real budget governance.
- **Reuses cost accounting the provider adapters already produce — no new estimation logic.** Every real `LLMResponse` already carries an honest `usage.cost_usd` (computed from configured pricing); the enforcer only accumulates that already-real number per alias and compares it to a ceiling. No pre-flight cost guess (would need a real tokenizer, which §12 forbids approximating) — an honest characteristic, documented rather than worked around: one real call's cost can push cumulative spend past the ceiling before the *next* call is refused, since there is no speculative estimate to refuse a call on in advance.
- **`DispatchingLLMGateway` gained one new, optional, defaulted-`None` constructor parameter: `budget_enforcer`.** Checked first in `_call()` — ahead of the Circuit Breaker, since a policy/budget gate takes priority over a resilience mechanism — raising a classified `ErrorCategory.BUDGET`/`llm.budget_exceeded`/not-retriable `LLMProviderError` if the alias is already over its ceiling. Every real success reports `response.usage.cost_usd` back to it. Every existing caller/test that never passes it gets byte-for-byte identical behaviour.
- **A budget failure never triggers a fallback attempt — the one new, genuinely different behaviour this step adds to `complete()`'s own chain-walking logic.** Every other category (including the aggregate `llm.chain_exhausted`) still falls back to the next candidate on any `LLMProviderError`; budget is the sole exception, because a ceiling is scoped to the alias itself, not to whichever provider would serve it — every candidate in the chain would share the identical verdict, so falling back could never be the fix. Proven by a dedicated test using two candidates, both wired to a gateway that raises `AssertionError` if ever called, confirming neither is attempted once the alias is over budget.
- **A budget failure is also never retried by backoff** — already true for free, since it is constructed with `retriable=False`, exercising the identical Error-Taxonomy-driven gate the previous step built, not new logic.
- **`kernel/bootstrap.py`** constructs one real `PerAliasBudgetEnforcer` (`_BUDGET_CEILING_USD = Decimal("10.00")`, the identical named-constant carve-out the Circuit Breaker/backoff constants already use — a placeholder safety ceiling, not a tuned production value) and passes it to `build_anthropic_prompted_completion_service`, which threads it into `DispatchingLLMGateway` alongside the Circuit Breaker and backoff policy. `build_anthropic_prompted_completion_service` itself gained the identical defaulted-`None` `budget_enforcer` parameter, threaded through unchanged.
- **New `tests/unit/kernel/llm_gateway/test_budget_enforcer.py`** (7 tests): an unseen alias is within budget; spend below/at/above the ceiling; spend accumulates across records; aliases tracked independently; constructor validation (`ceiling_usd <= 0` raises `ValueError`).
- **`test_dispatching_gateway.py` extended** (7 tests): no enforcer configured never blocks a call; a within-budget call succeeds and records its spend; a call that pushes spend over the ceiling blocks the *next* one (not itself); a budget failure never falls back (two unreachable-gateway candidates, neither called); a budget failure is never retried by backoff; budgets are tracked independently per alias. **`test_prompted_completion.py`/`test_bootstrap.py` extended**: `budget_enforcer` threads through unchanged (real-supplied and defaulted-`None` cases); the real composition root wires a real `PerAliasBudgetEnforcer`.
