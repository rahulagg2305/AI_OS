### Stage A – `governance.audit_log` Table (Schema and Migration Only)
- **New `kernel/src/ai_os_kernel/persistence/governance_schema.py`** (a new module, not added to the existing `persistence/schema.py`): `governance.audit_log`, column-for-column per data_model.md §9.1 — `audit_id` PK, `seq` (auto-incrementing, unique), `event_type`, `principal_id`, `principal_type`, `resource_type`/`resource_id` (nullable), `outcome`, `detail` (jsonb), `trace_id` (nullable), `prev_hash`/`row_hash`, `occurred_at`. No writer — schema and migration only, exactly as approved; nothing computes `row_hash`/`prev_hash` or writes a row yet.
- **Kept in its own module and schema (`governance`), not folded into `persistence/schema.py` (`workflow`)**: audit is a genuinely distinct bounded context from workflow state, and `persistence/schema.py`'s own docstring already scopes itself to "workflow-state persistence." `kernel/alembic/env.py`'s `target_metadata` is now a list of both modules' `MetaData` objects — Alembic has supported a sequence there since well before the installed version (1.18.5), so both remain live autogenerate-diff targets without merging two schemas into one `MetaData`.
- **`seq`'s documented type is `bigserial`**, implemented as a SQL-standard `GENERATED ... AS IDENTITY` column (`sa.Identity()`) rather than Postgres's legacy `BIGSERIAL` pseudo-type — both produce an auto-incrementing, sequence-backed bigint with identical insert behaviour; `IDENTITY` is what current Postgres/SQLAlchemy documentation recommends for new schemas. Verified directly: two inserts without specifying `seq` got strictly increasing values, and a hand-supplied duplicate `seq` was rejected by the `UNIQUE` constraint.
- **`outcome` gets a `CHECK` constraint; `event_type` does not** — the same reasoning already applied twice (`workflow_instances.status`/`approvals.status` vs. `workflow_steps.status`/`workflow_events.event_type`): §9.1 gives `outcome` an explicit four-value list (`allowed`/`denied`/`success`/`failure`), but lists `event_type` examples ending in an ellipsis — an explicitly open-ended set, not a closed one to enforce.
- **No foreign key**, unlike every `workflow`-schema table added so far: §9.1 does not scope this table to workflow instances at all — `resource_type`/`resource_id` is a loose, polymorphic pointer (auth, secrets, packs, sandboxes, git, not only workflows), so there is no single table it could reference.
- **Two deferrals carried over from the identical `workflow_events` precedent, not newly invented:** `UPDATE`/`DELETE` revocation for "the application role" (no such role exists yet) and the scheduled hash-chain verification job (data_model.md §9.1 — no worker process framework exists yet to run it in).
- 4 new/changed integration tests in `tests/integration/persistence/test_migrations.py`: the up/down/up round-trip test now also asserts the `governance` schema and its one table appear and disappear correctly; the documented columns/PK/`outcome` `CHECK` constraint are all present; the `CHECK` constraint genuinely rejects an invalid `outcome` value; `seq` auto-increments across inserts and its `UNIQUE` constraint genuinely rejects a hand-supplied duplicate.
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite: **183 tests passing** (132 unit + 51 integration).

### Stage A – `governance.config_changes` Table (Completes Governance Schema §9)
- **`governance_schema.py`**: added `config_changes`, column-for-column per data_model.md §9.2 — `change_id` PK, `config_key`, `old_value_digest`, `new_value_digest`, `changed_by`, `reason`, `changed_at`. In the same module as `audit_log`, same `governance` `MetaData`; this is the second and last table §9 documents, so the module docstring's "later work" note about it is now removed — `governance` schema §9 is complete. No writer — schema and migration only, exactly as approved.
- **No `CHECK` constraint and no foreign key, unlike `audit_log`**: every column here is a plain scalar (no `jsonb`, no enum-like column with a documented value list), so there is nothing to constrain that way; and, for the same reason `audit_log` has none, nothing scopes a configuration key to one specific table.
- **Nullability reasoned, not invented, since §9.2 marks no column nullable**: `old_value_digest` is nullable for a config key's first-ever value (no prior value to digest); `new_value_digest` is nullable when a change removes a key entirely (no new value to digest) — an "update" row has both. `config_key`/`changed_by`/`reason`/`changed_at` are `NOT NULL`: every governance-relevant change has a key, an actor, a recorded reason (the same "every record of this kind must carry a reason" rule already enforced for `workflow_instances`' `state.transitioned` event), and a time.
- Two indexes beyond what §9.2 explicitly lists (no "Indexes:" line exists for it either): `config_key` (the natural "history of changes to this key" query) and `changed_at DESC` (mirrors every other table's own recency index).
- **Migration `0005_governance_config_changes.py`**: does not create or drop the `governance` schema itself — `0004_governance_audit_log.py` already owns that; this migration only adds/drops its own table.
- 2 new integration tests in `tests/integration/persistence/test_migrations.py`: the documented columns/PK are all present; a `NULL` `old_value_digest` (a config key's first-ever value) and a `NULL` `new_value_digest` (a key's removal) are both genuinely accepted, proving the nullability reasoning is correct, not just assumed. `_EXPECTED_GOVERNANCE_TABLES` (used by the up/down/up round-trip test) now includes `config_changes`.
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite: **185 tests passing** (132 unit + 53 integration).

Renamed to `0006_platform_outbox_idempotency` (32 characters, at the limit) and re-verified the full up/down/up cycle actually applies.
- **No writer for either table**: `event_outbox` is ADR-0012's transactional outbox, but the Event Bus itself (in-process pub/sub, outbox relay) doesn't exist yet; `idempotency_keys` has no writer because no HTTP route yet needs idempotent-replay of a mutating request.

### Stage A – `trace.artifacts` and `trace.links` (Schema and Migration Only)
- **New `kernel/src/ai_os_kernel/persistence/trace_schema.py`**, mirroring `governance_schema.py`/`platform_schema.py`'s introduction exactly: its own `MetaData` (schema `trace`), combined into `kernel/alembic/env.py`'s `target_metadata` list (now four schemas: `workflow`, `governance`, `platform`, `trace`). `artifacts` — `artifact_key` PK, `artifact_type`, `external_id`, `title`, `location`, `version` — and `links` — `link_id` PK, `source_key`, `relationship`, `target_key`, `confidence`, `created_by`, `created_by_type`, `created_at`, `closed_at` (nullable) — both column-for-column per data_model.md §8.
- **Four `CHECK` constraints, one per documented closed value list**: `artifacts.artifact_type` (ten values), `links.relationship` (seven), `links.confidence` (three), `links.created_by_type` (three) — the same "canonical list is documented, so enforce it" reasoning already applied throughout `workflow`/`governance`.
- **`links.source_key`/`target_key` get real foreign keys to `artifacts.artifact_key`** — the first departure from the "no FK" pattern every `governance`/`platform` table followed. Those tables had no single natural target (polymorphic or unscoped pointers); here, a traceability link's source and target are unambiguously artifact keys, and §8 says impact analysis walks recursive CTEs over `links` — a link pointing nowhere real would silently corrupt that traversal.
- **The documented `UNIQUE (source_key, relationship, target_key) WHERE closed_at IS NULL` rule is a partial unique index** (`sa.Index(..., unique=True, postgresql_where=...)`), not a plain `UniqueConstraint` — standard SQL `UNIQUE` constraints cannot carry a `WHERE` clause. This is what lets the same triple be closed and later re-asserted without colliding with its own closed history, while still forbidding two simultaneously open links for one triple. Verified behaviorally, not just structurally: inserted one open link, confirmed a second open link for the identical triple is rejected, then closed the first and confirmed a new open link for the same triple is accepted.
- **Nullability**: only `closed_at` is nullable (§8 marks it so explicitly — the same "explicit `NULL` is the only nullability signal" convention already followed for `governance`/`platform`); every other column in both tables is `NOT NULL`.
- **No writer**: no Traceability Engine exists yet to run the recursive-CTE impact analysis §8 describes, and nothing writes a traceability link yet either.
- 4 new integration tests in `tests/integration/persistence/test_migrations.py`: documented columns/PK/`CHECK` constraints for both tables; the foreign key genuinely rejects a link naming a nonexistent artifact; the partial unique index genuinely allows reopening a closed triple while rejecting a second simultaneously-open one. `_EXPECTED_TRACE_TABLES` (used by the up/down/up round-trip test, now also asserting the `trace` schema itself appears/disappears correctly) is `{"artifacts", "links"}`.
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite: **192 tests passing** (132 unit + 60 integration).

### Stage A/B – `workflow_instances.run_manifest_id` Foreign Key Retrofit
- **New `kernel/src/ai_os_kernel/persistence/cross_schema_foreign_keys.py`**: attaches the foreign key `persistence/schema.py` has deferred since the baseline migration — `workflow_instances.run_manifest_id` → `evaluation.run_manifests.run_manifest_id` (data_model.md §4.1: "FK → `evaluation.run_manifests`"). Both prerequisites already existed before this step: the column (nullable, since the first migration) and the target table (`evaluation.run_manifests`, previous step).
- **Why a new module rather than an inline `sa.ForeignKey(...)` in `schema.py`**: `evaluation_schema.py` already imports `workflow_instances` from `schema.py` (for its own `run_manifests.workflow_id` FK, previous step). Having `schema.py` import `evaluation_schema.py` back, at module level, to reach a real `run_manifests.c.run_manifest_id` `Column` object, would be a genuine circular import — confirmed empirically before writing any code (a standalone script reproducing the two-`MetaData` shape) that a plain **string**-based cross-`MetaData` `ForeignKey` (e.g. `"evaluation.run_manifests.run_manifest_id"`) is not a viable escape hatch either: SQLAlchemy raises `NoReferencedTableError` the moment anything compiles or resolves it, because string-form FK resolution only ever searches the *referencing* column's own `Table.metadata.tables`, never a different `MetaData` object. A real `Column` object reference (not a string) is required for it to compile, and only one of the two modules can safely import the other's real object without a cycle — `evaluation_schema.py` already claimed that direction.
- **The module is a standalone composition step**, imported by neither `schema.py` nor `evaluation_schema.py`, so importing it is never itself part of any cycle: `register_workflow_run_manifest_foreign_key()` is called once from `kernel/alembic/env.py`, after all six schema modules' `MetaData` objects are already imported — mirroring the explicit, idempotency-guarded `configure_tracing()`/`configure_metrics()` composition calls already established in `bootstrap.py`. - **`catalog_schema.py`**: `workflow_definitions`' primary key changed from single-column `definition_id` to composite `(definition_id, version)`, exactly the documented resolution of the `definition_id` versioning ambiguity. New migration `0021_catalog_wf_definitions_pk.py`: a single, atomic `ALTER TABLE ... DROP CONSTRAINT workflow_definitions_pkey` / `ADD CONSTRAINT pk_workflow_definitions PRIMARY KEY (definition_id, version)` pair — not an expand/migrate/contract sequence, because this table has no writer anywhere in this codebase (no live data to migrate), and the change is safe by construction regardless: a single-column `definition_id` primary key already guarantees uniqueness on that column alone, and a value unique on one column is trivially still unique on that column plus another, so no row that could exist under the old constraint could ever violate the new, strictly broader composite one. Fully reversible (downgrade restores the original single-column constraint by name).
- **The paired foreign-key retrofit — `workflow_instances.definition_id`/`definition_version` → `catalog.workflow_definitions (definition_id, version)` — was implemented, tested, and then deliberately reverted.** This is the one significant finding of this step, surfaced per this session's "stop and report if something is inconsistent" rule:
  - The composite FK was straightforward to express in SQLAlchemy (`sa.ForeignKeyConstraint` on `workflow_instances`, importing the real `workflow_definitions` `Column` objects directly from `catalog_schema.py` — safe, one-directional, no circular import, since `catalog_schema.py` never imports back).
  - Before committing to it, the full test suite was run with the FK in place. Result: **37 of 39 tests in `tests/integration/workflow_engine/` failed** with `ForeignKeyViolationError` — including the most basic instance-creation test. Every failure traced to the same cause: `catalog.workflow_definitions` has no writer anywhere in this codebase (`ManifestLoader` only reads/validates a manifest file in memory; nothing persists one), while `SqlWorkflowInstanceRepository.create()` — real, already-accepted application code that has worked this way since the very first migration — writes a `workflow_instances` row with an arbitrary `definition_id`/`definition_version` pair unconditionally, with no matching catalog row ever able to exist.
  - This is categorically different from every other FK retrofit done in this implementation log (`run_manifest_id`, `experiment_id`, `agent_id`/`prompt_id`): those all pointed at tables with no existing write path to break. This one points at a column pair that real, tested, working code writes to constantly, with no corresponding writer for the referenced side. Adding it would not be a schema-only change — it would silently and immediately break the Workflow Engine's ability to create any instance at all, a functional regression far outside "schema and migration only" and outside this step's approved scope (no agent/tool/LLM/runtime changes).
  - **Reverted**: the `sa.ForeignKeyConstraint` was removed from `workflow_instances` in `schema.py`, and the migration that would have added it (`0022_workflow_definition_fk.py`) was deleted rather than merged, after confirming via a second full test run that reverting restores all 39 Workflow Engine tests to passing.
  - Both `schema.py` and `catalog_schema.py`'s docstrings were updated to record this precisely: the versioning ambiguity that used to block this FK is resolved, but the FK is now blocked by a *different*, newly-discovered reason (no catalog writer, no instance-creation-time validation) — not silently left looking "still pending the old reason."
- **A separate, unrelated documentation inaccuracy was found and corrected while investigating**: earlier reports (and both modules' own docstrings, until this step) described the deferred FK as owed to "`workflow_instances`/`workflow_events`." Checked directly against data_model.md §4.2 while implementing this step: `workflow_events` has never had a `definition_id` or `definition_version` column at all. Only `workflow_instances` ever needed this foreign key. Both docstrings now say so explicitly.
- 2 new integration tests in `tests/integration/persistence/test_migrations.py`: `test_catalog_workflow_definitions_composite_primary_key` (two rows sharing the same `definition_id` with different `version` values are both accepted — the entire point of this migration — while a genuine duplicate `(definition_id, version)` pair is still rejected); the existing `test_catalog_workflow_definitions_matches_the_documented_columns` updated to assert the composite PK. Round-trip test now covers 21 migrations.
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite: **231 tests passing** (133 unit + 98 integration — includes all 39 Workflow Engine integration tests passing, confirming the revert is complete and correct). Combined unit+integration coverage: **96.31%**.

### Stage A/B – Minimal `catalog.workflow_definitions` Writer + `workflow_instances` Composite FK (Now Safely Enforced)
- **New `kernel/src/ai_os_kernel/workflow_engine/definition_catalog.py`**: `WorkflowDefinitionCatalog` (`Protocol`) + `SqlWorkflowDefinitionCatalog`, the only implementation. `register(definition, pack_id)` is an **upsert keyed on `(definition_id, version)`** (`ON CONFLICT ... DO NOTHING`, not `DO UPDATE` — data_model.md §5's "versions are immutable" means a second registration of an already-recorded version is a no-op, not a silent overwrite). Deliberately **not** a Capability Manager or Manifest Loader extension — the smallest seam that lets `WorkflowInstanceService` register a definition before creating an instance that references it.
- **Column mapping from `WorkflowDefinition` to the five columns this writer supplies** (`definition_id`/`version` are the PK): `pack_id` — not a field on `WorkflowDefinition` at all (a workflow file has no notion of which pack it belongs to; that's manifest-level knowledge) — supplied explicitly by the caller. `inputs_schema`/`outputs_schema` — `definition.inputs`/`definition.outputs` directly. `graph` — `model_dump(mode="json", by_alias=True, exclude={"id","version","inputs","outputs"})`: everything the definition validated, minus what already has its own column — the least-invented reading that keeps the durable catalog record complete (nothing dropped, which matters for the reproducibility this table exists for, ADR-0022). `declared_permissions` — `WorkflowDefinition` has no permissions field of its own today; stored as an empty JSONB array rather than guessed from `agents`/`requiredTools` component references. `validated_at` — application-supplied (no server default), the same reasoning already applied to every other "when did this actually happen" column in this persistence layer.
- **The `workflow_instances` → `catalog.workflow_definitions` composite foreign key is now enforced** (new migration `0023_workflow_definition_fk.py`) — the same constraint attempted and reverted two steps ago. It is safe now, verified by actually running the full test suite with it in place (not assumed): all 39 `tests/integration/workflow_engine/` tests pass, because `WorkflowInstanceService.create_instance()` now registers the definition, every call, before the instance insert ever runs.
- **`WorkflowInstanceService` changes**: constructor takes a third dependency, `WorkflowDefinitionCatalog`; `create_instance()` takes a new required `pack_id: str` (validated via new `validate_pack_id`, mirroring `validate_principal`), and calls `definition_catalog.register(...)` before `repository.create(...)`. The two writes are deliberately **not** one atomic transaction — registration's own upsert is idempotent, so a registration that commits and an instance-creation that then fails for an unrelated reason leaves nothing incorrect behind, unlike `workflow_instances`/`workflow_events` (data_model.md §4, which does require one transaction). New `WorkflowDefinitionRegistrationError` (mirrors `WorkflowInstanceCreationError`) wraps a registration failure cleanly, never a bare stack trace — satisfying the approved shape's "FK violation / missing definition must fail cleanly" requirement.
- **Every caller of `WorkflowInstanceService`/`create_instance()` across the codebase was updated** — 2 unit test files (`test_service.py`: new `_FakeDefinitionCatalog`, 2 new tests proving registration happens before the repository call and that a registration failure stops instance creation; `test_advance_runner.py`: a minimal never-exercised fake to satisfy the constructor) and 8 integration test files (7 needed `pack_id`/`SqlWorkflowDefinitionCatalog` added to their own `create_instance`/`WorkflowInstanceService(...)` call sites; `test_state_transitions.py` needed no code change, since it calls the repository directly). A new `tests/integration/workflow_engine/conftest.py` autouse fixture ensures the one shared test definition (`se.product_creation`/`1.0.0`) is registered before every test in that package — idempotent, so it doesn't matter whether a given test goes through the service (which would also register it) or the repository directly (which would not).
