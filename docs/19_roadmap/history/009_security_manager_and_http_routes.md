# AI_OS Implementation History — Security Manager and HTTP Routes

**Milestone:** The minimal Security Manager slice, three authenticated read-only HTTP routes, and the paginated `GET /api/v1/workflows` route.

Split out of the original single `implementation_status.md` on 2026-07-28 — content preserved verbatim, in original order. See `docs/19_roadmap/history/INDEX.md`.

---

### Stage A – Minimal Security Manager Slice: Bearer-Token Auth + One Permission Check, Fronting `POST /api/v1/workflows`
- **New `ai_os_kernel.security_manager` package** (replacing the docstring-only Stage-C placeholder scaffolded at Step 1): `models.py` (`Principal`, `PrincipalType`, `SecurityContext`), `permissions.py` (`permissions_for_roles()` and the `_ROLE_PERMISSIONS` table), `token_verifier.py` (`TokenVerifier` Protocol, `JWTBearerTokenVerifier`, `build_jwt_bearer_token_verifier()`), `dependencies.py` (`require_permission()`, the FastAPI dependency chain).
- **`SecurityContext`/`permissions_for_roles()` deliberately model only the principal's own role-derived permissions**, not ADR-0023's full `principal ∩ workflow ∩ agent ∩ tool` monotonic-narrowing chain — that needs manifest-declared permissions on workflows/agents/tools, which is Capability Manager territory not yet built. The role table itself is authentication_authorization.md §4.2's documented five roles, reduced to the two permissions (`workflow:read`, `workflow:start`) this step actually enforces, not the SDK's full closed vocabulary — deliberately not invented ahead of a route that would need it.
- **`JWTBearerTokenVerifier` is bearer-token authentication, not full OIDC.** It verifies a JWT's HS256 signature and expiry against a pre-shared secret resolved through the existing `SecretProvider` seam (`secret://env/security/jwt-signing-key`, the identical pattern `_ANTHROPIC_API_KEY_SECRET_REFERENCE` already established) — a real, credible bearer-token mechanism, just not backed by a live identity provider (no JWKS fetch, no issuer/audience validation). This is the "clean minimal auth boundary that does not violate the architecture and can later be replaced by full OIDC without rewriting callers" the approved framing's own escape hatch anticipated: every caller depends on the `TokenVerifier` Protocol, not `JWTBearerTokenVerifier` — a real OIDC implementation later replaces one class, not any call site.
- **`require_permission()` fails closed at every stage**: no bearer token → `401`; a token that fails signature/expiry/claim verification → `401`; a verified principal lacking the required permission → `403`; **no signing secret configured at all → `503`**, deliberately distinct from `401` — the caller did nothing wrong, the service itself cannot authenticate anyone. Every 401/403 decision is logged (`security_manager.authentication_failed`/`security_manager.authorization_denied`) — real-but-partial auditability, not yet a `governance.audit_log` write (that table still has no writer at all, an unchanged, already-documented gap).
- **`kernel/bootstrap.py`** gained `_build_token_verifier()`, called unconditionally in `_lifespan` (authentication needs neither the database engine nor the LLM secret, so it does not wait on either), attaching the result — or `None`, on a missing/unresolvable secret — as `app.state.token_verifier`. `_JWT_SIGNING_KEY_SECRET_REFERENCE` follows the same named-constant, `secret://env/...`-reference convention as `_ANTHROPIC_API_KEY_SECRET_REFERENCE`.
- **New `ai_os_kernel/routes/workflows.py`**: `POST /api/v1/workflows`, requiring `workflow:start`, then calling the unchanged `app.state.trigger_prompted_agent_workflow` — the first real HTTP route in this codebase to reach the Workflow Engine. Deliberately narrower than api_architecture.md §6.1's documented contract: no `definition_id`/`definition_version`/`experiment_id` fields (there is exactly one real workflow definition), no `Idempotency-Key`, and `200` with a reduced, JSON-safe `StartWorkflowResponse` (`workflow_id`, `outcome`, `iterations`, `error`) instead of `202` fire-and-forget — since the trigger still runs the instance to completion synchronously (no worker loop exists yet), returning `202` for already-finished work would misrepresent what happened. `StartWorkflowResponse` is deliberately not the internal `WorkflowRunResult` itself, since that model's `last_instance`/`error` fields carry shapes (a full `WorkflowInstance`, a raw exception object) not meant to cross the API boundary unfiltered.
- **New `pyjwt>=2.9,<3.0` dependency** (`kernel/pyproject.toml`, `uv.lock` regenerated) — the first dependency this Security Manager slice needed; no other new third-party dependency was required.
- **New `tests/unit/kernel/security_manager/`** (17 tests: `test_models.py`, `test_permissions.py`, `test_token_verifier.py`) and **`tests/unit/kernel/routes/test_workflows.py`** (6 tests) — no real database, no real network, no real signing secret needed beyond an in-test constant: permission-table correctness for every documented role, JWT verification edge cases (wrong signature, expired, missing `sub`, unknown `principal_type`, malformed token), and the full 401/403/503 decision tree exercised against a real `bootstrap.build_app()` with `AIOS_DATABASE_URL` deliberately left unset.
- **New `tests/integration/test_workflows_route.py`** (2 tests, real Postgres via `testcontainers`, no Anthropic credential): an authorized (`workflow:start`) request genuinely reaches the real Workflow Engine through the real composition root and gets back a real, structured `failed` outcome — the demo agent isn't registered without a real LLM secret — proving the security boundary does not block or distort a legitimate request while remaining fully deterministic; an unauthorized (`viewer`) request is rejected with `403` before the engine is ever touched.
- **New opt-in `tests/integration/test_workflows_route_live.py`** — skipped unless `AIOS_SECRET_LLM_ANTHROPIC_API_KEY` is set: seeds a real `catalog.prompts` row and drives the demo workflow to a genuine Anthropic-backed `completed` result through the real HTTP route with a real bearer token — the full stack, end to end, for the first time.
- **Still deliberately narrow**: no full OIDC, no service-account API-key mechanism as a distinct concept, no ADR-0023 monotonic-narrowing chain beyond the principal's own permissions, no role assignment/administration, no `governance.audit_log` writer, no rate limiting, no RFC 9457 `application/problem+json` error bodies (401/403/503 responses here are FastAPI's default `{"detail": ...}` shape, not yet the documented Problem Details format — a distinct, not-yet-attempted gap, noted honestly rather than invented away), and every other api_architecture.md §6 endpoint still does not exist.
- `mypy --strict` (204 source files), `ruff check`, `ruff format --check` all clean on first attempt (after one expected `B008` false-positive on FastAPI's own `Depends(...)` idiom, suppressed with `# noqa: B008` and an explanatory comment, mirroring the existing `# noqa: S105` precedent for a different well-understood linter false positive). Full suite: **402 tests passing, 6 skipped** (six opt-in live tests, skipped by design without credentials). Combined unit+integration coverage: **97.17%** (`security_manager/`: 100% across every new file; `routes/workflows.py`: 100%; `bootstrap.py`: 95%).

### Stage A – Three Authenticated Read-Only Workflow Routes: `GET /workflows/{id}`, `.../steps`, `.../events`
- **`ai_os_kernel/routes/workflows.py`** gained `get_workflow`, `get_workflow_steps`, `get_workflow_events` — `GET /api/v1/workflows/{id}`, `.../steps`, `.../events` (api_architecture.md §6.1). Each calls the already-built `WorkflowInstanceRepository.get_instance()`/`list_steps()`/`list_events()` unchanged; no new Workflow Engine code was needed, exactly as the approved framing's "reuse existing Workflow Engine read accessors / repositories" bullet specified.
- **Gated on `workflow:read`**, already modelled (and already granted to every role, including `viewer`) by the previous step's `permissions_for_roles()` table — no new Security Manager code, no new permission, no new role.
- **`kernel/bootstrap.py`**: `_lifespan` now also attaches `app.state.workflow_instance_repository = SqlWorkflowInstanceRepository(engine)` alongside the existing `agent_registry`/`trigger_prompted_agent_workflow` assignments, when a real engine is available — a plain, stateless wrapper over the same engine, safe to construct separately from the `WorkflowInstanceService` `_build_workflow_trigger` already builds internally for writes.
- **Response shapes are the real domain models, unfiltered**: `WorkflowInstance`, `WorkflowStepRecord`, `WorkflowEventRecord` are returned directly as `response_model`s — unlike the write route's `StartWorkflowResponse`, none of these three carry an internal-only field (a raw exception, a full nested object) that needs projecting before crossing the API boundary, so no new DTO was invented (ADR-0004: a seam is justified only when it does something a direct return does not).
- **A `workflow_id` naming no real instance returns `404` from all three routes** — each first calls `get_instance()` and raises `404` before touching `list_steps()`/`list_events()`, so a workflow that never existed is distinguishable from one that exists with zero steps or events (which would otherwise both return an empty `200 []` from `list_steps()`/`list_events()` alone, since neither method checks instance existence itself).
- **Dependency ordering matters and is now explicit**: the `workflow:read` permission check is declared *before* the repository-availability check in each route's parameters, so FastAPI resolves authentication/authorization first — an unauthenticated or unauthorized request gets `401`/`403` even when the Workflow Engine itself is unavailable, never a `503` that would leak "is the backend even up" information ahead of a security decision. (Caught by the first test run this step — the two checks were originally declared in the opposite order, which leaked `503` instead of `401`/`403`; reordered before writing further tests.)
- **Deliberately narrower than api_architecture.md §6.1's documented shape**: the events route returns the complete list, not the cursor-paginated (`limit`/`cursor`/`next_cursor`) shape §9 documents for collections generally. Building real cursor pagination for one endpoint, ahead of every other collection endpoint (`GET /workflows`, `/approvals`, `/experiments`, ...) that would need the identical mechanism, is a distinct, later step — not attempted here, and every one of those other collection endpoints still does not exist regardless.
- **New `tests/unit/kernel/routes/test_workflows.py` additions** (9 more tests, parametrized across all three routes — 24 total in the file now): no bearer token → `401`; a role granting nothing → `403`; a valid, permitted request with no real database configured → `503` "workflow engine is not available" — all with no real database and no real network.
- **New `tests/integration/test_workflows_route.py` additions** (2 more tests, real Postgres via `testcontainers`, no Anthropic credential — 4 total in the file now): one drives a real instance to a genuine `completed` state using a substituted Echo-backed `PromptedAgent` (the identical technique `test_bootstrap_workflow_trigger.py` uses), then reads it back exclusively through the three authenticated HTTP routes, asserting the real persisted status, the real step's `agentId`/`outputs`, and the real event log (`workflow.started`, `workflow.completed` both present); the other asserts all three routes return `404` for a `workflow_id` that never existed.
- **Still deliberately narrow**: no `GET /api/v1/workflows` (list, cursor-paginated), no cursor pagination on the events route, no filtering (`status`, `created_after`, ...), no Dashboard, and every other api_architecture.md §6 endpoint still does not exist — exactly the framing's own "no full API surface expansion beyond these reads" constraint.
- `mypy --strict` (204 source files), `ruff check`, `ruff format --check` all clean. Full suite: **413 tests passing, 6 skipped** (six opt-in live tests, skipped by design without credentials). Combined unit+integration coverage: **97.25%** (`routes/workflows.py`: 100%).

### Stage A – `GET /api/v1/workflows`: Cursor-Paginated Collection Endpoint Over Every Instance
- **`WorkflowInstanceRepository` gained one new method, `list_instances(*, limit, before=None)`**, implemented in `SqlWorkflowInstanceRepository` alongside `get_instance`/`list_steps`/`list_events` (same "plain, unguarded read" shape) and added to the Protocol every existing fake `WorkflowInstanceRepository` implementation in the unit test suite (`test_advance_runner.py`, `test_service.py`) had to gain a stub for, to stay structurally conformant. Orders newest-first: `created_at` DESC, `workflow_id` DESC — the second column a deliberate tiebreaker for rows sharing one timestamp, using the fact that `workflow_id` is a ULID (data_model.md §2: "sortable, opaque") rather than inventing a new ordering concept. Matches the schema's own pre-existing `ix_workflow_instances_created_at_desc` index — that index was already there, unused until now.
- **`WorkflowListCursor`** (`ai_os_kernel.workflow_engine.repository`) is the keyset *value* — `created_at` + `workflow_id` — as a small frozen Pydantic model. Deliberately not the wire encoding: comparing two keysets is the repository's job (a genuine SQLAlchemy `tuple_(...) < (...)` row-wise comparison, not two independent column filters that could double-count or skip a row), while encoding one into an opaque string for an HTTP response is a transport concern that belongs in `ai_os_kernel.routes.workflows`, not the persistence layer — the same separation `SecurityContext`'s "value vs. wire format" split already established for the Security Manager.
- **`GET /api/v1/workflows`** (`ai_os_kernel.routes.workflows.list_workflows`) requests `limit + 1` rows from the repository — the classic "one extra row, never returned" technique for detecting a next page without a separate `COUNT` query — and returns api_architecture.md §9's documented envelope `{"items": [...], "next_cursor": "…" | null}`. `limit` is validated by FastAPI's own `Query(gt=0, le=100, default=50)` (`422` outside range, no new validation function needed); the cursor is decoded by a small pure `_decode_cursor()`/`_encode_cursor()` pair (base64 + JSON), rejecting anything malformed with `400` before any query runs.
- **Never offset-paginated** — api_architecture.md §9 is explicit that a growing collection makes offsets skip or duplicate rows; every page boundary here is a real row's own keyset position, not a row count.
- **Gated on the existing `workflow:read` permission** — no new Security Manager work, no new role, no new permission, exactly as approved. The permission check is declared before the repository-availability dependency in the route's parameters, the same ordering rule the previous step's own bug fix established, so an unauthenticated/unauthorized request never learns whether the Workflow Engine backend is even up.
- **Deliberately no filtering** — no `status`/`definition_id`/`created_after` query parameters (api_architecture.md §5's own documented filter examples) and no query DSL. The approved framing was a *correct list endpoint*, not search; a filtered list is a distinct, later step layered on the same cursor mechanism, not attempted here.
- **New `tests/unit/kernel/routes/test_workflows_cursor.py`** (5 tests): the cursor codec round-trips, is URL-safe, and rejects garbage input, non-JSON base64, and JSON missing a required field — all pure-function tests, no app, no database.
- **`tests/unit/kernel/routes/test_workflows.py` extended** (7 more tests, 26 total in the file): the three existing 401/403/503 parametrized tests now also cover `GET /workflows` itself; two new tests confirm `limit` outside `1`–`100` returns `422` (using a syntactically-valid-but-never-connected database URL, the same lazy-engine-construction technique `test_bootstrap.py` established, so the repository dependency succeeds and FastAPI's own query-parameter validation is what's actually being exercised, not a race against the 503 unavailable-backend path).
- **`tests/integration/test_workflows_route.py` extended** (2 more tests, real Postgres via `testcontainers`, no Anthropic credential — 6 total in the file now): one drives three real completed instances, then paginates through the entire real collection with `limit=2`, asserting every page respects the limit, the walk terminates, and every created instance appears in the result exactly once (no duplicates, no gaps) — genuine proof the keyset mechanism is correct, not just plausible; the other confirms a malformed cursor returns `400` end to end through the real route.
- **Still deliberately narrow**: no filtering, no free-form search, no `GET /api/v1/workflows/{id}/...` sub-resource pagination (the per-instance `/steps`/`/events` routes remain un-paginated — a single instance's own history is bounded, unlike the top-level collection), and every other api_architecture.md §6 endpoint besides the four workflow routes still does not exist.
- `mypy --strict` (205 source files), `ruff check`, `ruff format --check` all clean. Full suite: **426 tests passing, 6 skipped** (six opt-in live tests, skipped by design without credentials). Combined unit+integration coverage: **97.26%** (`routes/workflows.py`: 100%; `workflow_engine/repository.py`: 95%).
