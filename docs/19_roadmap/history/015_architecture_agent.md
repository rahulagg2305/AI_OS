### Stage B/C – The First Real, Thin Capability Pack: Architecture Agent (Third Increment Under the New Priority)

- **Read `implementation_status.md`, `DOCUMENTATION_INDEX.md`, `capability_pack_contract.md`, `agent_architecture.md`, the manifest schema, and `manifest_schema.md` before writing any code, per this step's own context-discipline requirement — and found real, load-bearing gaps, reported rather than silently built around.** See the three "discoveries" below; none blocked proceeding, since each had a documented, reasoned resolution that respected every existing boundary this step's own framing named.
- **Discovery 1 — the manifest schema requires a real `CapabilityPack` entry point the moment a manifest declares any agent, but no such type exists in this codebase.** `platform_sdk/schemas/manifest.schema.json`'s own `allOf` rule makes `entryPoint` required once `agents`/`workflows` is non-empty (`capability_packs/_template/manifest.yaml`'s own comment already anticipates this exactly). platform_sdk.md §6/§7 documents the real, full `CapabilityPack`/`PackContext`/`PackRegistration`/`HealthReport` shape — but `PackContext` alone names fourteen optional services (a Tool Invoker, Event Bus, Workspace Service, Traceability Engine, Quality Gate Registry, Speech Gateway, and more), almost none of which exist as real Kernel services yet. Building all fourteen would itself be "invented architecture" (stand-in types for services with no real implementation), not a faithful reduction of a real one — so new `ai_os_kernel.capability_manager.pack_contract` implements only what this pack's one agent genuinely needs: `PackContext` (`pack_id`/`pack_version` only), `PackRegistration` (`agents` only, `tools` defaulted empty), `HealthReport` (`status` only), and the `CapabilityPack` Protocol itself — the identical "reduced slice now, additive later" precedent already used for `TraceContext`/`ContextRequest`/`ProviderCapabilities`. `SoftwareEngineeringPack` (`capability_packs/software-engineering/src/ai_os_pack_software_engineering/pack.py`) is a real, correct implementation of this reduced contract — not a stub that lies about what it does, even though nothing calls it yet (see Discovery 2).
- **Discovery 2 — nothing in this codebase automatically installs a pack's manifest into `catalog.agents`/`catalog.tools`, and nothing calls a pack's own `CapabilityPack.activate()`.** `ai_os_kernel.capability_manager.SqlPackLifecycleRepository.register()` only ever writes `catalog.packs`/`catalog.pack_state_transitions` — it never parses `manifest.agents[]`. This is a real, distinct, larger future Capability Manager increment (a real pack installer), not attempted here — this step's own tests seed `catalog.agents`/`catalog.prompts` directly via SQL, mirroring the identical precedent `tests/integration/workflow_engine/test_registry.py` already established for every prior catalog-backed agent/tool row in this project's history. Registration and activation of the pack row itself still goes exclusively through the real `SqlPackLifecycleRepository`, per this step's own approved framing ("no new lifecycle mechanism").
- **Discovery 3 (the step's own named tension) — `EntrypointLoader`'s zero-argument construction and `PromptedAgent`'s real async constructor dependencies are still incompatible, and this step's own approved framing required a decided, recorded resolution, not a silent workaround.** `workflow_engine.prompted_agent`'s own docstring already documented this exact incompatibility and its prior resolution (`InMemoryAgentRegistry`only). **Resolution: a genuinely zero-argument-constructible wrapper that lazily builds its own real `PromptedAgent` on first `execute()` call.** New `ArchitectureAgentEntrypoint` (`agents/architecture.py`): `__init__()` takes no required arguments (satisfying `EntrypointLoader`/`SqlAgentRegistry` unmodified) and does no I/O; `execute()` — the one method that can genuinely `await` — lazily calls `build_anthropic_prompted_completion_service()` (unchanged, the identical real composition `kernel/bootstrap.py` itself already uses) exactly once, guarded by an `asyncio.Lock` so concurrent first calls build exactly one shared `PromptedAgent` instance (proven by a dedicated concurrency test, not asserted by inspection), then delegates to it unchanged. An optional, defaulted-`None` `service_factory` constructor parameter is the only new surface added — production code (`EntrypointLoader.load()`) never supplies it, so the zero-arg boundary is respected, not silently broken; a test supplies a deterministic (`EchoLLMGateway`-backed) factory instead. `output_schema` is a literal copy of `PromptedAgent.output_schema` (`{"content": <string>}`), since this wrapper's real output *is* whatever `PromptedAgent.execute()` returns, unmodified — "reuse, don't reinvent" applied to both the invocation logic and its declared contract.
- **A fourth, related compromise, recorded rather than silently accepted as normal: this pack imports Kernel internals directly.** capability_pack_contract.md's own "Platform Interaction Rules" name the Platform SDK as a pack's only sanctioned interaction surface — but no `ai-os-sdk` package exists yet (kernel's own `pyproject.toml`: "Planned, not yet scaffolded"). `agents/architecture.py` and the pack's own `pyproject.toml` both record this explicitly as a known, temporary compromise that a real Platform SDK migration should resolve later, not a pattern for future packs to copy uncritically.
- **New manifest**: `capability_packs/software-engineering/manifest.yaml` — `metadata.id: software-engineering`, one agent (`architect`, `modelAlias: coding-strong`, a real `entrypoint`/`inputSchema`/`outputSchema`), one prompt declaration (`architecture.propose_design`, `location: prompts/architecture_proposal.md`), `permissions: [llm:invoke]`, `entryPoint: ai_os_pack_software_engineering.pack:SoftwareEngineeringPack`. **Validated for real, not eyeballed**: `ai_os_kernel.manifest_loader.ManifestLoader.load_one()` was run against this exact file and returned successfully; `EntrypointLoader.load()` was run against both the agent's and the pack's own entrypoint strings and both genuinely constructed real objects (`isinstance(agent, Agent)` and the reduced `CapabilityPack` shape both hold).
- **A real second `uv` workspace member, not a documentation-only pack.** `capability_packs/software-engineering/pyproject.toml` (`ai-os-pack-software-engineering`, depending on `ai-os-kernel` directly per Discovery 4) — added to the root `pyproject.toml`'s `[tool.uv.workspace]`/`[tool.uv.sources]`/`ruff`/`mypy` configuration. `uv lock` regenerated (93 packages resolved) and `uv sync --frozen --all-packages` verified against both the latest `uv` (0.11.32) and the CI-pinned `uv==0.5.11`, the identical dependency-change verification discipline every prior step introducing a new dependency has followed. `ai_os_pack_software_engineering` is genuinely `importlib`-importable in this same Python environment — confirmed by direct execution, not assumed.
- **New tests, in three tiers matching what this session's environment can and cannot verify:** `capability_packs/software-engineering/tests/test_pack.py` — **6 tests, genuinely executed, no database, no live LLM call**: `activate()`/`deactivate()`/`health()` are real; `ArchitectureAgentEntrypoint()` constructs with zero arguments and no eager I/O; concurrent first `execute()` calls build exactly one shared service; **the deterministic Echo-backed end-to-end proof this step's own requirement names** — a real `WorkflowStep` of type `agent` genuinely dispatches through the real `AgentStepExecutor` to this pack's real entrypoint, which genuinely renders a real prompt template and completes it via `EchoLLMGateway`, with the rendered content flowing back unmodified; the Pydantic input/output models construct validly. `tests/integration/workflow_engine/test_architecture_agent_pack.py` (new, Kernel-side, Postgres via testcontainers) — a deterministic test that registers+activates the pack through the real `SqlPackLifecycleRepository` and seeds a real `catalog.agents` row, then proves `SqlAgentRegistry.resolve_agent()` genuinely resolves this pack's own entrypoint (the specific tension this step exists to resolve, provable without any live LLM call); an opt-in live test (skipped without `AIOS_SECRET_LLM_ANTHROPIC_API_KEY`, mirroring `test_prompted_agent_live.py` exactly) goes one step further — a real `WorkflowStep`, dispatched through `AgentStepExecutor`/`SqlAgentRegistry`, genuinely completes against the live Anthropic API and returns a real architecture proposal.
- **Still deliberately narrow, exactly per this step's approved scope**: no Build/Test/Documentation Agent, no human-approval gating for a proposed architecture (output capture only), no Tool/Workflow/Quality-Gate/Command declared by this pack, no HTTP route, no `kernel/bootstrap.py` wiring, no automated manifest -> catalog installer, no LICENSE file, no SDK pack contract test suite (it does not exist anywhere in this codebase to run yet).
- `mypy --strict` (260 source files, kernel + this pack together), `ruff check`, `ruff format --check` all clean. Unit suite: **555 passed** (549 Kernel unit tests + 6 new pack tests), zero regressions. **Environment note:** Docker Desktop was unavailable again this session, so `tests/integration/workflow_engine/test_architecture_agent_pack.py` could not be executed live (neither its deterministic-Postgres tier nor its opt-in-live tier, the latter also needing a real Anthropic key almost certainly absent too); verified instead by confirming the file collects and imports cleanly under `pytest --collect-only`, plus the manual `ManifestLoader`/`EntrypointLoader` verification described above, which exercises the same real code paths (manifest parsing, entrypoint construction, `isinstance` checks) this integration test would also exercise.
