### Stage B/C – Delivery Pipeline: Architecture → Build → Test → Documentation Chained Into One Real Workflow (Seventh Increment Under the New Priority — First Complete Product Loop)

- **Read `implementation_status.md`, `DOCUMENTATION_INDEX.md`, `workflow_architecture.md`'s Step Contract section, and the code needed for this step before writing any.** The Step Contract section's own words shaped this step's design directly: its five invocation fields are "never a computed value, a cross-step reference, a template, or conditional logic" — read as ruling out a new `WorkflowStep` field for a cross-step reference, not as ruling out chaining itself (that document's own Context Management section separately, explicitly names "Previous workflow state" as a sanctioned context source, without specifying how it reaches an agent — this step is that "how").
- **New `ai_os_kernel.context_manager.resolvers.WorkflowStepOutputResolver`** — the one genuinely missing piece this step's own approved framing named. A second real resolver for the same "Workflow State" source `context_manager.md` §3 already documents (sibling to `WorkflowStateResolver`, not a new `SourceType`; §5's own `required_context_types` example list already names `previous_outputs` explicitly). Configured with a flat, statically-declared `step_sources: Mapping[str, str | Sequence[str]]` (`{consuming_step_id: source_step_id(s)}` — "this step's input includes the named output of step X," the smallest data structure that says exactly that), reading a named prior step's real, persisted output (`workflow_steps.outputs`, via `WorkflowInstanceRepository.list_steps()`, picking the highest `attempt` for a given step name). Two small, optional per-step knobs, both still flat and statically declared: `field_selectors` (extract one named field verbatim, for a consumer wanting free text fed into a prompt's own `{{context}}` variable) and `output_transforms` (a real, narrow Python callable applied to the merged output before encoding — used exactly once by this pipeline's own composition, never declared inline in any workflow definition file). Returns no items — not an error — for a step absent from `step_sources`, or when a referenced source step has not (yet) produced a real output: the identical "cannot be checked, not an error" shape `WorkflowStateResolver` already established.
- **New `ai_os_pack_software_engineering.pipeline` module and `workflows/delivery_pipeline.yaml`** — the first genuine consumer of the already-real, previously-unused `ai_os_kernel.workflow_engine.loader.WorkflowDefinitionLoader` in this codebase's own history (every prior `WorkflowDefinition` in this project, including `kernel/bootstrap.py`'s own demo, was constructed directly in Python, for the documented reason that no real pack directory existed yet to load one from — one now does). The YAML declares four `agent` steps in order (`architecture`, `build`, `test`, `documentation`), each naming a real, pack-qualified `agentId` (`software-engineering/architect`, etc.). `pipeline.py` owns this pipeline's own configuration of the generic resolver above: `build` reads `architecture`'s own `content` field as free text; `test` reads `build`'s own whole output, enriched with the one deliberate exception — `runCommand = [sys.executable, filePath]`, since the Build Agent's own already-shipped contract has no reason to decide how its own file is run; `documentation` reads **both** `build`'s and `test`'s own outputs merged (`build` first, `test` second — `test`'s own `exitCode` therefore wins over `build`'s own same-named field, a declared merge order, never a computed value), which already contains every field Documentation's own contract needs, with no transform required. `build_pipeline_trigger()` mirrors `kernel/bootstrap.py`'s own `_build_workflow_trigger` shape exactly (create → start → run-to-completion via the existing `WorkflowAdvanceRunner`) — composition only, no new Workflow Engine capability — and lives in the pack, not the Kernel, since every step here needs the pack's own `SqlAgentRegistry`-resolvable agents.
- **A genuine, discovered bug — found by actually running the four-step chain end to end, not by inspection.** `WorkflowStateResolver` has no per-step concept of its own: it unconditionally contributes the workflow instance's own top-level `inputs` to *every* agent step's assembled context — correct, existing, unchanged behaviour, since every prior real caller of it had only ever had one agent step to worry about. Included naively alongside the new resolver in one shared `DefaultContextManager`, this corrupted the clean single-JSON/single-text payload the `build`/`test`/`documentation` steps each expect: `DefaultContextManager.assemble()` concatenates every resolver's own items, and `PromptedAgent`'s/this pack's own `_extract_payload()`'s own `"\n\n".join(...)` flattening then produced two JSON objects (or two texts) joined by a blank line — a `json.JSONDecodeError` for `test`, and an invalid, multi-line Python string literal for `build`'s own generated file. **Resolution**: `_StepScopedResolver`, a small, pipeline-owned wrapper (in `pipeline.py`, not the Kernel) restricting `WorkflowStateResolver`'s own contribution to the `architecture` step alone — the one step that genuinely needs it (no prior step to read from) — with zero changes to `WorkflowStateResolver` itself.
- **Docker Desktop was unavailable yet again this session — both tiers of the real integration test need a real Postgres container, a genuinely discovered fact about this specific test.** Every prior single-agent test in this pack could stay deterministic without one (`InMemoryAgentRegistry`, `AgentStepExecutor.execute()` called directly, no persistence at all); this test's own job is to prove a step's real, *persisted* output reaches the next step's real input, which only exists once `SqlWorkflowInstanceRepository.advance_workflow()` has actually written it — there is no way to prove that hand-off without the real, Postgres-backed instance/step machinery underneath, regardless of whether the agents themselves make a real LLM call. **In its place, a manual, ad-hoc end-to-end trace was run this session** against a fake, in-memory `WorkflowInstanceRepository` stand-in exposing only `get_instance`/`list_steps`, driving the real `AgentStepExecutor`, the real `WorkflowStepOutputResolver`, and all four real, completely unmodified pack agents through the same code paths production would use. This is what caught the bug above (on the first run) and, after the fix, confirmed for real: a design proposal's own real content reaching Build's own real prompt (read back from Build's own persisted `instruction` field, never hand-copied by the trace itself); a real, valid file genuinely written; a real Test Agent genuinely running it and reporting a real `passed: true, exitCode: 0`; and a real Documentation Agent genuinely recording that real outcome to a real Markdown file on disk. Not a substitute for the real Postgres-backed test (unexecuted this session — the single highest-priority re-verification item once Docker Desktop is available), but materially stronger than `--collect-only` alone.
- **New tests**: `tests/unit/kernel/context_manager/test_resolvers.py` (+8) — `WorkflowStepOutputResolver`'s own whole-object JSON encoding, single-field extraction, multi-source merge with declared collision order (later step wins), transform application, three distinct no-items cases (absent from `step_sources`, source step not yet completed, only one of several sources ready), and highest-`attempt` selection. `tests/integration/workflow_engine/test_delivery_pipeline.py` (2, collect cleanly, unexecuted this session — see above) — a deterministic full-chain proof (`InMemoryAgentRegistry`, all four real agents, `EchoLLMGateway`-backed completion services for the three `PromptedAgent`-backed ones, no pack registration needed at all since `pack_id` is a plain, unenforced string column) and an opt-in live one (the real `SqlAgentRegistry`, seeded `catalog.agents` rows for all four agents). **A genuinely discovered, positive difference for the live tier**: unlike every prior single-agent live test in this pack (each needed a self-contained, test-only substitute prompt specifically because their own `{{context}}` placeholder needed a real Context Manager/workflow-instance round trip no single-agent test stood up), this test's own live tier seeds and uses all three real, shipped prompts directly — this pipeline finally *is* that round trip, for real, end to end.
- **Still deliberately narrow, exactly per this step's own approved scope**: no human-approval gating between steps, no `DockerSandbox` backend, no automated manifest → catalog installer, no new HTTP route (the `build_pipeline_trigger()` closure is callable but unrouted, exactly like `kernel/bootstrap.py`'s own demo trigger before its own later step added one), no second pipeline or general-purpose chaining mechanism beyond this one, fixed, four-step definition — the manifest's new `workflows[]` entry (`se.delivery_pipeline`) is schema-valid and re-validated, but nothing in this codebase automatically installs a manifest-declared workflow into `catalog.workflow_definitions` either (the identical, already-recorded "no automated installer" gap every catalog-backed entity in this codebase shares).
- `mypy --strict` (273 source files, kernel + this pack together), `ruff check`, `ruff format --check` all clean. Unit suite: **603 passed** (553 Kernel + 8 new resolver tests + 42 pre-existing pack tests), zero regressions. **Environment note:** Docker Desktop was unavailable again this session — see this section's own bug/manual-trace bullets above for how this step's real end-to-end proof was verified in its place; re-running `tests/integration/workflow_engine/test_delivery_pipeline.py` (both tiers) is the single highest-priority re-verification item once Docker Desktop is available again.
