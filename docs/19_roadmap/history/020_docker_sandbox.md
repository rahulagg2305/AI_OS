### Stage B/C – DockerSandbox: A Real ADR-0016 Tier 1 Sandbox Backend (Eighth Increment Under the New Priority)

- **Read `implementation_status.md`, `DOCUMENTATION_INDEX.md`, ADR-0016, and `security_architecture.md` §5.1 before writing any code — both documents converged on an identical, specific control list, used directly as this step's own checklist**: network disabled by default, read-only root with one writable working-copy mount plus `tmpfs` scratch, non-root `--user`, `--cap-drop=ALL`/`--security-opt=no-new-privileges`, default seccomp retained (never `--privileged`/`seccomp=unconfined`), memory/CPU/PID/wall-clock limits from configuration, no Docker socket or extra host mounts, no secrets, and ephemeral per-step lifetime.
- **New `ai_os_kernel.sandbox.docker_executor.DockerSandbox`** — implements the existing `SandboxExecutor` Protocol unchanged (`guarantees` property, `execute()` with the identical signature `LocalSubprocessSandbox` already has); no caller anywhere in this codebase needed to change. Every construction parameter (`image`, `mem_limit`, `nano_cpus`, `pids_limit`, `user`, `tmpfs_size`) is a named, documented, overridable default — and, per this step's own explicit constraint, there is no parameter that could weaken isolation (no network-isolation opt-out, no extra-mount parameter, no way to request `privileged` or `seccomp=unconfined`).
- **Every Tier 1 control genuinely requested from the Docker Engine, not merely intended**: `network_mode="none"`; `read_only=True` plus exactly one `volumes={...}` entry (the caller's own `working_directory`, resolved, bind-mounted read-write at `/workspace`) plus one `tmpfs={"/tmp": "size=64m"}` scratch mount; `user="65534:65534"` (nobody:nogroup) by default; `cap_drop=["ALL"]`; `security_opt=["no-new-privileges"]`; `mem_limit`/`nano_cpus`/`pids_limit` passed straight through to the container's own cgroup limits. `SandboxGuarantees` for this backend: all five fields `True` — verified directly against `LocalSubprocessSandbox`'s own honest 3/5 in a dedicated test.
- **Timeout and output-cap enforcement, honestly documented as mechanically different from `LocalSubprocessSandbox`'s own live, eager-kill-on-cap-exceeded draining loop, while preserving an identical outcome guarantee.** `container.wait(timeout=...)` is raced against the deadline; a `requests.exceptions.ReadTimeout` triggers an explicit `container.kill()` and `timed_out=True`, with no partial output preserved (the identical "simple, easy to reason about" choice `LocalSubprocessSandbox`'s own docstring already commits to). When the command finishes in time, its full stdout/stderr are fetched from the Docker Engine's own log buffer and truncated client-side to `max_output_bytes` per stream — a container is not killed the instant a cap is exceeded the way a bare subprocess is here, but the caller-visible contract is identical: never more than `max_output_bytes` per stream, ever, and the wall-clock timeout remains a hard backstop regardless.
- **"Docker not available" is a clear, typed `DockerSandboxUnavailableError`, confirmed for real against this session's own genuinely-unavailable daemon.** `DockerSandbox()` construction does zero I/O; the real `docker.DockerClient` is built and `ping()`-checked, lock-guarded, only on the first `execute()` call — any `docker.errors.DockerException`/connection failure at that point is caught and re-raised with a clear message, never left as a raw third-party exception.
- **A genuine, discovered, load-bearing limitation, explicitly out of this step's own scope to fix — recorded, not silently patched.** This pack's own Build/Test/Documentation agents construct `command` using `sys.executable` — a host-specific absolute interpreter path with no reason to exist inside this backend's own minimal container image. Running those exact, already-shipped commands against `DockerSandbox` unmodified would fail outright. This step's own approved framing explicitly forbids touching agent/pack code to fix this; it is recorded here and in §5/§6 as the necessary prerequisite before `DockerSandbox` can become any agent's own default.
- **New dependency**: `docker>=7.1,<8.0` added to `kernel/pyproject.toml`'s own `dependencies` (previously only an effective transitive dependency via `testcontainers`, a dev-only one) — `uv.lock` regenerated, `uv sync --frozen --all-packages` re-run. One new, narrowly-scoped mypy override (`module = "docker.*"`, `ignore_missing_imports = true`) records that `docker` ships no types and no stub package exists.
- **A deliberate, recorded first departure from this project's own "real fakes, never mocks" testing convention.** `tests/unit/kernel/sandbox/test_docker_executor.py` (13 tests) uses `unittest.mock` — the stdlib, no new dependency — because `docker`'s own client/container classes are third-party and cannot be meaningfully re-implemented as an in-process fake the way every other Protocol in this codebase already is. Scoped narrowly to proving this backend's own Python code asks the Docker Engine for the right thing (every Tier 1 control individually asserted against the real `containers.create()` call's own kwargs, timeout-triggers-kill, output-cap truncation, container-always-removed, lazy client construction, stdin-failure-never-raises) — never that Docker itself enforces anything, which only a real daemon can prove.
- **New Kernel-side integration test** (`tests/integration/sandbox/test_docker_sandbox_live.py`, 7 tests) — the real, unmocked proof: a real container's own socket-connect attempt genuinely fails (network isolation); a real write inside the mounted working directory genuinely succeeds and is genuinely visible on the host afterward, while a real write anywhere else on the container's own root genuinely fails with "Read-only file system" (filesystem containment); a real non-root UID; a real timeout-triggered kill; genuine container removal after every call (verified against the real Docker Engine's own container list, not merely trusted); and real stdin delivery over `docker`'s own raw `attach_socket` API — the single most platform/version-sensitive mechanism in this backend. Gated by a `docker_available` fixture that pings the daemon and skips cleanly, with a clear reason, on failure — the identical opt-in-live shape (ADR-0015) this project's own LLM-key-gated tests already use.
- **Docker Desktop was unavailable yet again this session — all 7 live tests collect and skip cleanly; none could be executed for real.** A genuine, positive fact recorded rather than left implicit: GitHub Actions' own standard runners ship Docker pre-installed and running, and `ci.yml`'s own `integration` job already runs `pytest tests/unit tests/integration -v` — unlike every prior Docker-gated test in this project's history (which needed testcontainers' own separate Docker dependency to run Postgres, and were *also* blocked in CI-equivalent local runs only because this specific development machine lacks Docker Desktop), this suite should genuinely execute, unskipped, the next time CI runs.
- **Still deliberately narrow, exactly per this step's own approved scope**: no agent/pack/Workflow Engine code changed at all; `LocalSubprocessSandbox` untouched and still the default everywhere it already was; `DockerSandbox` is not wired in as any agent's own default (a small, separate decision, explicitly deferred here — see the `sys.executable`-portability limitation above); no network-isolation escape hatch or per-tool override mechanism of any kind — one consistent Tier 1 posture, no configurable weakening; the default image (`python:3.12-slim`) is tag-pinned, not digest-pinned (security_architecture.md §10's own aspirational target) — recorded as a real, later hardening step, the identical "documented hardening path, not a redesign" treatment ADR-0016 itself already gives gVisor.
- `mypy --strict` (276 source files) clean, `ruff check`/`ruff format --check` clean. Unit suite: **616 passed** (603 previous + 13 new), zero regressions. **Environment note:** Docker Desktop was unavailable again this session — the 7-test live suite collects and skips cleanly; re-running it, and the still-unexecuted `test_delivery_pipeline.py` from the previous step, are jointly the single highest-priority re-verification item once Docker Desktop is available.
