### Stage B – Workflow Step Contract: Minimum Invocation Fields (Documentation Only)
- **`docs/03_architecture/workflow/workflow_architecture.md`**: new "Step Contract (Minimum Invocation Fields)" section, placed right after "Supported Step Types." Defines exactly five optional fields a step may declare beyond `id`/`type`: `agentId` (required when `type` is `agent`), `toolId` (required when `type` is `tool`), and `promptId`/`promptVersion`/`modelAlias` (optional, `agent` steps only — inputs to that agent's own Prompt Engine render and LLM Gateway call, never consumed by the Workflow Engine itself). Five explicit rules pin down scope: `type` remains the sole discriminator; the agent/tool requiredness above; `promptId`/`promptVersion`/`modelAlias` are meaningless on a `tool` step and must not be declared there; the five other step types (`decision`/`parallel`/`sub_workflow`/`quality_gate`/`human_approval`) declare none of these fields and keep their own already-documented contracts unchanged; and these fields identify *what* to invoke, never *how* — no templating, branching, or per-step scripting, consistent with the "no large orchestration language" fence this step was explicitly approved under.
- **`docs/03_architecture/agents/agent_architecture.md`**: one cross-reference sentence added to the Invocation lifecycle, after step 7 — when a step declares `promptId`/`promptVersion`/`modelAlias`, those are the values an agent uses at invocation step 4, constructed into its `AgentRequest` at step 2. Deliberately not a restatement of the contract table itself (Constitution Article 1, "Single Source of Truth" — `workflow_architecture.md` remains the one authoritative definition).
- **`docs/08_database/data_model.md` §4.3**: one clarifying paragraph, no schema change — notes that `workflow_steps.agent_id`/`tool_id` will record what a step *actually* invoked once this contract is wired into real execution (still always `NULL` today), and that this table has no `prompt_id`/`prompt_version`/`model_alias` columns of its own — whether a per-step execution record should carry them (mirroring `evaluation.llm_calls`) is left to whoever eventually builds that wiring, not decided here.
- **Field naming**: `agentId`/`toolId`/`promptId`/`promptVersion`/`modelAlias` in the YAML-facing docs, matching every other multi-word field already in the Workflow Contract table (`qualityGates`, `humanApprovalPoints`, `failureHandling`, `retryPolicy`) and the existing `_CamelModel` alias-generator pattern (`WorkflowStep.join_policy` ↔ manifest `joinPolicy`) — the eventual Python/DB-side names would be the snake_case mirror (`agent_id`, `tool_id`, `prompt_id`, `prompt_version`, `model_alias`), matching `workflow_steps.agent_id`/`tool_id`'s already-existing column names exactly.
- **`agentId` format** matches the Agent Contract's own `id` field (`<pack_id>/<slug>`, fully qualified) exactly — the same string `catalog.agents.agent_id` already stores; **`toolId`** uses the dot-namespaced convention Coding Standards already assigns to tool/workflow/gate ids. Neither invents a new id shape.
- **Not implemented, deliberately**: `WorkflowStep` (`ai_os_kernel/workflow_engine/models.py`) still validates only `id`/`type`/`joinPolicy` — its own docstring's "no document defines a field-level contract... deferred until a doc defines them" note is now stale (a doc does define them, as of this step) but was left untouched, since fixing it would mean editing code in a documentation-only step; the next implementation step should update it alongside adding the fields themselves. `workflow_steps` gained no new columns. `DispatchingStepExecutor`/`EchoAgent`/`EchoTool` are untouched — every Agent-type step still invokes the same `EchoAgent`, ignoring these fields entirely, exactly as before this step.

### Stage B – `workflow_steps` Gains `prompt_id`/`prompt_version`/`model_alias` (Completes the Step Contract's Five Fields, Writer-Only)
- **New migration `0027_workflow_steps_prompt.py`**: purely additive — three nullable `sa.Text` columns on `workflow.workflow_steps`. No FK, no new index, mirroring `agent_id`/`tool_id`'s own shape on this same table exactly (added two steps ago). Revision id kept to 26 characters (the first draft, `0027_workflow_steps_prompt_fields`, was 33 — over the `alembic_version.version_num VARCHAR(32)` limit — caught before running any migration, not after).
- **`kernel/src/ai_os_kernel/persistence/schema.py`**: `workflow_steps` gains `prompt_id`, `prompt_version`, `model_alias` (all `sa.Text, nullable=True`), placed next to `agent_id`/`tool_id`. Typed to match `evaluation.llm_calls.prompt_id`/`prompt_version`/`model_alias` exactly (data_model.md §6) — the approved shape's "consistent with `evaluation.llm_calls` where practical." Nullability necessarily differs: `llm_calls` records one completed call that always has these; a step may declare none, some, or all of them.
- **Deliberately no foreign key on `prompt_id`/`prompt_version`** to `catalog.prompts (prompt_id, version)`, unlike `llm_calls`' own composite FK to the same target. Reasoned explicitly, not left implicit: that FK is safe on `llm_calls` because a real call actually happened against an already-rendered prompt; here, the columns merely record what a step *declared*, and no writer exists for `catalog.prompts` in this codebase (only the reader, `SqlPromptCatalog`) — a real FK would make it impossible to ever record a declared `prompt_id` without a matching catalog row, the identical failure mode the `workflow_definitions` FK saga already established as unsafe. This keeps the three new columns consistent with their `agent_id`/`tool_id` siblings, which carry no FK for the identical reason (no writer for `catalog.agents`/`catalog.tools` either).
- **`kernel/src/ai_os_kernel/workflow_engine/step_record.py`**: `WorkflowStepRecord` gains `prompt_id: str | None`, `prompt_version: str | None`, `model_alias: str | None`.
- **`kernel/src/ai_os_kernel/workflow_engine/repository.py`**: `SqlWorkflowInstanceRepository.advance_workflow()`'s `workflow_steps` insert now also copies `next_step.prompt_id`/`next_step.prompt_version`/`next_step.model_alias` — the same writer-only pattern as `agent_id`/`tool_id`, extended to the remaining three Step Contract fields in the same call. Docstring updated to describe all five fields together rather than just two.
- **Writer-only, exactly as approved**: no dispatch change, no Capability Manager registry, no Context Manager, no real Prompt Engine or LLM Gateway call from a workflow step. `DispatchingStepExecutor`/`EchoAgent`/`EchoTool` are untouched.

- **`docs/08_database/data_model.md` §4.3** updated: documents all five columns, the shared "declared, not dispatched" caveat, and the no-FK reasoning.
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite: **297 tests passing** (173 unit + 124 integration, same count as last step — one existing test extended, none added). Combined unit+integration coverage: **96.75%** (`workflow_engine/step_record.py`: 100%).

### Stage B – Minimal `AgentRegistry`/`ToolRegistry`: Real Dispatch by Declared `agentId`/`toolId`
- **New `kernel/src/ai_os_kernel/workflow_engine/registry.py`**: two Protocols, `AgentRegistry` (`resolve_agent(agent_id) -> Agent`) and `ToolRegistry` (`resolve_tool(tool_id) -> Tool`), kept separate rather than one combined "capability" Protocol — mirroring the codebase's existing separation between `Agent` and `Tool` themselves, and satisfying Interface Segregation (`AgentStepExecutor` only ever needs to resolve agents, never tools, and vice versa). Both methods are `async`, even though the one implementation here does no I/O, the same forward-looking shape already used for `PromptEngine`/`LLMGateway` — a real Capability-Manager-backed registry would plausibly need I/O (checking pack activation state, lazily importing a pack's module).
- **`InMemoryAgentRegistry`/`InMemoryToolRegistry`**: the one trivial implementation for this step — a plain `Mapping[str, Agent]`/`Mapping[str, Tool]` copied at construction time by the composition root (no pack discovery, no activation state, no permissions). Registered instances may still be `EchoAgent`/`EchoTool` — this registry does not care what an `Agent`/`Tool` actually does, only that one exists for a given id. Raises the new `AgentNotRegisteredError`/`ToolNotRegisteredError` (added to `workflow_engine/errors.py`) for an unregistered id, never a bare `KeyError`.
- **Deliberately not the Capability Manager** (kernel_architecture.md: "Controls installation, activation, deactivation, upgrades and health of Capability Packs"). No pack lifecycle, no install/activate state machine, no permissions enforcement — only a lookup from an already-validated declared id to an already-constructed instance. A real Capability-Manager-backed registry is the natural second implementation of these same two Protocols later (Stage C), not attempted here.
- **`AgentStepExecutor`/`ToolStepExecutor` now take a registry instead of a single fixed instance.** Each `execute()` call reads `step.agent_id`/`step.tool_id` (already required and validated by `WorkflowStep` — see the last few steps' own work) and resolves it through the injected registry before invoking, validating output exactly as before. A defensive `ValueError` guards the statically-impossible-but-not-provable case of `step.agent_id`/`tool_id` being `None` despite the step's own type (`WorkflowStep` validation should already have prevented this) — mirroring the existing "cannot execute step of type X" `ValueError` pattern, not silently trusting an invariant blindly.
- **`DispatchingStepExecutor` itself is unchanged** — it still only knows to route by `step.type` to whichever `StepExecutor`-conforming object it was given; it has no knowledge of registries at all. This keeps the "the only place that knows all three executors exist" property intact.
- **Real dispatch by declared id, not real capability discovery** — the approved distinction, made explicit throughout the new module's own docstring: different steps declaring different `agentId`/`toolId` values now genuinely resolve to different registered instances (proven by new tests using distinguishable fakes, not two indistinguishable `EchoAgent`s), but nothing here discovers, installs, activates, or permission-checks a capability. `DispatchingStepExecutor`'s own routing logic is untouched.
- **Every existing test constructing `AgentStepExecutor`/`ToolStepExecutor` with a bare `Agent`/`Tool` instance updated** to wrap it in a registry keyed by the step's own declared id — 2 unit test files and 1 integration test file.
- **New `tests/unit/kernel/workflow_engine/test_registry.py`** (5 tests): resolving a registered agent/tool returns the exact registered instance; resolving an unregistered id raises the new, named error; the registry's constructor copies its argument (mutating the caller's dict afterward does not affect what resolves). **2 new tests each** in `test_agent_step_executor.py`/`test_tool_step_executor.py`: an unregistered id raises clearly; two steps declaring different ids resolve to two distinguishable fakes (a `_NamedAgent`/`_NamedTool` that echoes its own name, proving real per-id routing rather than assuming two `EchoAgent`s "look the same either way").
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite: **306 tests passing** (182 unit + 124 integration). Combined unit+integration coverage: **96.59%** (`workflow_engine/registry.py`: 100%; `step_executor.py`: 95% — the two defensive "step declares no agentId/toolId" `ValueError` branches are unreached, since `WorkflowStep` validation already prevents that state from ever existing).

### Stage B – `catalog.agents`/`catalog.tools`-Backed `SqlAgentRegistry`/`SqlToolRegistry`
- **`kernel/src/ai_os_kernel/workflow_engine/registry.py`**: two new classes, `SqlAgentRegistry`/`SqlToolRegistry` — a second implementation of `AgentRegistry`/`ToolRegistry`, mirroring `SqlPromptCatalog`'s shape (SQLAlchemy 2.0 Core, ADR-0011; look up one row by its natural key; fail cleanly if missing or the query itself fails). Each confirms a declared `agentId`/`toolId` is a real, registered row in `catalog.agents`/`catalog.tools` before returning the same trivial `EchoAgent`/`EchoTool` stand-in the in-memory registries already use — `catalog.agents`/`catalog.tools` carry no `entrypoint` column in the current schema, so there is nothing to dynamically load a real implementation from (a genuine, pre-existing gap between the Agent Contract's own required `entrypoint` field and the persisted catalog schema — see "Alignment checkpoint" below).
- **The one honest exception: `catalog.tools.trust_tier` is carried through, not discarded.** `SqlToolRegistry` reads the row's real declared `trust_tier` and constructs the returned `EchoTool` with it, rather than always defaulting to `tier2_trusted`. This means a catalog-declared `tier1_sandboxed` tool is still refused by `ToolStepExecutor`'s existing ADR-0016 sandbox guard even when resolved through this catalog-backed path — silently downgrading a real trust declaration would have quietly defeated an already-built safety guarantee for no reason.
- **`EchoTool` (`workflow_engine/tool.py`) changed from a fixed class attribute to a constructor-settable `trust_tier`**, defaulting to `tier2_trusted` — every existing direct `EchoTool()` construction (no args) behaves identically to before; only `SqlToolRegistry` passes a non-default value. `EchoAgent` needed no equivalent change: nothing on `catalog.agents` is safety-relevant the way `trust_tier` is, and `AgentStepExecutor` enforces no analogous gate.
- **New errors `AgentRegistryError`/`ToolRegistryError`** (`workflow_engine/errors.py`), mirroring `PromptCatalogError`'s role: a genuine persistence-layer failure during lookup, distinct from `AgentNotRegisteredError`/`ToolNotRegisteredError` ("no such id").
- **Still deliberately not the Capability Manager**: no pack lifecycle, no activation-state check against `catalog.packs`, no permissions enforcement — a catalog row existing is the only thing either registry checks, exactly the same boundary the in-memory registries already drew, just against a real table instead of a caller-supplied mapping.
- **New `tests/integration/workflow_engine/test_registry.py`** (5 tests, real Postgres, ADR-0015): a registered agent resolves to `EchoAgent`; an unregistered agent id raises `AgentNotRegisteredError`; a registered `tier2_trusted` tool resolves to an `EchoTool` carrying that tier; a registered `tier1_sandboxed` tool resolves to an `EchoTool` honestly carrying *that* tier (proving no silent trust-tier laundering); an unregistered tool id raises `ToolNotRegisteredError`.
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite: **311 tests passing** (182 unit + 129 integration). Combined unit+integration coverage: **96.43%** (`registry.py`: 93% — only the `SQLAlchemyError`-wrapping branches are uncovered, the same precedent as `SqlPromptCatalog`'s own 91%, since nothing triggers a genuine connection failure without mocking, which ADR-0015 forbids).

### Stage B – `catalog.agents`/`catalog.tools` Gain a Required `entrypoint` Column (Schema and Migration Only)
- **New migration `0028_catalog_entrypoint.py`**: purely additive — one `TEXT NOT NULL` column on each of `catalog.agents`/`catalog.tools`. Safe unmodified for the identical reason `workflow_steps.prompt_id`/`prompt_version`/`model_alias` were: neither table has a writer anywhere in this codebase (the Manifest Loader validates a manifest file; it does not persist one), so there is no live data a `NOT NULL` addition could violate.
- **Shape resolved from the already-authoritative source, not invented**: `platform_sdk/schemas/manifest.schema.json`'s own `agents[]`/`tools[]` entries already require and validate an `entrypoint` (pattern `^[a-zA-Z_][a-zA-Z0-9_.]*:[a-zA-Z_][a-zA-Z0-9_]*$`, documented there as "Python import path, `module.path:ClassName`") — the "what shape should entrypoint be" question flagged as open in last step's own report turned out to already be answered, just not yet mirrored into the catalog schema. `entrypoint` is `sa.Text`, `NOT NULL` (required in the manifest schema, the same "required there → `NOT NULL` here" pattern already followed by every other column on these two tables), with **no `CHECK` constraint** mirroring the manifest's regex: format validation for a patterned string is the Manifest Loader's job at load time, the same convention `agent_id`'s/`tool_id`'s own documented id shapes already follow without a Postgres-level format constraint.
- **`kernel/src/ai_os_kernel/persistence/catalog_schema.py`**: `agents`/`tools` table definitions and docstring updated to match.
- **Schema and migration only, exactly as approved**: no entrypoint-loading logic (dynamic import, construction) was added. `SqlAgentRegistry`/`SqlToolRegistry` (see last step) are unchanged — they still confirm a row exists and return the same trivial `EchoAgent`/`EchoTool` stand-in regardless of what `entrypoint` says.
- **`docs/08_database/data_model.md` §5** updated: both table rows now list `entrypoint`; a new narrative paragraph explains the gap, the shape source, and why no `CHECK` constraint was added.
- **Every existing raw-SQL `INSERT INTO catalog.agents`/`catalog.tools` fixture updated** to supply a value for the new `NOT NULL` column — discovered systematically by running the full suite after the migration, not assumed: 2 test files beyond `test_migrations.py` itself (`tests/integration/llm_gateway/test_call_recorder.py`, `tests/integration/workflow_engine/test_registry.py`), plus 7 call sites within `test_migrations.py` (the `catalog_tools`/`catalog_agents` column-set and not-null tests, the trust-tier `CHECK` constraint test, and the shared `_insert_real_agent_and_prompt` helper). Two column-set assertions (`test_catalog_agents_matches_the_documented_columns`, `test_catalog_tools_matches_the_documented_columns`) updated to include `entrypoint`. No new tests needed — this is a schema-only, mechanically-verified change.
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite: **311 tests passing** (182 unit + 129 integration, unchanged — existing fixtures updated, none added). Combined unit+integration coverage: **96.43%**.

### Stage B – Minimal Entrypoint Loader for Agent/Tool Construction
- **New `kernel/src/ai_os_kernel/workflow_engine/entrypoint_loader.py`**: `EntrypointLoader.load(entrypoint: str) -> Any`, the smallest possible "resolve `module.path:ClassName`, import it, construct it with no arguments" mechanism — not a plugin framework. The regex mirrors `platform_sdk/schemas/manifest.schema.json`'s own `agents[].entrypoint`/`tools[].entrypoint` pattern exactly (the authoritative shape, not invented here). Every distinct failure mode — a malformed string, an unimportable module, a missing attribute, a name that is not a class, a constructor that raises — becomes one `EntrypointLoadError` (new, `workflow_engine/errors.py`), always chained via `from` when there is an underlying exception. Deliberately **not** a `Protocol`: there is exactly one way to dynamically import a Python module, and no second implementation is real or imminent (ADR-0004) — a fake test double for "how you import a module" is not a capability this codebase has any reason to swap, and this also directly satisfies the step's own "do not invent a large plugin framework" constraint. The loader is synchronous by design (`importlib.import_module` does blocking file I/O); the two async call sites that use it are responsible for running it off-thread.
- **`Agent`/`Tool` (`workflow_engine/agent.py`/`tool.py`) are now `@runtime_checkable` Protocols**, enabling `isinstance()` structural-presence checks against whatever a loaded entrypoint actually constructs — turning "resolved to something structurally unrelated" into a clear registry error at resolution time rather than a confusing failure the first time something calls `.execute()`.
- **`SqlAgentRegistry`/`SqlToolRegistry` (`workflow_engine/registry.py`) now do real dispatch**: each reads the row's declared `entrypoint` (tools also read `trust_tier`), loads and constructs it via `EntrypointLoader` through `asyncio.to_thread` (keeping the blocking import off the event loop), then `isinstance()`-validates the result against `Agent`/`Tool` before returning it — an entrypoint resolving to something that satisfies neither Protocol now raises `AgentRegistryError`/`ToolRegistryError`, not a bare attribute error later. Both constructors gained an optional `loader: EntrypointLoader | None = None` parameter (defaulting to a real `EntrypointLoader()`), the same "inject, but default sensibly" shape already used elsewhere in this codebase.
- **`SqlToolRegistry`'s trust-tier handling changed from override to agreement-check.** The previous step carried the catalog's `trust_tier` through by constructing `EchoTool` with it; now that a real entrypoint's own code declares its own `trust_tier` (which may not even be safely mutable — e.g. a frozen dataclass), the registry instead **compares** the loaded object's own `trust_tier` against the catalog row's declared value and raises `ToolRegistryError` ("refusing to trust either value alone") on any disagreement, rather than silently overriding either side. A real pack's own code declaring a different trust tier than its own catalog registration is exactly the kind of inconsistency ADR-0016's sandbox guard exists to surface, not paper over.
- **Zero-argument construction (`cls()`) has a real downstream consequence**: a `Tool` used as a real entrypoint must declare `trust_tier` as a class-level default (not something only settable via a constructor argument) to ever match a non-default catalog declaration, since the loader never passes constructor arguments. `tests/integration/workflow_engine/_entrypoint_stubs.py` (new, not a test module itself) provides `SandboxedStubTool`/`MismatchedTrustTierStubTool` (fixed `tier1_sandboxed` class attribute, no `__init__`) alongside `NamedStubAgent` (a distinguishable real `Agent`) and `NotAnAgentOrTool` (satisfies neither Protocol), all genuinely importable so they can serve as real `entrypoint` values in integration tests.
- **`tests/integration/workflow_engine/test_registry.py` rewritten** (10 tests, real Postgres, ADR-0015) to seed real, importable `entrypoint` values instead of the previous fake `'pack.agents:Agent'`/`'pack.tools:Tool'` placeholders, and to exercise: loading the real production `EchoAgent`/`EchoTool` entrypoints; loading a genuinely different, distinguishable custom entrypoint (`NamedStubAgent`) and running it; an unregistered id still raising `AgentNotRegisteredError`/`ToolNotRegisteredError`; a malformed/unimportable entrypoint propagating `EntrypointLoadError`; an entrypoint resolving to `NotAnAgentOrTool` raising `AgentRegistryError`/`ToolRegistryError`; a `tier1_sandboxed` entrypoint whose own code and catalog row agree resolving successfully; and a `trust_tier` disagreement raising `ToolRegistryError`. **New `tests/unit/kernel/workflow_engine/test_entrypoint_loader.py`** (12 tests, no database — pure Python import mechanics, ADR-0015 does not apply): uses its own module's dotted path as a real, importable entrypoint target for locally-defined stub classes, empirically verified (not assumed) to work under pytest's default "prepend" import mode.
- **Audited, not just assumed, which other test files' fake entrypoint placeholders needed to become real values**: `tests/integration/persistence/test_migrations.py` and `tests/integration/llm_gateway/test_call_recorder.py` both insert raw `catalog.agents`/`catalog.tools` rows for unrelated schema/FK-satisfaction purposes and never call `SqlAgentRegistry`/`SqlToolRegistry` — confirmed unaffected by re-running both files' suites, not just by tracing the code.
- **Still deliberately not the Capability Manager**: no pack lifecycle, no activation-state check, no permissions enforcement, no sandboxing, no network/code download — a catalog row existing plus its declared `entrypoint` resolving cleanly and agreeing on `trust_tier` (for tools) is the entire boundary.
