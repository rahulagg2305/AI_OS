# AI_OS Implementation History — LLM Gateway and Prompt Engine Foundation

**Milestone:** The first LLM Gateway slice, its `llm_calls` writer, the first Prompt Engine slice, `PromptedCompletionService`, the `SqlPromptCatalog`, the `catalog.prompts` composite-PK+FK retrofit, and two remaining deferred FK retrofits.

Split out of the original single `implementation_status.md` on 2026-07-28 — content preserved verbatim, in original order. See `docs/19_roadmap/history/INDEX.md`.

### Stage B – LLM Gateway: Minimal First Slice (Protocol + Reduced Contract + Trivial Implementation)
- **New `kernel/src/ai_os_kernel/llm_gateway/` package (previously an empty stub)**: `models.py` (`LLMRequest`, `LLMResponse`, `Message`, `MessageRole`, `StopReason`, `UsageRecord`) and `gateway.py` (`LLMGateway` Protocol, `EchoLLMGateway`). Mirrors the exact "one Protocol, one trivial implementation" reduction already used for `ai_os_kernel.workflow_engine.agent`/`.tool` — not the full fourteen-subsystem architecture `llm_gateway.md` §3 documents.
- **`LLMRequest` keeps exactly four of §4's documented fields**: `model_alias` (required, never a literal model id — ADR-0002's entire LLM-agnosticism mechanism, not part of any deferred subsystem), `messages`, `system` (reduced from the documented `SystemBlock[]` to a plain `str | None` — a list only matters for per-block prompt-cache breakpoints, and caching is deferred), and `max_output_tokens` (a request's own basic length bound, not the deferred Budget Enforcer's workflow/experiment cost ceiling). Excluded, each tied to an explicitly deferred subsystem: `tools`/`tool_choice` (tool-calling), `response_format` (structured output), `thinking`/`effort` (capability-negotiated routing), `stream` (streaming), `cache_hints` (caching), `budget`/`timeout_seconds` (budgets), `metadata`/`require_capabilities` (capability negotiation).
- **`LLMResponse` reduces `content` from the documented `ContentBlock[]` (`text | tool_call | thinking`) to a plain `str`** — only `text` has meaning without tool-calling/thinking, both deferred; a one-variant discriminated union would be unnecessary structure. **`stop_reason` reduces the documented five-value enum to two** (`end_turn`, `max_tokens`) — the only two a trivial, provider-free implementation can honestly produce; `tool_use`/`refusal`/`pause_turn` each need a subsystem that doesn't exist yet, and `stop_details` (which only ever accompanies `refusal`) is dropped with it. **`usage` is kept complete** against §5's full `UsageRecord` shape (including `cache_read_tokens`/`cache_write_tokens`, matching `evaluation.llm_calls`' own already-built columns, and `retries`/`fallback_used`) — a trivial implementation can honestly report zero/false for all of them, a true statement rather than an invented one. Excluded from the response: `served_from_cache` (caching), `degradations` (capability negotiation), `raw` (no real provider payload exists to pass through).
- **`EchoLLMGateway` genuinely exercises `max_output_tokens`, not a half-finished field**: it treats the field as a character-count length bound (explicitly documented as *not* a real token count — §12 forbids approximating a real tokenizer for actual accounting, "an approximation would corrupt both budget enforcement and cost reporting") and truncates its echoed content when it would exceed that bound, reporting `stop_reason = max_tokens` when truncation occurred and `end_turn` otherwise — both values in the reduced enum are genuinely reachable, not dead code. `usage.input_tokens`/`output_tokens` stay honestly `0` regardless (no real tokenizer was used for *counting*, only the field's length-cap *effect* is real). `latency_ms` is a real wall-clock measurement, not invented. `provider`/`model_id`/`model_version` are clearly-fake, honestly-labelled sentinels (`"echo"`/`"echo-1"`/`"1.0.0"`), the same transparency `EchoAgent`/`EchoTool` already use.
- **No writer to `evaluation.llm_calls`.** Observability is one of §3's fourteen subsystems and explicitly out of scope; nothing here produces a call worth recording. **No wiring into `DispatchingStepExecutor` or the Workflow Engine at all** — this step is a standalone Protocol + implementation, not yet consumed anywhere, matching the approved scope precisely ("Prompt Engine / Context Manager integration beyond what is strictly required for this minimal contract" — nothing was required, so nothing was added).
- 12 new unit tests: `tests/unit/kernel/llm_gateway/test_models.py` (6 — a well-formed request is accepted; `system` is optional; blank `model_alias`, empty `messages`, and non-positive `max_output_tokens` are all rejected; the request is genuinely frozen) and `test_gateway.py` (6 — completion echoes the conversation's *last* message regardless of earlier turns; content is truncated exactly at the bound with `stop_reason = max_tokens`; content exactly at the bound is *not* truncated; `usage` is honestly zeroed/false throughout; `provider`/`model_id` are the documented echo sentinels).
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite: **254 tests passing** (147 unit + 107 integration). Combined unit+integration coverage: **96.45%** (`llm_gateway/models.py`, `llm_gateway/gateway.py`: both 100%).

### Stage B – LLM Gateway: Minimal `evaluation.llm_calls` Writer, Wired to `EchoLLMGateway.complete()`
- **New `kernel/src/ai_os_kernel/llm_gateway/call_recorder.py`**: `LLMCallRecorder` Protocol + `SqlLLMCallRecorder`, the minimal write path for `evaluation.llm_calls` — the Observability subsystem named in `llm_gateway.md` §3/§13 ("Every call emits a span and writes one `evaluation.llm_calls` row"), reduced to exactly that one write. No span, no metrics — "no full observability platform work beyond this writer" is this step's own fence.
- **Deliberately not an `LLMGateway`-conforming decorator.** A wrapper that both calls an inner gateway and records the result would need per-call correlation context (workflow, step, agent, prompt) that the already-shipped `LLMRequest` does not carry (`metadata: TraceContext` was excluded when the request contract was reduced last step). Composed explicitly by the caller instead: call `gateway.complete(request)` first, then `recorder.record(...)` with the workflow/step context the caller already has — exactly "after a successful `EchoLLMGateway.complete()` call, write one `evaluation.llm_calls` row," the approved step's own wording, not a hidden extra abstraction. `LLMRequest`/`LLMResponse`/`EchoLLMGateway` themselves are untouched.
- **Column mapping — every value comes directly from the already-produced `LLMRequest`/`LLMResponse`/`UsageRecord`, nothing invented**: `model_alias` ← `request.model_alias`; `provider`/`model_id` ← `response.provider`/`response.model_id`; `stop_reason` ← `response.stop_reason.value`; every `UsageRecord` field maps to its identically-named column. `degradations` has no source in the reduced `LLMResponse` (capability negotiation was deferred at the contract level too) — stored as an empty JSONB array, the same "no field maps to this yet" honesty already used for `catalog.workflow_definitions.declared_permissions`. `call_id` is a new prefixed ULID (`call_`, a reasoned choice — data_model.md's own prefix list is illustrative, not exhaustive, the same reasoning already used for `lease_`/`stp_`).
- **`agent_id`/`prompt_id`/`prompt_version` are optional on the call path, exactly as approved, but the schema makes them `NOT NULL` with real foreign keys** (data_model.md §6) — there is no way to store a partial or absent combination today. All three are required together: passing fewer than three raises `LLMCallRecordingError` (new, mirrors `WorkflowDefinitionRegistrationError`'s shape) before any database access, clearly, rather than surfacing a raw `NOT NULL` violation. When all three are provided, they must reference real `catalog.agents`/`catalog.prompts` rows — enforced by the foreign keys `evaluation.llm_calls` already had (built when that table itself was created), not re-implemented here; a violation is still wrapped in the same clean error. `workflow_id`/`step_id` are always required, matching the schema exactly, and are blank-checked before any database access too.
- **New `kernel/src/ai_os_kernel/llm_gateway/errors.py`** (`LLMCallRecordingError`) and **`kernel/src/ai_os_kernel/llm_gateway/ids.py`** (`new_call_id()`), mirroring the equivalent `workflow_engine` modules exactly.
- **No unit test file for `SqlLLMCallRecorder`** — consistent with the precedent set for `SqlWorkflowDefinitionCatalog` (a thin SQL writer, exercised only against real Postgres, ADR-0015). 7 new integration tests in `tests/integration/llm_gateway/test_call_recorder.py`: a real `EchoLLMGateway.complete()` call is recorded with every column correct; providing some but not all of `agent_id`/`prompt_id`/`prompt_version` is rejected; providing none of the three is rejected identically (not silently accepted as a special "no correlation" case); blank `workflow_id`/`step_id` are each rejected before any database access; an unknown `agent_id` and an unknown `prompt_id` are each rejected by the real foreign keys.
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite: **261 tests passing** (147 unit + 114 integration). Combined unit+integration coverage: **96.53%** (`llm_gateway/call_recorder.py`, `errors.py`, `ids.py`: all 100%).

### Stage B – Prompt Engine: Minimal First Slice (Protocol + Reduced Render Contract + Trivial Implementation)
- **New `kernel/src/ai_os_kernel/prompt_engine/` package (previously an empty stub)**: `models.py` (`PromptRenderRequest`, `PromptRenderResponse`), `errors.py` (`PromptNotFoundError`, `PromptVariableMissingError`), `renderer.py` (`PromptEngine` Protocol, `InMemoryPromptEngine`). Mirrors the exact "one Protocol, one trivial implementation" reduction already used for `LLMGateway`/`EchoLLMGateway` and `Agent`/`Tool` — not the full six-subsystem architecture `prompt_engine.md` §5 documents (Prompt Registry, Version Manager, Template Renderer, Variable Validator, Prompt Resolver, Composition Engine, Observability Hook).
- **`PromptRenderRequest`/`PromptRenderResponse` model the runtime call envelope of §7's Resolution Flow (steps 1-5), not the persisted §6 Prompt Contract.** `prompt_id` and `version` are both required, and `version` is caller-supplied explicitly — no Version Manager/Prompt Resolver resolution logic, no config-driven defaults, no experiment-forced pinning (§9), all deferred. `variables` carries the runtime substitution values. The response echoes `prompt_id`/`version` back alongside the rendered `content`, exactly §7 step 5 ("rendered prompt is returned together with metadata (prompt id + version)"). Excluded, each tied to an explicitly deferred subsystem: `cache_boundary_index` (§12's stable/volatile split for the LLM Gateway's prompt-cache breakpoint, ADR-0025 — caching is this step's own fence); the full §6 Prompt Contract fields (`name`, `description`, `owner`, `template`, `input_schema`, `tags`, `metadata` — these describe the *stored* prompt, which needs real `catalog.prompts` loading, also deferred); role/alias-based requests (Prompt Resolver).
- **`InMemoryPromptEngine` holds templates in a plain `dict[tuple[str, str], str]` supplied at construction time — not `catalog.prompts`** (that table exists, schema-only, with no reader; "real prompt catalog loading beyond what is strictly needed" is this step's own explicit fence). Rendering does plain `{{variable_name}}` substitution only — §12 requires "a restricted, non-executing syntax: variable substitution and simple conditionals only," and even the documented "simple conditionals" half of that restricted syntax is deferred here, not invented as a second template language. Required variables are derived from the placeholders literally present in the template text (not a declared `input_schema`, which would need the same deferred catalog loading); a missing one raises `PromptVariableMissingError` naming every missing variable at once, before any substitution runs. An unregistered `(prompt_id, version)` pair raises `PromptNotFoundError`. Extra variables not referenced by the template are silently ignored — no over-strict rejection was documented, so none was invented.
- **Deliberately not a proxy to the LLM Gateway.** `system_architecture.md`'s "LLM Abstraction Path" is explicit: "The Prompt Engine returns a rendered prompt to the caller; it is not a proxy in the call path. The caller then invokes the LLM Gateway." Nothing here constructs an `LLMRequest` or calls `LLMGateway` — mirroring the same "composed explicitly by the caller" shape already established for `LLMCallRecorder` (not an `LLMGateway`-conforming decorator, for the analogous reason that the correlation context it would need isn't carried by the reduced request contract).
- 11 new unit tests (no integration test file — a pure in-memory component with no I/O, the same precedent as `EchoLLMGateway`/`EchoAgent`/`EchoTool`): `test_models.py` (5 — a well-formed request is accepted; `variables` defaults to empty; blank `prompt_id`/`version` are each rejected; the request is genuinely frozen) and `test_renderer.py` (6 — variables are substituted correctly; a template with no placeholders needs no variables; extra unreferenced variables are ignored; an unknown prompt id or version raises and names it; a missing required variable raises and names it; no substitution is attempted when a variable is missing).
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite: **272 tests passing** (158 unit + 114 integration). Combined unit+integration coverage: **96.67%** (`prompt_engine/models.py`, `errors.py`, `renderer.py`: all 100%).

### Stage B – PromptedCompletionService: Minimal Explicit Composition of the Prompt Engine and the LLM Gateway
- **New top-level module `kernel/src/ai_os_kernel/prompted_completion.py`** (`PromptedCompletionResult`, `PromptedCompletionService`) — a single bare module, not a new subpackage, the same "composition, not a subsystem" shape `bootstrap.py` already uses for whole-app wiring. Proves `system_architecture.md`'s "LLM Abstraction Path" end to end: `PromptEngine.render()` → build an `LLMRequest` from the rendered content → `LLMGateway.complete()`.
- **Not a `Protocol`, not a new `Agent`.** A composition of two already-injected Protocols needs no seam of its own (ADR-0004: an interface is justified only when a second implementation is real or clearly imminent). It does not implement or extend `ai_os_kernel.workflow_engine.agent.Agent` — "full Agent runtime redesign" is explicitly out of scope this step, and no real Agent exists yet to be the documented caller; nothing in the Workflow Engine calls this service.
- **Rendered content becomes the sole user message** (`Message(role=USER, content=render_response.content)`). `PromptEngine`'s reduced contract renders one block of text with no documented system/user split at this stage — that split needs the deferred Context Manager, so none was invented. `model_alias`/`max_output_tokens` are supplied by the caller directly, since a rendered prompt could never produce them.
- **Recording via the existing `evaluation.llm_calls` writer is optional, per call, and adds no new logic to `LLMCallRecorder` itself.** `call_recorder: LLMCallRecorder | None` is an optional constructor dependency; a given call is recorded only when the caller also supplies `workflow_id`/`step_id` for that call — omitting either just leaves that one call unrecorded, it does not raise. The recorder's own already-tested "`agent_id`/`prompt_id`/`prompt_version` must all be provided together" rule is untouched: `prompt_id`/`prompt_version` are always supplied automatically (echoed straight from the render response), so recording without an `agent_id` still fails inside the recorder exactly as it already did.
- **`PromptedCompletionResult`** bundles both artifacts a caller needs — `render: PromptRenderResponse` and `response: LLMResponse` — a frozen Pydantic model, consistent with every other reduced-contract shape in this codebase.
- 6 new unit tests (`tests/unit/kernel/test_prompted_completion.py`), composed entirely from already-existing trivial implementations (`InMemoryPromptEngine`, `EchoLLMGateway`) plus a new in-memory fake recorder — no real database, no real provider, no integration test file needed: a prompt renders and completes correctly; the rendered content reaches the LLM request as its user message (proven via `EchoLLMGateway`'s own truncation behavior); a template needing no variables works with none supplied; a call is recorded when a recorder and `workflow_id`/`step_id` are both given; no recording is attempted with no recorder configured; no recording is attempted when `workflow_id`/`step_id` are withheld even though a recorder is configured.
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite: **278 tests passing** (164 unit + 114 integration). Combined unit+integration coverage: **96.72%** (`prompted_completion.py`: 100%).

### Stage B – Prompt Engine: Minimal `catalog.prompts`-Backed Reader (`SqlPromptCatalog`, a Second `PromptEngine` Implementation)
- **New `kernel/src/ai_os_kernel/prompt_engine/catalog.py`**: `SqlPromptCatalog`, a second implementation of the existing `PromptEngine` Protocol, reading a template row from `catalog.prompts` by `(prompt_id, version)` instead of an in-process map. Mirrors `SqlWorkflowDefinitionCatalog`'s shape as closely as a *read* mirrors that module's *write*: a thin SQLAlchemy 2.0 Core component (ADR-0011), no Prompt Registry, no writing/admin API, no Capability Manager extension — a reader/renderer path only, exactly the approved shape.
- **Shared rendering logic extracted**: `render_template()` (plain `{{variable}}` substitution + missing-variable validation) moved out of `InMemoryPromptEngine.render()` into a module-level function in `prompt_engine/renderer.py`, now called by both implementations. The two `PromptEngine` implementations can now only ever differ in *where a template comes from*, never in what rendering means — the concrete justification ADR-0004 asks for a Protocol to earn (a second implementation is now real, not hypothetical).
- **Only `content` is read from `catalog.prompts`.** The table also has `pack_id`/`input_schema`/`content_hash` columns, but this reduced render contract (`PromptRenderRequest`/`PromptRenderResponse`) has no field for any of them yet — reading columns the contract can't expose would be dead data. Required variables still come from the placeholders literally present in `content`, not the row's own `input_schema` — validating against a declared schema remains real prompt catalog loading beyond this step's scope, the same fence `InMemoryPromptEngine` already drew.
- **`PromptNotFoundError`'s docstring generalized** (it now covers "no row" from either implementation, not just the in-memory map) and a new `PromptCatalogError` added for a genuine persistence-layer failure (a `SQLAlchemyError` during the query, distinct from "no such row"), mirroring `WorkflowDefinitionRegistrationError`/`LLMCallRecordingError`'s "fail cleanly" shape.
- **Discovered, not fixed, in this step: `catalog.prompts` still has `prompt_id` alone as its primary key** (data_model.md §5, `catalog_schema.py`) — the identical single-column-PK shape `catalog.workflow_definitions` had before its own composite-key migration. This means two versions of the same `prompt_id` cannot coexist as separate rows today, discovered empirically while writing this step's own integration test (a second version insert raised `UniqueViolationError` on `prompts_pkey`). Not fixed here: a PK migration is a distinct, higher-risk schema change needing its own explicit approval — precisely the precedent already set for `workflow_definitions`. The test was adjusted to prove the reader distinguishes two *different* `prompt_id`s correctly instead (see that test's own docstring for the full explanation); the gap itself is now tracked in §4.
- **No writer, no unit test file** — a thin SQL reader, integration-tested only against real Postgres (ADR-0015), the same precedent as `SqlWorkflowDefinitionCatalog`/`SqlLLMCallRecorder`. 4 new integration tests (`tests/integration/prompt_engine/test_catalog.py`): a real row renders with variables substituted; an unknown `prompt_id` and an unknown `version` of a known `prompt_id` each raise `PromptNotFoundError`; a missing required variable raises `PromptVariableMissingError` and names it; two distinct `(prompt_id, version)` rows render independently.
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite: **282 tests passing** (164 unit + 118 integration). Combined unit+integration coverage: **96.65%** (`prompt_engine/catalog.py`: 91% — only the `SQLAlchemyError`-wrapping branch is uncovered, since nothing in this reader triggers a genuine connection-level failure without mocking the database, which ADR-0015 forbids).

### Stage A/B – `catalog.prompts` Composite Primary Key + `evaluation.llm_calls` Prompt FK Retrofit (Closes the Gap Discovered Last Step)
- **`docs/08_database/data_model.md` §5/§6 updated first**: `catalog.prompts` now documents the composite primary key `(prompt_id, version)`, mirroring `catalog.workflow_definitions`' own row exactly; the shared "prompt and workflow-definition versions are immutable" narrative paragraph now covers both tables' composite keys and both downstream composite foreign keys (`workflow_instances` → `workflow_definitions`, `llm_calls` → `prompts`); `evaluation.llm_calls`' table row now documents `prompt_id`/`prompt_version` as a **composite FK** against `catalog.prompts (prompt_id, version)`, replacing the old single-column description.
- **`catalog_schema.py`**: `prompts.version` changed from a plain `nullable=False` column to a second `primary_key=True` column, giving the table the composite `(prompt_id, version)` primary key. **`evaluation_schema.py`**: `llm_calls.prompt_id` no longer carries an inline `sa.ForeignKey(prompts.c.prompt_id)`; a table-level `sa.ForeignKeyConstraint(["prompt_id", "prompt_version"], [prompts.c.prompt_id, prompts.c.version], name="fk_llm_calls_prompt_id_version")` replaces it — the identical pattern already used for `workflow_instances`' own composite FK to `workflow_definitions`. Both modules' docstrings updated with the same "safe by construction, discovered while building `SqlPromptCatalog`" reasoning now also recorded in the migration itself.
- **New migration `0024_catalog_prompts_pk.py`**: unlike the `workflow_definitions`/`workflow_instances` precedent (`0021`/`0023`, kept as two separate, independently-reversible migrations because the foreign key didn't exist yet when the primary key changed), this one **cannot** be split the same way — `evaluation.llm_calls.prompt_id` already carried a live foreign key to `catalog.prompts.prompt_id` (added in `0020_evaluation_llm_calls`), and Postgres refuses to drop a primary key a foreign key still depends on. One atomic migration: drop the old FK (`llm_calls_prompt_id_fkey`) → drop the old PK (`prompts_pkey`) → create the new composite PK (`pk_prompts`) → create the new composite FK (`fk_llm_calls_prompt_id_version`). The exact auto-generated constraint names were verified empirically against a real migrated Postgres container before being hardcoded into `op.drop_constraint(...)` calls, not assumed from naming-convention memory. Fully reversible (`downgrade()` restores both original constraints in reverse order).
- **The composite FK retrofit is a genuine correctness improvement, not just a mechanical necessity**: the old single-column FK only checked that `prompt_id` existed *somewhere* in `catalog.prompts`, never that `prompt_version` matched that row's actual `version`. Verified safe against every existing caller before writing the migration (`SqlLLMCallRecorder`'s callers, `tests/integration/llm_gateway/test_call_recorder.py`, `tests/integration/persistence/test_migrations.py` — all already use matching `version`/`prompt_version` pairs) and confirmed by running the full test suite with the migration in place, not assumed — the same "verify, don't assume" discipline the `workflow_definitions` FK saga established.
- **`tests/integration/persistence/test_migrations.py`**: `test_catalog_prompts_matches_the_documented_columns` updated to assert the composite PK; new `test_catalog_prompts_composite_primary_key` (mirrors the `workflow_definitions` equivalent — two versions of the same `prompt_id` now both accepted, a genuine duplicate `(prompt_id, version)` pair still rejected); new `test_evaluation_llm_calls_requires_a_matching_prompt_version` proves the new composite FK's own correctness improvement — a real `prompt_id` with a `prompt_version` that was never registered is now rejected, which the old single-column FK could not have caught. Round-trip test now covers 24 migrations.
- **`SqlPromptCatalog` needed no code change** — it already queried by `(prompt_id, version)` via a `WHERE` clause, never relying on `prompt_id` alone being unique; the approved shape's "keep SqlPromptCatalog working against the new key shape" requirement was satisfied by the reader's existing design, confirmed by re-running `tests/integration/prompt_engine/test_catalog.py` unchanged.
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite: **284 tests passing** (164 unit + 120 integration). Combined unit+integration coverage: **96.65%**.

### Stage A/B – Two Remaining Deliberately-Deferred Foreign Key Retrofits (`evaluation.experiments`, `evaluation.metrics`)
- **`evaluation_schema.py`**: `experiments` now imports `workflow_definitions` from `catalog_schema.py` (added to the existing `agents, prompts` import) and carries an inline `sa.ForeignKeyConstraint(["definition_id", "definition_version"], [workflow_definitions.c.definition_id, workflow_definitions.c.version], name="fk_experiments_definition_id_version")` — the identical composite-FK pattern `workflow_instances` already uses against the same target. `metrics.run_id` gained a plain `sa.ForeignKey(experiment_runs.c.run_id)` (`experiment_runs` is defined earlier in the same module, so no import or ordering issue). Both modules' docstrings updated to record why each was deferred and why each is safe now.
- **New migration `0025_experiments_definition_fk.py`**: purely additive (`op.create_foreign_key`, no prior constraint to drop, unlike `0024`) — `experiments.definition_id`/`definition_version` never carried a foreign key before. Safe against the existing test suite unmodified: every `evaluation.experiments` row `tests/integration/persistence/test_migrations.py` inserts already uses the `(def_test, 1.0.0)` pair that file's own autouse fixture guarantees is registered in `catalog.workflow_definitions` before every test.
- **New migration `0026_metrics_run_id_fk.py`**: also purely additive, but **not safe against the existing test suite unmodified** — discovered by attempting the retrofit and running the full suite first, not assumed. Three tests inserted a `metrics` row referencing `run_id = 'run_1'`, a value with no matching `evaluation.experiment_runs` row anywhere (nothing writes to either table in real application code yet, so there was no risk to any real code path — only to test fixtures). Two of the three needed a real `experiment_runs` row seeded first (and, transitively, a real `experiments` row for *its own* foreign key); the third already expected failure for an unrelated reason (an unregistered `workflow_id`) and needed no change.
- **New `tests/integration/persistence/test_migrations.py` helper `_insert_real_experiment_run`**: seeds a real `evaluation.experiments` row and a real `evaluation.experiment_runs` row referencing it — the minimal chain `metrics.run_id`'s new foreign key requires. Used to fix the two affected metrics tests and to write two new dedicated tests, `test_metrics_run_id_foreign_key_rejects_an_unknown_run`/`test_metrics_run_id_foreign_key_accepts_a_real_run`. Two new dedicated tests were added for the `experiments` retrofit too: `test_experiments_definition_foreign_key_rejects_an_unregistered_definition`/`_accepts_a_registered_definition`. Round-trip test now covers 26 migrations.
- **`docs/08_database/data_model.md` §6 updated**: `experiments`' and `metrics`' table rows now document their new foreign keys; a new narrative paragraph explains both retrofits and why each was deferred until now.
- `mypy --strict`, `ruff check`, `ruff format --check` all clean. Full suite: **288 tests passing** (164 unit + 124 integration). Combined unit+integration coverage: **96.65%**.

**This closes the last of the standing "still open, not to be invented away" foreign-key retrofit list** carried across the last several steps' reports — `evaluation.metrics.run_id`, `evaluation.experiments.definition_id`/`definition_version`, and (last step) `catalog.prompts`' own composite key are all resolved. The only remaining, deliberately out-of-scope schema item of this kind is `workflow_definitions`/`prompts`/`tools`/`agents`' own `pack_id` columns, still un-FK'd to `catalog.packs.pack_id` (see §4).
