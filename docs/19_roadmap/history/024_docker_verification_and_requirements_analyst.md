### Stage B/C – Bug 1: `pipeline.py`'s Own Independent `python_command` Re-Derivation
- **Root cause**: `_run_generated_file_with_python` (the pipeline's own `output_transforms` entry for the Test step) called `default_python_command()` directly — independently re-resolving "the" default sandbox backend from `AIOS_SANDBOX_BACKEND` — on the implicit assumption that this would always match whatever backend the Build/Test agents in the same run were actually using. That assumption holds only when every agent is left to its own bare default; it breaks the moment a caller explicitly injects a specific `sandbox=` into an agent (exactly what the previous step's own zero-regression test fix did for `test_delivery_pipeline.py`'s deterministic tier — `sandbox=LocalSubprocessSandbox()` was passed to each agent, but the pipeline's own transform still independently resolved `AIOS_SANDBOX_BACKEND`'s ambient value, unset and therefore `"docker"`, producing `runCommand = ["python3", ...]` for an agent whose real sandbox was `LocalSubprocessSandbox` running directly on a Windows host with no `python3` on `PATH`). Surfaced as `test_delivery_pipeline.py::test_all_four_steps_genuinely_chain_through_real_persisted_outputs` failing with `WorkflowRunOutcome.FAILED`.
- **Fix**: `_run_generated_file_with_python` became `_make_run_generated_file_with_python(python_command)` — a factory returning a closure over an explicitly-supplied `python_command`, rather than a bare function re-deriving its own. `build_pipeline_context_manager`/`build_pipeline_trigger` both gained an optional `python_command: tuple[str, ...] | None = None` parameter (defaulting to `default_python_command()` when omitted — unchanged behaviour for the real production path, where every agent genuinely does share that same default). The caller that constructs agents with an explicit `sandbox=` override must now also pass the matching `python_command` — the one party that actually knows which backend is in play, rather than two independent resolutions relying on coincidence.
- **`test_delivery_pipeline.py`'s deterministic tier** and **`test_delivery_pipeline_docker.py`** both updated to pass `python_command=LocalSubprocessSandbox().python_command` / `DockerSandbox().python_command` respectively, matching each test's own explicit agent-level overrides exactly.

### Stage B/C – Bug 2: `test_verification_agent_pack.py`'s Own Hardcoded `sys.executable`
- **Root cause**: this test resolves `TestAgentEntrypoint` through the real `SqlAgentRegistry` (`EntrypointLoader`'s own zero-argument `cls()` call — the one path with no possible constructor override), so the resolved agent's own sandbox is genuinely whatever `AIOS_SANDBOX_BACKEND` currently names (`DockerSandbox`, by default). The test then constructed its own `runCommand` using `sys.executable` directly — the identical portability bug the whole `history/023` step existed to fix, just re-introduced in test code that step didn't touch. Surfaced as a `SandboxExecutionError`: `exec: "C:\\...\\python.exe": executable file not found in $PATH` — the container genuinely rejecting a host-only path, exactly as it should.
- **Fix**: the test now reads `resolved.sandbox.python_command` off the *actually-resolved* agent instance and builds `runCommand` from that, rather than assuming a fixed interpreter path — mirroring the same fix already applied in production code. `import sys` removed (no longer used).
- **No other test file had this pattern** — confirmed by a repository-wide search for `sys.executable` in `tests/` and `capability_packs/`; every remaining occurrence either constructs `LocalSubprocessSandbox()` explicitly (unit tests, correctly self-consistent) or is this module's own now-fixed integration test.
