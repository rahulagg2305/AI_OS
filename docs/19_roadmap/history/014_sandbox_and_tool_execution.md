### Stage B/C – Sandbox: Minimal Tier 1 Sandbox Executor (ADR-0016 — First Increment Under the New Multi-Agent-Pipeline Priority)

- **Read `implementation_status.md`, `DOCUMENTATION_INDEX.md`, ADR-0016, and `security_architecture.md` before writing any code, per this step's own context-discipline requirement — and found a real architectural tension, reported rather than silently avoided or silently deferred.** ADR-0016's own "Alternatives Considered" section states plainly: "Direct subprocess execution with a restricted user — Simplest; rejected outright. It shares the kernel, filesystem namespace, and network namespace with the platform, and offers no meaningful containment for hostile code." security_architecture.md §5.1 likewise names the Tier 1 runtime as "Ephemeral OCI container per step, via `SandboxRuntime` (Docker/Podman...)" with no subprocess-only path documented anywhere. This step's own approved framing nonetheless asks for a real `LocalSubprocessSandbox` "per ADR-0016's Tier 1 guarantees" — a genuine, direct tension with the ADR's own explicit rejection, not a documentation-naming quibble. **Resolution, consistent with the framing's own signal that a future Docker/OCI backend is the real Tier 1 implementation:** build the subprocess backend for real and useful today, but make it **truthfully self-report**, via a new `SandboxGuarantees` matrix, exactly which ADR-0016 controls it does and does not actually enforce at the OS level — rather than silently claiming Tier 1 compliance it cannot deliver, or silently weakening what it does implement. This mirrors the identical "declare a real, checkable capability matrix instead of asserting or hiding a limitation" precedent the LLM Gateway's own `ProviderCapabilities`/`CapabilityNegotiator` already established (see this document's own earlier entry). Not a full stop-and-report halt, since the framing's own "interface ready for a future Docker/OCI backend" language already anticipated exactly this two-tier resolution.
- **Naming discrepancy surfaced, not silently reconciled:** ADR-0016 and security_architecture.md both name this seam `SandboxRuntime`; this step's own approved framing calls it `SandboxExecutor`. The new package uses `SandboxExecutor` (per the explicit framing), with the discrepancy recorded in the package's own docstring for a future documentation pass to reconcile.
- **New `ai_os_kernel.sandbox` package**: `SandboxExecutor` Protocol (`execute(*, command: Sequence[str], working_directory: Path, timeout_seconds: float, max_output_bytes: int, env: Mapping[str, str] | None = None) -> SandboxResult`, plus a `guarantees: SandboxGuarantees` property) — every parameter shaped for a future container backend too, not only for a subprocess, per this step's own "no change to callers" requirement. `SandboxResult` (`exit_code: int | None`, `stdout`, `stderr`, `timed_out`, `truncated`, `duration_seconds`) and `SandboxGuarantees` (five booleans, one per ADR-0016 control this step's own framing named) are new, frozen Pydantic models. `SandboxExecutionError` is a new exception for invalid input and start-up failure — never for the executed command's own non-zero exit code, which is a legitimate result, not an error.
- **`LocalSubprocessSandbox` — real, working, and honestly incomplete, exactly as the resolution above requires.** Declares `enforces_timeout=True`, `enforces_output_cap=True`, `enforces_secret_exclusion=True`, `enforces_network_isolation=False`, `enforces_filesystem_containment=False`. What is genuinely enforced: **secret exclusion** — the child process never inherits `os.environ` at all; its environment is built from nothing but a small, explicit, execution-necessary allowlist (`PATH`, and on Windows `SYSTEMROOT`/`PATHEXT`/`COMSPEC`) plus whatever the caller explicitly passes via `env` — there is no leak to prevent because there is no inheritance to begin with, not best-effort scrubbing of a larger inherited set. **A real wall-clock timeout** and **a real, eagerly-enforced per-stream output cap** — the moment either stdout or stderr exceeds `max_output_bytes`, the process is killed immediately (`truncated=True, timed_out=False`), rather than left running and blocked on an undrained pipe until the unrelated timeout eventually catches it — a distinct, deliberately-designed outcome from a real timeout, not conflated with it. **No `shell=True`, ever** (security_architecture.md §15) — `command` is a `Sequence[str]` executed via `asyncio.create_subprocess_exec`, so shell metacharacters in an argument are never interpreted. What is honestly *not* enforced, per `guarantees`: no network isolation (nothing prevents the child from opening a socket — this backend must never run genuinely untrusted/hostile code for that reason alone) and no filesystem containment (`working_directory` sets the child's starting cwd and is validated to exist, but is not a jail — an absolute path or `..` still escapes it). No memory/CPU/PID limits either (ADR-0016 assigns these to OCI runtime configuration; enforcing them for a bare subprocess needs platform-specific primitives — POSIX `resource.setrlimit`, Windows Job Objects — this step's own framing does not name and which were judged real, avoidable complexity for a first slice, left to a more capable local backend or, more likely, made a configuration line by the container backend instead).
- **A real, Windows-`ProactorEventLoop`-specific bug was found and fixed during implementation, not left in.** The first working version wrapped the whole read-and-wait sequence in `asyncio.wait_for` and relied on cancellation to interrupt a timed-out or over-cap read — this hung indefinitely on Windows: cancelling a `Task` blocked on a pending subprocess-pipe read does not reliably unblock it, since the underlying OS read only completes once the pipe actually produces data or closes, and cancellation alone does not force that. Fixed by restructuring around `asyncio.wait(..., return_when=FIRST_COMPLETED)` in a deadline-bounded loop that **kills the process before cancelling** — killing closes both pipe ends, which lets every pending read (and the process-exit wait) resolve promptly on its own, with `cancel()` reduced to cleanup rather than the mechanism relied on to end a hang. Found and fixed by actually running the tests locally, not by inspection alone — this bug would not have been caught by `mypy`/`ruff` or by reading the code, only by execution.
- **New tests only, and — for the first time in five consecutive steps — genuinely executed this session, not just DDL-compiled or reasoned about.** `tests/unit/kernel/sandbox/test_executor.py`: 18 tests, no Docker/Postgres dependency at all (a real OS subprocess needs neither), using `sys.executable` throughout so the suite is portable between this session's Windows environment and CI's Linux runners without relying on any shell built-in. Covers: successful/non-zero-exit/stderr-separated execution; running in the given working directory; a hanging process genuinely killed on timeout; output genuinely truncated and the process genuinely killed early when a stream exceeds its cap; **the load-bearing secrets-isolation proof this step's own requirement named** — a secret set in the *test process's own* environment via `monkeypatch.setenv` is confirmed absent from the sandboxed child's observed environment, and more broadly, no arbitrary ambient variable crosses over unless explicitly passed via `env=`; explicitly-provided `env` values do pass through; **the load-bearing shell-injection-immunity proof** — a payload containing `$(...)`/`` `...` ``/`&&` is printed back byte-for-byte, never evaluated; every invalid-input rejection (empty command, non-positive timeout/output cap, missing working directory, nonexistent executable); and a direct equality check that `guarantees` reports the honest, reduced set of controls documented above.
- **Still deliberately narrow, exactly per this step's approved scope**: no `DockerSandbox`/OCI backend (the Protocol is shaped to accept one later with no caller change, but none is implemented), no real `Tool` using this sandbox, no Tool Invoker wiring (no such package exists in this codebase yet — confirmed by inspection, a gap worth naming for the roadmap, not silently filled), no Capability Pack, no relaxation of any control this step did implement.
- `mypy --strict` (251 source files), `ruff check`, `ruff format --check` all clean. Unit suite: **539 passed** (521 previous + 18 new), zero regressions, zero flakes observed this run. **Environment note:** this step needed no Docker/Postgres at all — the first fully, genuinely test-verified step in five consecutive steps, rather than one cross-checked only via DDL/SQL compilation. A cosmetic, non-blocking `PytestUnraisableExceptionWarning` (an "unclosed transport"/"Event loop is closed" `ResourceWarning`) is observed on this Windows session when a killed subprocess's pipes are torn down after the per-test event loop closes — does not fail any test (no `filterwarnings` configured to error on it), not reproduced by inspection as a Linux/CI concern (CI runs `ubuntu-latest`, whose asyncio subprocess implementation does not share Windows' `ProactorEventLoop` pipe-transport-closing behaviour), and not chased further with a private-API workaround given "stay inside this one small step."

### Stage B/C – A Real `tier1_sandboxed` Tool, and a Narrowed `ToolStepExecutor` Guard (Second Increment Under the New Priority)

- **Read `implementation_status.md`, `DOCUMENTATION_INDEX.md`, ADR-0016, and workflow_architecture.md's Tool Contract before writing any code, per this step's own context-discipline requirement.** Direct inspection of `ai_os_kernel.workflow_engine.step_executor`/`tool.py` confirmed the exact blocker this step closes, named in the prior step's own §6 recommendation: `ToolStepExecutor.execute()` refused *every* `tier1_sandboxed` tool unconditionally (`tool.trust_tier is not TrustTier.TIER2_TRUSTED` → always raise), and its own docstring said so in as many words ("no sandbox exists yet"). No new architectural contradiction was found — this step's own framing already anticipated the exact resolution shape the previous step's `SandboxGuarantees` design set up.
- **New `ai_os_kernel.workflow_engine.tool.SandboxBackedTool`**: a second `@runtime_checkable` structural-marker Protocol (`sandbox: SandboxExecutor`), the identical "structural presence check, not a concrete-type check" shape `Tool` itself already uses for `SqlToolRegistry`'s own entrypoint validation. Exists solely so `ToolStepExecutor` can tell a genuinely sandbox-backed tool apart from one that merely declares the tier.
- **New `ai_os_kernel.workflow_engine.sandboxed_tool.SandboxedCommandTool`**: the first real `tier1_sandboxed` `Tool`. `trust_tier` is a fixed class attribute (not constructor-settable like `EchoTool`'s), since — unlike `EchoTool`, which can honestly claim either tier depending on how it's used — this Tool's entire behaviour *is* what `tier1_sandboxed` describes. `execute()` delegates to an injected `SandboxExecutor`, mapping its `SandboxResult` onto a new, real `output_schema` (`exitCode: integer|null`, `stdout`, `stderr`, `timedOut`, `truncated`, `durationSeconds`). Command, working directory, timeout, output cap, and any explicit environment are all supplied at **construction**, not per invocation — `execute(inputs)` ignores whatever it is called with (currently always `{}`), preserving the already-established "no per-step input-mapping mechanism exists yet" deferral this step's own framing explicitly keeps on record, rather than inventing one to make the command "configurable."
- **`ToolStepExecutor`'s guard is narrowed, not weakened — and this distinction is enforced in code, not just asserted in prose.** New logic: a `tier1_sandboxed` tool is dispatched only when `isinstance(tool, SandboxBackedTool) and tool.sandbox is not None`; anything else (no `sandbox` attribute at all, or one that is structurally present but `None`) still raises the identical `ToolSandboxRequiredError` as before. `tier2_trusted` tools are completely unaffected — the same always-allowed path, byte-for-byte. `ToolSandboxRequiredError`'s own docstring, and `ToolStepExecutor`'s, were both updated to state the narrowed rule precisely rather than leaving the old "only tier2_trusted" wording stale and misleading.
- **No architectural upgrade is claimed by this step, and none should be inferred from a passing test.** Whichever `SandboxExecutor` a `SandboxedCommandTool` is constructed with is what actually runs the command — today, `LocalSubprocessSandbox`, whose own `guarantees` (previous step) honestly report no network isolation and no filesystem containment. Dispatching a `tier1_sandboxed` tool through this path does not change that; `SandboxedCommandTool`'s own docstring restates it explicitly so a future reader does not mistake "the guard let it through" for "this is now safe for hostile code."
- **New tests, all genuinely executed this session (no Docker/Postgres — a real OS subprocess needs neither):** `tests/unit/kernel/workflow_engine/test_sandboxed_tool.py` (7 tests) — `trust_tier` is `TIER1_SANDBOXED`; the tool satisfies `SandboxBackedTool` and exposes the same sandbox instance it was constructed with; a real command's `SandboxResult` is correctly mapped onto the declared output shape; a non-zero exit code and a real timeout are both reported correctly; `inputs` are genuinely ignored; the tool's own output genuinely validates against its own declared `output_schema`. `tests/unit/kernel/workflow_engine/test_tool_step_executor.py` (+3): a `tier1_sandboxed` tool whose `sandbox` attribute is structurally present but `None` is still refused (proving the guard checks the value, not just presence); **the real end-to-end proof this step exists for** — a `WorkflowStep` of type `tool`, resolved through `ToolStepExecutor`, genuinely executes a real OS command through a real `SandboxExecutor`, with the real stdout/exit code/timed-out fields flowing all the way back; and a genuinely sandbox-backed tool's output is still schema-validated, not exempted from that check. (One portability fix made while running these for real: a child `print()`'s line ending is `\r\n` on Windows vs `\n` elsewhere — assertions compare `.strip()`'d output, not exact bytes, so the suite is genuinely cross-platform rather than accidentally Windows-shaped.)
- **Still deliberately narrow, exactly per this step's approved scope**: no `DockerSandbox` backend, no Capability Pack, no Architecture/Build/Test/Documentation Agent, no HTTP route, no `kernel/bootstrap.py` wiring (proving the dispatch path needed no real running-Kernel consumer — the unit tests are the end-to-end proof), and this codebase still has no `tool_invoker` package at all (re-confirmed by inspection, not newly discovered).
- `mypy --strict` (253 source files), `ruff check`, `ruff format --check` all clean. Unit suite: **549 passed** (539 previous + 10 new), zero regressions. **Environment note:** no Docker/Postgres needed again this step; the same cosmetic, non-blocking Windows `ResourceWarning` family from the previous step is observed a few more times (proportional to the number of new real-subprocess tests) — still not a test failure, still not reproduced as a Linux/CI concern.
