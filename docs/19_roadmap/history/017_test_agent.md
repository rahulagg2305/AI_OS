### Stage B/C – Test Agent: Real Sandboxed Verification, No LLM Judgment (Fifth Increment Under the New Priority)

- **Read `implementation_status.md`, `DOCUMENTATION_INDEX.md`, and the code needed for this step before writing any — found two real, load-bearing gaps during implementation, both resolved and recorded, neither blocking.**
- **Discovery 1 — `AgentStepExecutor` has no per-step mechanism to hand any agent arbitrary structured fields.** `_invocation_inputs()` only ever populates `promptId`/`promptVersion`/`modelAlias` (from a step's own declared fields) and `context` (from the Context Manager) — there is no way for a step to say "and also pass this agent a `workingDirectory`." Architecture and Build both never hit this because their real data flows through prompt rendering; a Test Agent that makes no LLM call has no prompt for anything to flow through. **Resolution**: new `_extract_payload()` accepts `workingDirectory`/`filePath`/`runCommand` either directly as top-level `inputs` keys (the primary, minimal, structured contract this step's own approved framing names — what a direct call, or a future real per-step input-mapping mechanism, would supply) **or**, when absent, as a single JSON object inside the Context Manager's own assembled `context` (flattened the same way `PromptedAgent._build_variables` already flattens it) — reusing the identical "context is the one real channel for external per-step data" principle Architecture/Build already established, with a JSON payload instead of free text since this agent's input is structured. Not a new input-mapping mechanism — the one that already exists, used the only way it can carry more than one named value.
- **Discovery 2 — the manifest schema itself assumes every agent uses a model.** `platform_sdk/schemas/manifest.schema.json`'s `agents[]` entry requires `modelAlias` unconditionally, with no escape hatch for an agent that calls no model at all — which this one deliberately does not. This module has no authority to change that schema (real, later Platform SDK/manifest-schema work, not "implementation details" this step's own framing grants freedom over). **Resolution**: the manifest still declares a syntactically-valid `modelAlias`, purely to satisfy the schema, with an explicit inline comment — and this module's own docstring and this document both record, prominently, that the Test Agent's real implementation never reads or uses it. `permissions` genuinely reflects reality throughout: `sandbox:execute` only, no `llm:invoke`.
- **New `ai_os_pack_software_engineering.agents.verification.TestAgentEntrypoint`** — deliberately **not** `PromptedAgent`-backed, taking this step's own constraint ("pass/fail must come from real sandboxed execution outcome, never from LLM judgment") to its cleanest conclusion: verifying an exit code needs no model call, so none is made. Simpler than `ArchitectureAgentEntrypoint`/`BuildAgentEntrypoint`: no `service_factory`, no lazily-built completion service, no lock — zero-argument construction is trivial, not merely satisfied, since nothing here needs building lazily at all. `filePath` is independently checked (resolved, containment-verified via `is_relative_to()`, existence-verified) before any sandbox call, before constructing a `SandboxedCommandTool` with the caller's exact `runCommand` — duplicating `build.py`'s own path-validation discipline rather than sharing it (the identical ADR-0004 "no shared module for a single real caller each" reasoning this pack's own `_build_real_service` duplication already established). `passed` is computed from `exitCode == 0 and not timedOut` only — the identical "written" success logic `BuildAgentEntrypoint` already uses, never from anything about `output`'s own content.
- **New manifest entry**: `agents[]` gains `test` (`permissions: [sandbox:execute]` only, a real `entrypoint`/`inputSchema`/`outputSchema`, `modelAlias` present-but-unused per Discovery 2 above, explicitly commented as such in the manifest itself). No new `prompts[]` entry — this agent uses none. **Re-validated for real**: `ManifestLoader.load_one()` re-run against the updated file, `EntrypointLoader.load()` re-run against the new agent entrypoint string — both genuinely succeed.
- **New tests, all genuinely executed this session (no Docker/Postgres — no LLM call, no network at all, the fastest-running test file across all three agents):** `capability_packs/software-engineering/tests/test_verification_agent.py` (12 tests) — zero-arg construction; a genuine passing case and a genuine failing case via direct `execute()`; a missing file, an escaping path, missing required fields, and a nonexistent working directory each rejected before any sandbox call; **the real end-to-end proof this step exists for, proven both ways** — a real `WorkflowStep` of type `agent`, dispatched through the real `AgentStepExecutor` with a real (fake-resolver-backed) Context Manager, genuinely runs a real file inside the sandbox and reports a genuinely correct pass outcome in one test and a genuinely correct fail outcome in another; a malformed JSON context payload rejected clearly; the input model constructs validly.
- **New Kernel-side integration test** (`tests/integration/workflow_engine/test_verification_agent_pack.py`), mirroring this pack's own precedent: a deterministic tier proving `SqlAgentRegistry` genuinely resolves this agent — and, **a genuinely discovered, positive difference from its two pack-mates, recorded explicitly**: a second tier needing *no live provider credentials at all*, since this agent makes no LLM call, proving a real passing and a real failing case through the `SqlAgentRegistry`-resolved instance directly, runnable unconditionally once Docker Desktop is available (no API-key skip marker anywhere in this file).
- **Still deliberately narrow, exactly per this step's approved scope**: no Documentation Agent, no automatic Build -> Test pipeline (each agent still proven independently), no `DockerSandbox` backend, no automated manifest -> catalog installer, no test-framework auto-discovery, no `kernel/bootstrap.py` wiring.
- `mypy --strict` (266 source files, kernel + this pack together), `ruff check`, `ruff format --check` all clean. Unit suite: **571 passed** (Kernel, unchanged), **30 passed** (this pack, 18 previous + 12 new), zero regressions. **Environment note:** Docker Desktop was unavailable again this session, so `tests/integration/workflow_engine/test_verification_agent_pack.py` could not be executed live; verified instead via `pytest --collect-only` plus direct execution of every unit-testable real code path (both dispatch outcomes via `AgentStepExecutor`, the payload extractor, the path validator) — this step's own tests needed no Docker/live-key workaround to be *meaningfully* verified, only to be run through the real Postgres-backed `SqlAgentRegistry` specifically. A cosmetic, harmless `PytestCollectionWarning` is emitted whenever this agent's `Test`-prefixed classes are imported into a `test_*.py` file — each is skipped automatically (all declare `__init__`), nothing is ever mis-collected; not renamed, to preserve the `Architecture`/`Build`/`Test` naming symmetry this pack's own manifest and code deliberately share.
