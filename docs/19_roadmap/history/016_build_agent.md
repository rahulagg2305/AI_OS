### Stage B/C – Build Agent: LLM Instruction to Real Sandboxed File Write (Fourth Increment Under the New Priority)

- **Read `implementation_status.md`, `DOCUMENTATION_INDEX.md`, and the code needed for this step before writing any — confirmed the exact composition needed already exists (`ArchitectureAgentEntrypoint`'s zero-arg/lazy-build pattern, `SandboxedCommandTool`, `LocalSubprocessSandbox`) and no new architectural contradiction stood in the way.** One real, load-bearing gap was found during implementation itself, not before: `SandboxExecutor.execute()` had no mechanism for delivering real *data* (LLM-produced file content) to a sandboxed command safely — an argv string risks shell-quoting/length limits for a full file, and an environment variable has real OS-level size limits. Resolved by a small, additive Protocol extension, not a workaround: new optional `stdin: bytes | None = None` on `SandboxExecutor.execute()` (and, passed straight through, on `SandboxedCommandTool`) — defaulted `None`, so no existing caller's behaviour changes; delivered concurrently with output draining (a 4th task alongside stdout/stderr/wait, not written before the read loop starts, avoiding a pipe deadlock for larger content); best-effort (a command that never reads its stdin, or closes it early, does not fail the call — `BrokenPipeError`/`ConnectionResetError` are caught and swallowed, since not needing all the input is a legitimate outcome); and, when absent, the child's own stdin is `DEVNULL`, not inherited from the Kernel process — the identical "no ambient inheritance" principle already applied to environment variables.
- **New `ai_os_pack_software_engineering.agents.build.BuildAgentEntrypoint`** — the identical zero-argument-constructible, lazily-self-composing pattern `ArchitectureAgentEntrypoint` already established (see the previous step's own reasoning for why `PromptedAgent` cannot itself be `EntrypointLoader`'s zero-arg entrypoint), reused rather than reinvented, now additionally deferring creation of its own private sandbox working directory the same way (a `tempfile.mkdtemp()` call is I/O, so it happens on first `execute()`, lock-guarded, never in `__init__`). `execute()` composes two already-real pieces: a real `PromptedAgent` (the identical `build_anthropic_prompted_completion_service()` composition `architecture.py`'s own `_build_real_service()` already uses, deliberately not shared as a common helper — each agent owns its own small copy, ADR-0004's "no shared module needed for a single real caller each") produces a completion; that completion is parsed and genuinely written through a `SandboxedCommandTool` constructed fresh per call (its command depends on the model's own output, so a new instance per invocation is the correct, already-established shape for that Tool, not a limitation).
- **The LLM's file-write instruction is parsed from a fixed, delimited text format (`FILE_PATH: ...` / `FILE_CONTENT_BEGIN` / `FILE_CONTENT_END`), not JSON — a reasoned choice, not the only option.** JSON would require the model to correctly escape arbitrary file content (quotes, newlines, backslashes) inside a JSON string — an avoidable source of parse failures for exactly the payload (source code) this agent moves; a delimited format needs no escaping, since the content between the two markers is used verbatim. A new prompt, `prompts/build_write_file.md`, instructs the model to respond in exactly this format and nothing else — no prose, no markdown fences.
- **The model's own declared file path is independently validated before any sandbox call is made — the sandbox itself still cannot be trusted to contain a write, and this step's own approved framing required the boundary to be real.** New `_resolve_safe_relative_path()`: resolves the model's path against the working directory and checks containment via `is_relative_to()` on the *resolved, joined* path, not a pre-join syntactic check. **A genuine, non-obvious cross-platform escape was found and specifically guarded against**: checking only `Path.is_absolute()` misses a root-anchored-but-driveless path (`/etc/passwd` on Windows has a root but no drive, so `is_absolute()` is `False`) — joining such a path onto an existing one silently *discards the existing path's own tail* rather than raising (`WindowsPath("C:/work") / "/etc/passwd"` == `WindowsPath("C:/etc/passwd")`, not an error). Resolving the final joined path and comparing containment catches this and every other escape form (`..` traversal, absolute paths) uniformly, regardless of syntactic shape — the identical canonical-path-resolution discipline security_architecture.md §5.2 already mandates for Tier 2 operations, applied here defensively for a Tier 1 one.
- **The write itself happens through a small, portable, no-shell Python script executed inside the sandbox — never through this module's or the pack's own Python code touching the filesystem directly**, satisfying this step's own explicit constraint ("no direct/unsandboxed file writes from agent code") literally: the script reads file content from stdin and writes it to the (already-validated, relative) path it is given, creating parent directories for a nested path the same way any normal file write would.
- **No per-workflow workspace exists yet (security_architecture.md §5.3, still Stage C) — this agent's own private temporary directory is a documented placeholder, not a claim of real workspace isolation.** New `workingDirectory` output field, added specifically because a future Test Agent verifying what this agent wrote needs to know *where* — `filePath` alone is not enough when each agent instance's directory is otherwise undiscoverable.
- **New manifest entries**: `agents[]` gains `build` (`modelAlias: coding-strong`, `permissions: [llm:invoke, sandbox:execute]`, a real `entrypoint`/`inputSchema`/`outputSchema`); `prompts[]` gains `build.write_file`; the pack's own top-level `permissions` gains `sandbox:execute` (already in the closed permission vocabulary, ADR-0023). **Re-validated for real**: `ManifestLoader.load_one()` re-run against the updated file, `EntrypointLoader.load()` re-run against the new agent entrypoint string — both genuinely succeed.
- **New tests, all genuinely executed this session (no Docker/Postgres — a real OS subprocess needs neither):** `tests/unit/kernel/sandbox/test_executor.py` (+3 — real stdin delivery and echo-back, real `DEVNULL` non-inheritance when absent, real best-effort delivery when the command never reads stdin) and `tests/unit/kernel/workflow_engine/test_sandboxed_tool.py` (+1 — stdin passthrough). `capability_packs/software-engineering/tests/test_build_agent.py` (12 tests — see the corrected note on this figure earlier in this document's own §2 narrative for this step): zero-arg construction with no eager I/O; **the real end-to-end proof this step exists for** — a real `WorkflowStep` of type `agent`, dispatched through the real `AgentStepExecutor`, genuinely results in a real file existing on disk afterward, with content traceable to the (deterministic, `EchoLLMGateway`-backed) completion; nested-path creation; lazy working-directory creation when none is supplied; a malformed completion rejected before any sandbox call, with nothing written; every path-escape case (`..` traversal, POSIX-absolute, the Windows driveless-root case) rejected; the parser and path-validator tested directly in isolation; the Pydantic input/output models construct validly.
- **New Kernel-side integration test** (`tests/integration/workflow_engine/test_build_agent_pack.py`), mirroring `test_architecture_agent_pack.py` exactly: a deterministic tier (real Postgres, no live LLM call) proves `SqlAgentRegistry` genuinely resolves this pack's Build Agent entrypoint; an opt-in live tier (skipped without `AIOS_SECRET_LLM_ANTHROPIC_API_KEY`) proves the full chain — a real `WorkflowStep`, `AgentStepExecutor`, `SqlAgentRegistry`, a real Anthropic completion, and a real sandboxed file write — using a self-contained, test-only prompt (not the pack's own shipped one, which needs a real Context Manager-supplied `context` variable this focused proof does not stand up, the identical choice `test_architecture_agent_pack.py` itself already makes).
- **Still deliberately narrow, exactly per this step's approved scope**: no Test/Documentation Agent, no automatic Architecture -> Build pipeline (each agent proven independently; wiring one's output into the other is explicitly a later step), no `DockerSandbox` backend, no automated manifest -> catalog installer, no `kernel/bootstrap.py` wiring.
- `mypy --strict` (263 source files, kernel + this pack together), `ruff check`, `ruff format --check` all clean. Unit suite: **553 passed** (Kernel), **18 passed** (this pack, including the 6 from the previous step), zero regressions. **Environment note:** Docker Desktop was unavailable again this session, so `tests/integration/workflow_engine/test_build_agent_pack.py` could not be executed live; verified instead via `pytest --collect-only` (the file imports and collects cleanly) plus direct execution of every unit-testable real code path — the sandbox's own `stdin` handling, the parser, the path validator, and the full deterministic dispatch chain via `InMemoryAgentRegistry`, all of which are the identical underlying operations the integration test would also exercise.
