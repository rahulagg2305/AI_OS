**Goal:** §5's Access / Filter Layer.
**Input:** A knowledge query from a real principal.
**Output:** Only the items that principal may see.
`knowledge_access_predicate` applies `knowledge:read` as a **SQL
predicate** in the same statement that resolves ranking and provenance —
§4's "AS SQL PREDICATES, not post-filtering", ADR-0013's "cannot leak
through ranking". Proven: retrieval genuinely *finds* the chunk while the denied query returns nothing.
**The vocabulary was not undecided** — `knowledge:read` was already in
the manifest schema's closed vocabulary; it only lacked an enforcement
point. Granted to all 5 roles (§4.2 says nothing about knowledge).
**Two forks escalated.** Absent principal → unenforced, not denied
(denying would silently starve the running `requirements-analyst` step);
an *empty* set **is** denied. `project_id` scoping is un-implementable:
no `project_id` on workflows, ingestion writes NULL. Both are R-021.
The principal thread already existed and was dropped in `_invocation_inputs`.
