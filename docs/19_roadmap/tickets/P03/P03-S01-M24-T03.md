**Goal:** A real, dedicated Git permission check through the existing narrowing chain.
**Input:** An entrypoint's own manifest-declared `permissions`.
**Output:** Git-tool reachability gated on `git:write`, not just `sandbox:execute`.

No ticket named this; recommended by the prior Task, investigated, proceeded. Confirmed real gap: `build_pack_context` forwarded a configured
`git_service` to any `sandbox:execute` entrypoint's `ToolInvokerAdapter` — every such agent (`lint`/`qa-test`/`build`/`documentation`, not only
`git-push`) could reach `platform.git.push` once a real service existed, regardless of its own declared permissions. Neither named option
(`is_authorized_to_decide_approval`'s role pattern, or the full ADR-0023 `SecurityContext` chain) is reachable as-is here — no `Principal`/
`SecurityContext` reaches `ToolInvokerAdapter` (pre-existing, disclosed; widening that Protocol is a distinct, later SDK step). Fix: gate
`git_service` on `_GIT_PERMISSION in permissions`, the identical shape the `llm`/`sandbox` checks already use — the declared-permission term,
the same partial scope `permission_grant.over_granted_permissions` (pack-ceiling term) already carries. Deliberately not a `ValueError` when
declared without a `git_service` (unlike `llm`/`sandbox`): the manifest declares it unconditionally; the service is legitimately absent today.
Proven both ways against the same real service: `[sandbox:execute, git:write]` genuinely pushes; `[sandbox:execute]` alone gets
`UnknownToolError` on every Git tool id, zero audit rows. Fixed one existing test whose own permissions list predated this check. Full suite green.
