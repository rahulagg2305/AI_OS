# ADR-0011: Persistence and Workflow State — PostgreSQL with an Append-Only Event Log

**Status:** Accepted
**Date:** 2026-07-25
**Decision Makers:** Chief Architect, Project Owner
**Related Documents:** `docs/03_architecture/workflow/state_management.md`, `docs/08_database/data_model.md`

---

## Context

Workflow state must be durable across process restarts, resumable after failure and after human approval pauses, append-only for audit, and queryable for the Dashboard. The same system must also store traceability links, evaluation results, audit records, knowledge-index metadata, and vector embeddings. AI_OS additionally needs workflow replay, which requires an ordered record of everything that happened — not just the current state.

## Decision

**PostgreSQL 16 is the single system of record.** Workflow state uses **event sourcing with a materialised snapshot**:

- `workflow_events` — append-only, monotonically sequenced per workflow instance. Every state transition, step start/finish, agent invocation, tool call, gate result, and human decision is an event. `UPDATE` and `DELETE` are revoked on this table for the application role; corrections are new compensating events. This is the replay and audit substrate.
- `workflow_instances` — a materialised current-state row per instance, updated in the same transaction as the event append. Serves fast status queries without folding the event log.

Both are written in one transaction, so the snapshot can never disagree with the log.

Supporting decisions:

| Concern | Decision |
|---|---|
| Access layer | SQLAlchemy 2.0 **Core** (not the ORM) with explicit table definitions. Predictable SQL, no lazy-loading surprises on the hot path. |
| Migrations | Alembic. Every schema change is a reviewed migration; production schema changes require human approval ([ADR-0007](ADR-0007-human-governance-for-critical-decisions.md)). |
| Work distribution | `SELECT … FOR UPDATE SKIP LOCKED` leasing over a `workflow_leases` table, with lease expiry for crashed workers. This is what allows multiple workers without a broker ([ADR-0020](ADR-0020-deployment-topology-and-scaling.md)). |
| Large artifacts | Never in the database. Stored via the Storage Service and referenced by content-addressed ID (`sha256:…`). |
| Local development | SQLite through the same repository interfaces, with a documented capability matrix. SQLite lacks advisory locks, `SKIP LOCKED`, `LISTEN/NOTIFY`, and pgvector, so it is **single-process development only** and is not a supported production configuration. |
| Timestamps | `TIMESTAMPTZ`, UTC, generated by the database. |

## Alternatives Considered

- **Temporal / durable-execution engine** — Genuinely strong on durability, timers, and retries, and this was the closest call in the decision set. Rejected because AI_OS's Workflow Engine must own Quality Gates, Human Approval Points, agent invocation, and per-run cost accounting as first-class concepts; Temporal would either duplicate that ownership or force it into activity code, blurring the invariant in [ADR-0005](ADR-0005-agents-never-communicate-directly.md). It also adds a substantial operational dependency before the first workflow runs. **Revisit trigger:** if workflow orchestration correctness (timers, retries, recovery) consumes disproportionate engineering effort in Stages C–E, or if cross-region durability becomes a requirement, reopen with a migration ADR.
- **Document store (MongoDB) for workflow state** — Flexible schema; rejected because the multi-table transactional guarantee between event append and snapshot update is the property being relied on, and traceability and evaluation queries are relational.
- **Event log in Kafka with a projected read model** — Excellent for scale; rejected as premature. It adds a broker, a projection lag window, and no transactional guarantee against the read model at a scale Postgres handles comfortably.
- **Snapshot-only state (no event log)** — Simplest; rejected because it makes replay and forensic reconstruction impossible, which the Constitution's observability principle requires.
- **Separate databases per concern** — Rejected: multiplies operational burden and forfeits cross-domain joins (for example experiment → workflow → gate results → traceability).

## Consequences

### Positive
- Replay, audit, and forensic reconstruction are available by construction, not bolted on.
- One database to operate, back up, and secure.
- Multi-worker concurrency without introducing a broker.
- Transactional consistency between state, traceability, and evaluation data.

### Negative
- The event log grows without bound; requires a documented retention and archival policy (see `docs/12_operations/operations_runbook.md`).
- Event schema evolution needs versioned event payloads from day one.
- PostgreSQL becomes a single point of failure; addressed operationally by managed Postgres with replication and PITR.

### Neutral
- SQLite in development means a capability gap developers must be aware of; documented in the data model.

## Compliance

Complies with the Constitution (Observability by Default, Traceability by Design) and `docs/03_architecture/workflow/state_management.md`.
