# Standard Report Format for an Implementation Step – AI_OS

**Status:** Active | **Last Updated:** 2026-08-13 (**both completion percentages are now mandatory in every report's status block** — see item 7; `scripts/roadmap/generate.py` emits both, and `tests/roadmap` fails the build if either is dropped). Prior: 2026-07-30 (**default evidence shape trimmed** to bullets + short snippets, full pasted output reserved for surprises/bugs/real design decisions — see item 6 and `docs/process/standing_rules.md`'s new Efficiency discipline section. Prior, same day: added 4 permanent rules: coding-standards confirmation, evidence-based claims, the phase/%/remaining-areas status block, and the optional efficiency note — see each item below and `docs/process/standing_rules.md`'s own pointer entry)

This is the report shape every approved implementation step in this project's history has ended with. Follow it unless the product owner's own approval message specifies a different format for that step (audits, infrastructure steps, and reconciliation steps have each asked for small variations — follow what was actually asked for that step; this is the default when nothing else is specified).

---

## The standard shape

1. **Files created/modified** — grouped if the step touched more than one category (e.g. "renames" vs. "doc updates" vs. "test-fixture fix").
2. **How to run the tests** — the exact command(s) actually run. **Scoped by default (added 2026-07-30, see `docs/process/standing_rules.md`'s Efficiency discipline):** a normal step runs and reports only the tests for the modules it touched plus their direct dependents, not the full suite — say so plainly ("scoped run: X passed, covering `<modules>`"). Run and report the **full** suite + full `mypy`/`ruff` sweep only at the three checkpoints that rule names (every 5th step, any core-infrastructure change, or an explicit request) — say which of the three applied when you do. Split into deterministic vs. opt-in-live tiers if both exist. State plainly whether Docker/an external dependency was available this session, and if not, what was done instead to verify (a manual trace, `--collect-only`, direct code-path execution) — never silently claim a test suite "passes" without saying whether it was actually executed, and never silently expand a scoped run into a full-suite claim. **Don't re-verify a subsystem the step's diff didn't touch and couldn't plausibly affect** (`docs/process/standing_rules.md` Efficiency discipline) — say so ("Sandbox/LLM Gateway untouched this step, prior proof stands") instead of re-running or re-tracing it.
3. **How to verify manually** — a human-runnable path to confirm the feature works, independent of the automated tests. A one-line pointer is enough when the automated test above already covers it end to end; expand only if manual verification adds something the test doesn't.
4. **Confirmation that `docs/19_roadmap/feature_inventory.md` was updated** (corrected 2026-08-12: this said `implementation_status.md`, which has been **superseded** since 2026-08-11 and must not be updated) — this is not optional, but the update itself should be small (added 2026-07-30): a status line, a percentage, a one-sentence pointer to the real detail (a commit, a test file, a `history/` entry) — not a paragraph. If the step is large enough to need its own detailed history entry, it goes in `docs/19_roadmap/history/` (see that folder's own `INDEX.md`), with only the short pointer left in `implementation_status.md` itself. The same applies to `feature_inventory.md`'s own completion-table row.
5. **Coding standards confirmation (added 2026-07-30).** Explicitly confirm the step's own changes comply with `docs/process/coding_standards.md` — don't just state that `mypy`/`ruff` are clean (that's a separate, narrower bar). Check the actual conventions that tooling can't: naming, no placeholder/speculative architecture, real fakes over mocks, no hardcoded config, discovered-gaps recorded rather than worked around. **Flag any deviation found — including in code the step didn't write**, if it was touched or read closely enough to notice. A clean "confirmed, no deviations found" is a sufficient one-line statement when true; don't manufacture verbosity when there's nothing to flag.
6. **Every claim backed by real evidence (added 2026-07-30; default evidence shape trimmed 2026-07-30).** A test count, a mypy/ruff result, a file count, "the pipeline ran end to end" — none of these are asserted from memory, from a prior step's number, or from what "should" be true. Run the command in this step and derive the number from its real output. This was already this project's actual practice (see `docs/process/standing_rules.md`'s own numeric-claims rule, born from a hard-evidence audit that caught stale test counts); it remains a permanent, unconditional reporting rule so it is never dropped for a step that feels "too small" or "too quick" to bother.
   - **Default presentation: bullet points and short evidence snippets** — a one-line result (`pytest tests/integration/test_x.py -v → 2 passed`), not the full pasted terminal block. This is a presentation rule, not a rigor rule — the command still has to actually run; only how much of its raw output gets quoted back changes.
   - **Full detail is preserved when something surprising, a bug, or a real design decision occurred** — the exact same bar this document already uses for "judgment calls worth flagging" (see item 5's spirit and the efficiency note in item 8). A clean, expected result gets a snippet; a real finding gets the space it needs.
7. **Status block (added 2026-07-30) — the report's own last section before the recommendation.** A short block, not prose:
   - **Phase:** the current phase from `feature_inventory.md`'s own Section 4 phase table (e.g. "B.5 — Multi-Agent Delivery Pipeline Proof").
   - **Phase % complete:** the phase's own real completion estimate, grounded in that section's basis, not a new vibe number.
   - **BOTH completion percentages, side by side — mandatory since 2026-08-13, never one alone.** Quote the two headline lines verbatim from a fresh `python -m scripts.roadmap.generate`, which now emits both:
     - **Ticket-weighted completion** — the share of *currently ticketed* work that is done (`done` = 1, `partial` = 0.5). This is a navigation aid, and it goes almost still late in a project: discovering a new Task grows the denominator as fast as finishing one grows the numerator.
     - **Module-average completion** — the unweighted mean of `feature_inventory.md`'s 44 per-module percentages, i.e. how much of the *system itself* exists. A module hits 100% only when the subsystem is genuinely complete, so this is the harder and more honest number.
     **Why both are required.** A document-only audit on 2026-08-13 found these two had drifted **35 points apart** — 96% ticket-weighted against 60.4% module-average — while only the flattering one was ever published. Reporting either alone is now a process violation, not a style choice. If they diverge further, say so in the report rather than picking the better one; the gap is information, not noise.
   - **Remaining:** one line naming the major feature areas still outstanding (not a full list — a pointer, e.g. "Dashboard/CLI/Voice (Phase F), remaining SE Pack agents/workflows, Quality Gate Engine").
   This replaces asking for this breakdown separately each time — it is now a standard part of every report, not a special request.
8. **Efficiency note (added 2026-07-30) — optional, include only if real.** One or two sentences on anything noticed this step that would make future steps faster or safer: a pattern worth generalizing, a repeated manual check that could be automated, a doc that's becoming unwieldy, a recurring source of friction. If nothing genuine surfaced, omit the section entirely rather than manufacturing a suggestion to fill it.
9. **Recommend the next small step only** — one recommendation, with reasoning for why it's next over the alternatives, not a menu. Wait for approval before starting it.
10. **Explicitly wait for approval before any further implementation.** Do not chain into the next step unprompted.

## Commit discipline (added 2026-07-28)

Once the repository has a git history (see `docs/process/standing_rules.md`), **commit at the end of every step**, as part of the report — state the commit hash and a one-line summary of what it captures. Follow the Git Safety Protocol already in force (no destructive operations, no force-push, never commit without being asked to push).

## What "thorough" does and doesn't mean

- Do quantify claims (`616 passed`, `218 passed, 10 skipped, 0 failed`) rather than saying "tests pass."
- Do state plainly when something could *not* be verified this session (a missing daemon, a missing API key) and what was done as the next-best substitute.
- Don't pad the report with narration of the investigation process — report findings and decisions, not the search for them.
- Don't recommend more than one next step. If several are genuinely live candidates, name them as alternatives under the one you're actually recommending, with the reasoning for the ranking.
- Items 5–8 above are meant to add a handful of lines, not double the report's length — a status block is four short lines, a coding-standards confirmation is one sentence when clean, and an efficiency note is skipped entirely when there's nothing real to say.
